18 · 消息渠道

用户不一定愿意打开你的 Web UI，但一定在飞书、钉钉或 Discord 里。 渠道（Channel）把 Agent 接入这些 IM 平台：收消息、回消息、处理工具审批， 并决定「哪条消息进哪个 Agent 的哪个会话」。

读完你能做到

  • 说清渠道适配器、网关、分发器三者的分工
  • 用 create_app(channels=[...]) 启用飞书 / 钉钉 / Discord
  • 写出「首条命中即停」的路由规则，并选对 session_scope
  • 知道多副本时为什么只能有一个进程持有长连接

先说为什么：把 Agent 放进用户已经在的地方

做一个自己的聊天页面成本不低，而且用户不会为了一个 Agent 专门打开它。 渠道把 Agent 直接放进 IM：

能力 说明
收发消息用户在平台发消息，Agent 回复到同一个聊天
主动推送Agent 可以主动向指定聊天 / 用户发消息
路由不同聊天 / 用户交给不同 Agent 与会话
多模态图片、文件收发
工具审批在对话里完成确认，而不是跳回控制台
上下文注入自动告诉 Agent 所在平台、聊天名、群聊 / 私聊

架构：适配器、网关、分发器

IM 平台（飞书 / 钉钉 / Discord）
      │  长连接
      ▼
ChannelBase 适配器 ── ChannelEvent ──▶ ChannelGateway（无状态编排）
                                          │
                                          ├─ 路由 → agent_id / session_id
                                          ├─ 驱动 ChatService.run
                                          ├─ 收集事件流
                                          └─ send_response 回平台
      ▲
      │
ChannelLifecycleDispatcher（把存储里的渠道记录与本机实例对齐）
组件 职责
ChannelBase_base.py:303 平台翻译层：连接、收消息、发回复；平台差异全在这里
ChannelGateway_gateway.py:46 无状态编排：路由、驱动运行、处理确认
ChannelLifecycleDispatcher_dispatcher.py:54 把存储里的渠道记录与本机长连接实例保持一致

适配器不 import 编排层，只产出规范化的 ChannelEvent。 这样新增平台时，不需要碰路由、会话、审批这些逻辑。

启用渠道

用 create_app 的 channels 参数 _app.py:134 声明本服务允许接入哪些类型： 

from agentscope.app import create_app
from agentscope.app.channel import (
    DingTalkChannel,
    DiscordChannel,
    FeishuChannel,
)

app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
    channels=[FeishuChannel, DingTalkChannel, DiscordChannel],
)

不传就完全不启用渠道功能。启用后，用户通过 /channels 下的接口创建、配置、启停渠道。 前端可以用 GET /channels/types 拿到每种类型的凭据表单 JSON Schema。

会话路由：交给谁、进哪个会话

路由不是一张预先写好的对照表，而是一组有顺序的规则。 resolve() _routing.py:41 按顺序匹配，首条命中即停。

字段 说明
match_keychat_id、user_id，或 metadata 里的键（如 chat_type）
match_value精确匹配；"*" 表示兜底
agent_id命中后交给谁
session_scopeper_chat 或 per_chat_user
 
{
  "bindings": [
    {
      "match_key": "chat_id",
      "match_value": "oc_product_team",
      "agent_id": "product-expert",
      "session_scope": "per_chat"
    },
    {
      "match_key": "chat_id",
      "match_value": "*",
      "agent_id": "friday",
      "session_scope": "per_chat"
    }
  ]
}

会话划分

session_scope 含义 适用
per_chat一个聊天一个会话默认；私聊天然一人一会话，群聊整群共享
per_chat_user同一聊天里每个用户各自一个会话群里多人分别和机器人对话，互不干扰

会话 ID 不是存出来的，而是用 (channel_id, agent_id, scope_key) 做 uuid5 确定性推导。所以每个节点算出的结果一致，创建会话可以幂等 _routing.py:1。

路由配置的三条硬校验

必须有且仅有一条兜底规则（match_value="*"）；兜底必须在最后； 不允许重复的 (match_key, match_value)。否则保存失败。

自定义渠道

接内置之外的平台，继承 ChannelBase，实现三个抽象成员： 

from pydantic import BaseModel, Field

from agentscope.app.channel import ChannelBase


class MyChannel(ChannelBase):
    channel_type = "my_platform"
    display_name = "My Platform"
    platform_bot_id_field = "token"

    class Credentials(BaseModel):
        token: str = Field(
            title="Bot Token",
            json_schema_extra={"format": "password"},
        )

    class Config(BaseModel):
        only_at_reply: bool = True

    def __init__(self, channel_id, credentials, config) -> None:
        self._channel_id = channel_id
        self._token = credentials.token
        self._config = config

    @property
    def channel_id(self) -> str:
        return self._channel_id

    async def start_listening(self, emit) -> None:
        self._emit = emit
        ...

    async def send_response(self, event, events) -> None:
        ...

然后把类加进 channels，它就会出现在管理界面的平台列表里。

工具确认要回传定位键

渠道收到 RequireUserConfirmEvent 后，把确认结果包成 ChannelConfirmationResultEvent，带上 chat_id、channel_user_id、tool_call_id。 服务端不会信任卡片内容，而是从会话状态里读权威的待确认调用。

需要扫码授权的平台，可以实现 credential_binding，让管理界面多出「扫码授权」页签。 绑定过程必须无状态：device code、PKCE verifier 这些都放进 provider_state 返回。

长连接与多副本

渠道靠长连接收消息，所以进程必须一直活着。这带来两个部署约束：

约束 原因
enable_channel_worker 只能有一个进程为 True 平台只会把某个机器人的事件交给一条连接；每个副本都建连会浪费甚至重复投递
不适合纯 serverless 没有长期存活的进程来维持 WebSocket

分布式部署时，每个节点可以各自维持长连接；同一条消息可能被多个节点收到， 但同一个会话在同一时刻只允许一个节点收集并发送回复，所以用户不会看到重复回答。 前提是 storage 与 message_bus 都指向共享 Redis。

安全与权限

  • 凭据加密保存，GET /channels/{id} 返回脱敏结果
  • 工具审批仍然走 08 章的权限系统，渠道只是把确认 UI 放在 IM 里
  • 确认结果只带定位键，不信任卡片回传的内容
  • IM 消息同样可能包含提示注入，权限规则与工具检查不能省
  • 二维码 / 扫码授权流程必须无状态，避免多副本丢失中间状态

陷阱与窍门

没传 channels 就找接口

不传就完全不启用渠道功能，/channels/types 也是空的。 先把需要的类列进 channels。

多个副本都开 enable_channel_worker

平台消息可能重复投递。只保留一个进程持有长连接，其余通过共享存储 / 总线协作。

兜底规则没放最后

match_value="*" 会吃掉后面所有规则。保存时的校验会拦住， 但写配置时就要有这个意识：具体规则在前，兜底在最后。

以为 match_value 支持前缀 / 正则

它是精确匹配，只有 "*" 例外。要按群 / 用户区分子集， 用 metadata 里的键（比如 chat_type）。

改 session_scope 后旧会话没变

只会影响之后的消息。已经按旧 scope 建好的会话不会被合并或迁移。

用 chat_ids 拿平台 ID

配路由时不要手抄 chat_id。GET /channels/{id}/chat_ids 会列出机器人已知的聊天，直接复制。
