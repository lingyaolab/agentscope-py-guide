15 · Agent Service

前 14 章都在「写一个 Agent」。这一章把它变成服务：多用户、多会话、可持久化、 能流式推事件、能从外部中断。核心入口只有一个 create_app， 但它要求你先想清楚三件事：状态存哪、事件怎么传、工作区归谁。

读完你能做到

  • 用 create_app 加上三个必需组件启一个服务
  • 说清 Agent、Session、Credential、Workspace 的关系
  • 走通「建 Agent → 建凭证 → 建会话 → POST /chat → 订阅 SSE」
  • 知道默认的 X-User-ID 不是鉴权，生产必须替换

先说为什么：单机脚本到服务的鸿沟

SDK 是一个库：你构造 Agent、调用 reply_stream、自己处理事件。 一旦要给多个用户用，立刻多出一堆「外围职责」：

职责 SDK 里 服务里
请求路由 你自己写 FastAPI routers
用户隔离 你自己传 每个请求解析 user_id，所有权在路由层强制
会话状态 内存 / 自己存 Storage + SessionRecord
事件推送 自己消费生成器 MessageBus + SSE，多订阅者、可重放
工作区 自己建 WorkspaceManager 按策略分配与回收
后台任务 / 定时任务 自己写 内置 ToolOffload 与 Scheduler

服务的价值就是把这些「外围」接管掉，让基于 Agent 的代码不用重写就能承接生产流量。

import uvicorn

from agentscope.app import create_app
from agentscope.app.message_bus import RedisMessageBus
from agentscope.app.storage import RedisStorage
from agentscope.app.workspace_manager import LocalWorkspaceManager

storage = RedisStorage(host="localhost", port=6379)
message_bus = RedisMessageBus(host="localhost", port=6379)
workspace_manager = LocalWorkspaceManager(
    basedir="/data/workspaces",
    ttl=3600.0,
)

app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
)

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8000)

三个组件的连接池都在应用 lifespan 里打开，关闭时释放。 启动顺序大致是 storage → message bus → workspace manager → 其他 manager → 服务； 任何一步失败，已进入的资源也会被清理。

资源模型：Agent 是模板，Session 是状态

这是最容易搞混的一点：

资源 是什么 生命周期
User 请求解析出的租户标识 外部系统负责
Credential 某 provider 的 key 与连接配置 可跨 Agent / Session 复用
Agent 展示名、system prompt、chat_config 可复用模板，不含运行时状态
Session 一次正在进行的会话 承载 AgentState、消息、模型配置
Workspace 运行时环境（文件、MCP、技能） 按 manager 策略分配，TTL 回收
Schedule cron 触发的 Agent 执行 持久化，跨重启
MessageBus 会话锁、回放、收件箱、唤醒 进程级 / Redis

记住一句话：Agent 是可复用的模板，Session 才是运行时状态。 同一个 Agent 可以在不同模型下驱动多个会话，互不干扰。

一次聊天：五步与端点

  1. POST /agent：注册 Agent 身份（展示名、system prompt、配置）
  2. GET /credential/schemas → POST /credential：发现并保存 provider key
  3. POST /sessions：创建会话，绑定模型与凭证
  4. 可选：POST /workspace/mcp、POST /workspace/skill
  5. POST /chat：触发一次运行；事件走 GET /sessions/{id}/stream

POST /chat _chat.py:54 是触发即返回的：立刻给你 {"status": "started"}， 事件通过按会话的 SSE 流异步投递。

会话：状态、SSE 与中断

同一会话同时只能跑一次

服务用 ChatRunRegistry 强制这条规则。重复 POST /chat 会返回 HTTP 409。要靠多轮触发并行，应该建多个会话，而不是并发打同一个。

SSE 支持重放与扇出

GET /sessions/{id}/stream _session.py:815 连接保持打开。后接入的客户端会先收到缓冲历史，再接收实时事件； 多个标签页或断线重连都能保持同步。帧格式与 03 章一致：data: <json>\n\n。

中断

POST /sessions/{id}/interrupt _session.py:426 是 ChatService.interrupt() _chat.py:679 的薄封装：它可以取消正在跑的回复，也可以结束 HITL 暂停的回复。 清理逻辑就是 13 章的「关闭未完成工具调用」。

会话来源

SessionRecord.origin 是带 tag 的联合类型： user、schedule、channel、team。 判断来源用 isinstance(record.origin, ChannelOrigin)，不用再检查 id 是否自洽。

多租户与鉴权

每个请求都解析出一个 user_id，凭证、Agent、会话、调度、消息都归它所有。 路由层强制所有权，所以一份部署可以服务多用户。

默认的 X-User-ID 不是鉴权

get_current_user_id deps.py:35 只是从 header 读一个字符串。任何人都能伪造。生产环境必须替换为 JWT / OAuth / session token。 

from agentscope.app.deps import get_current_user_id as default_dependency

app.dependency_overrides[default_dependency] = my_jwt_user_id

默认的资源访问策略是 DenyAllResourceAccessPolicy：用户之间不共享凭证、Agent、知识库。 要跨用户共享，传入自定义 resource_access_policy（20 章）。

MessageBus

实现 适合

它把「触发 chat」和「投递事件」解耦：调度、队友消息、后台工具完成，都是通过 inbox + wakeup 叫醒空闲会话，而不是直接调用 ChatService。

分布式部署靠共享 Redis

存储与消息总线都指向同一个 Redis，多个 worker 进程就能服务同一个逻辑服务。 会话锁在总线里，所以同一会话不会被两个进程同时跑。

两层中间件

服务里有两个完全不同的中间件层，别混：

层 包住什么 典型用途
ASGI 中间件 每次 HTTP 请求 协议适配、CORS、鉴权、OpenTelemetry
Agent 层中间件 ChatService 内每次 Agent 调用 收件箱、工具卸载、状态变更通知

框架始终安装三个 Agent 层中间件：

  • InboxMiddleware __init__.py:4： 每步推理前清空收件箱，把 HintBlock 以事件形式注入
  • ToolOffloadMiddleware __init__.py:8： 工具超时后转后台，完成时通过消息总线回送
  • StateChangeMiddleware __init__.py:7： 状态变化时发 CustomEvent

协议适配也在这里：AGUIProtocolMiddleware 通过 extra_middlewares 装载，把原生 SSE 帧改写成 AG-UI 格式。

download_secret 所有副本必须共享同一个值，否则下载令牌会随机失效

陷阱与窍门

把 X-User-ID 当鉴权

它只是占位依赖。任何人都能改 header 冒充别人。上线前一定覆盖 get_current_user_id。

同一会话并发 POST /chat

服务用 ChatRunRegistry 保证同一会话同时只跑一次，第二次返回 409。 要并行就建多个会话，别指望同一个会话排队。

多副本各自跑 scheduler / channel worker

cron 会在每个副本各触发一次，平台消息会重复投递。只保留一个进程开启， 其余通过消息总线通知持有者。

多副本 download_secret 不一致

一个副本签发的下载令牌会被另一个拒绝，表现为「下载随机失败」。 负载均衡后必须显式设置同一个值。

反代缓冲了 SSE

用户会等整段生成完才看到内容。nginx 要 proxy_buffering off， 服务端已经带了 X-Accel-Buffering: no，但反代配置仍要配合。

Agent 是模板，Session 是状态

更新 Agent 的 system prompt 会影响之后所有新会话，但不会重写已有会话的历史。 运行时状态在 SessionRecord.state 里。

20 分钟动手练习

  1. 本地起 Redis，用 create_app + RedisStorage + RedisMessageBus 启一个服务，打开 /docs 看 OpenAPI。
  2. 走一遍建 Agent → 建凭证 → 建会话 → POST /chat → 订阅 SSE，观察事件顺序。
  3. 在流式输出中途调用 POST /sessions/{id}/interrupt，确认会话回到可继续状态。
  4. 把 get_current_user_id 覆盖成一个固定用户，确认后续请求不再需要 X-User-ID。
