23 · 生产化

本地跑通和线上可用之间，隔着四件事：超时、重试、限流、部署。 这一章把它们落到 AgentScope 的具体参数上，也讲清楚哪些防护框架已经做了、 哪些必须你自己补。

读完你能做到

  • 分清模型层、Agent 层、SDK 层三层重试，避免请求次数相乘
  • 给模型调用、工具执行和整次 reply 分别设超时
  • 用中间件限制本进程并发，并知道多进程为什么要靠网关
  • 理解会话锁与 409 单飞，不让同一会话并行跑两轮
  • 用 create_app 配出可水平扩展的部署，并接上健康检查

先说为什么：生产失败不是「代码有 bug」

现象 根因 该加什么
请求偶尔卡 10 分钟 上游连接挂起，没有超时 HTTP 超时 + 整次 reply 超时
429 一来就雪崩 无退避、无并发上限 指数退避 + 并发/配额限制
同一会话出现两份回答 用户双击或多标签页同时提交 会话锁 + 409 单飞
工具卡住，整个 reply 不动 工具没有超时或卸载 工具超时 + 后台卸载
重启后任务丢了一半 状态在内存、关闭不优雅 Redis 持久化 + 优雅关闭
账单突然翻十倍 循环、重试、上下文一起膨胀 迭代上限 + 预算中间件 + 成本告警

AgentScope 已经做了其中一部分：模型重试、会话锁、工具卸载、lifespan 清理。 但全局限流、整体超时、鉴权、多副本选主不在框架里，得在部署层补。

超时：四层，别只设一层

层 默认行为 设在哪 超时后
HTTP 到模型 由 provider SDK 决定，可能很长 client_kwargs={"timeout": ...} 抛 APITimeoutError
单次工具执行 App 默认 10 秒后转后台 ToolOffloadMiddleware(timeout_secs=...) 不取消，转后台并稍后回送结果
整次 reply 无内建上限 自己用 asyncio.wait_for 或网关 取消协程，需处理中断状态
会话锁 租约 600 秒，心跳续期 MessageBusKeys.SESSION_RUN_TTL_SECS 持有进程崩溃后，其他进程最多等一个租约

OpenAI / DashScope 模型都接受 client_kwargs，直接透传给底层 openai.AsyncClient _model.py:150。 生产里至少设一个明确值： 

import os

from agentscope.credential import OpenAICredential
from agentscope.model import OpenAIChatModel

model = OpenAIChatModel(
    credential=OpenAICredential(
        api_key=os.environ["OPENAI_API_KEY"],
    ),
    model="gpt-4.1",
    max_retries=0,
    client_kwargs={
        "timeout": 30.0,
        "max_retries": 3,
    },
)

这里故意把 AgentScope 的 max_retries 设为 0，把重试交给 SDK， 原因见下一节。

整次 reply 的超时

import asyncio

from agentscope.message import UserMsg


async def reply_with_timeout(agent, text: str, timeout: float = 120):
    try:
        return await asyncio.wait_for(
            agent.reply(UserMsg(name="user", content=text)),
            timeout=timeout,
        )
    except asyncio.TimeoutError:
        # 超时是最后一道防线；用户主动取消优先用
        # POST /sessions/{id}/interrupt
        return None
wait_for 会取消协程

取消可能留下不完整的上下文与未释放的工具。用户可见的取消应走 /sessions/{id}/interrupt；wait_for 只用于兜底， 并配合前端重连与状态检查。

工具超时的语义也不是「杀掉工具」。ToolOffloadMiddleware 到点后把执行 转入后台，先给智能体一个占位结果；后台完成后通过收件箱与唤醒把真实结果送回 _tool_offload_middleware.py:79。 有副作用的工具被「超时后继续跑」未必符合预期，需要自己判断。

重试：三层叠起来会变成 16 次

同一件事有三层都在重试：

层 重试什么 间隔 默认
模型 ChatModelBase 只重试 provider 声明的可重试异常（连接、超时、429、5xx） 固定 retry_delay 3 次
Agent _call_model 捕获所有 Exception，再切 fallback 无间隔 0 次（ModelConfig.max_retries）
Provider SDK 自己的一套重试与退避 指数退避 OpenAI SDK 自带

如果每层各重试 3 次，最坏情况是 4 × 4 × 4 = 64 次请求。即使只叠两层，也是 16 次。 正确做法是只保留一层重试：

策略 AgentScope SDK 适合
交给 SDK 退避 max_retries=0 client_kwargs={"max_retries": 3} 推荐：有指数退避与抖动
交给 AgentScope max_retries=3 client_kwargs={"max_retries": 0} 需要统一所有 provider 的固定间隔
只做降级 两层都 0，配 fallback_model 0 主模型不可用时快速切换

AgentScope 模型层的重试循环在 _base.py:208， 每次固定 retry_delay 秒；SDK 那层通常更聪明，所以生产更常把重试交给 SDK。

工具不会被自动重试

tool_retries_limit _config.py:260 不是「重试次数」，而是同一个工具名 + 参数连续失败多少次后注入错误提示。 有副作用的工具更不能自动重放。

降级：主模型挂了怎么办

ModelConfig 支持一个备用模型： 

from agentscope.agent import Agent, ModelConfig

agent = Agent(
    name="assistant",
    system_prompt="You are a helpful assistant.",
    model=primary,
    model_config=ModelConfig(
        max_retries=0,
        fallback_model=backup,
    ),
)

_call_model 会先对主模型尝试 max_retries + 1 次，再切到备用模型 _agent.py:3317。 备用模型可以是不同厂商、不同价位，但要注意：

  • 上下文窗口可能不同，长上下文请求切过去会直接失败
  • 工具调用格式与能力可能不同，复杂 ReAct 场景要单独评测
  • Agent 层捕获所有 Exception， 认证失败、参数错误也会触发降级，产生无谓调用
  • 降级次数要打点：长期靠备用模型跑，说明主模型配置已经坏了
降级不是重试

重试是「同一个模型再试一次」，降级是「换一个模型」。前者解决瞬时抖动， 后者解决持续不可用。两者都开时，先想清楚总请求上限。

限流：框架只管会话，不管全局配额

先区分三种「限流」：

类型 谁来做 作用
Provider 429 模型层重试 / SDK 退避 缓解，不解决配额
本进程并发 自定义中间件 防止单实例打满
全局 QPS / 租户配额 API 网关、Redis 令牌桶 真正的配额与公平性

AgentScope 没有内建的全局限流器。单进程可以先加一个并发闸门： 

import asyncio
from typing import AsyncGenerator

from agentscope.middleware import MiddlewareBase


class ConcurrencyLimitMiddleware(MiddlewareBase):
    """限制本进程内同时进行的模型调用数。"""

    def __init__(self, limit: int = 8) -> None:
        self._sem = asyncio.Semaphore(limit)

    async def on_model_call(self, agent, input_kwargs, next_handler):
        await self._sem.acquire()
        try:
            result = await next_handler(**input_kwargs)
        except BaseException:
            self._sem.release()
            raise

        if isinstance(result, AsyncGenerator):
            async def _limited():
                try:
                    async for chunk in result:
                        yield chunk
                finally:
                    self._sem.release()

            return _limited()

        self._sem.release()
        return result
流式响应必须持有到消费完

如果拿到异步生成器就释放信号量，限的只是「建立连接」，不是「占用模型」。 上面的写法把释放放在生成器的 finally 里；调用方必须消费或关闭生成器， 否则信号量会泄漏。

多进程部署时，这个信号量只在单进程内有效。全局配额应放在网关或 Redis： 按 user_id 做令牌桶，按模型做 QPS 上限，429 时返回 Retry-After。

AgentScope 会把 provider 的 429 归类成 ErrorType.RATE_LIMIT _errors.py:18， 前端可以据此提示「稍后再试」，而不是当成内部错误。

会话单飞：同一会话只跑一轮

用户双击、多个标签页、渠道重复投递，都会让同一会话同时收到两次触发。 AgentScope 用两层保护：

机制 范围 行为
消息总线会话锁 跨进程 agentscope:session:lock:{sid}，租约 600 秒，心跳续期
ChatRunRegistry 单进程 同一会话已有运行中的 task 时拒绝再次 spawn
POST /chat HTTP 重复提交返回 409，前端应提示「正在回答」

会话锁的语义在 _base.py:327： 阻塞获取，持有期间实现方用心跳续租，进程崩溃后其他副本最多等一个租约。 ChatRunRegistry 则只管本进程的 task _chat_run_registry.py:36， 关闭时会取消所有在途运行并等待 finally 执行完 _chat_run_registry.py:117。

这意味着：同一会话的请求应该排队或拒绝，不要指望并行加速。 调度触发、队友消息、后台工具完成都通过收件箱 + 唤醒进入同一会话，而不是直接开新 run。

预算与迭代上限：防止一轮跑一天

生产里最容易失控的不是单次调用，而是 ReAct 循环：

旋钮 默认 建议
ReActConfig.max_iters_config.py:365 50 按业务降到 8–15，超限后让模型收尾
tool_retries_limit 3 连续失败注入提示，避免无限重试同一调用
ReplyBudgetControlMiddleware 未启用 给单次 reply 设加权 token 上限（第 21 章）
上下文压缩阈值 trigger_ratio=0.8 长会话开启，避免每轮都带全量历史

max_iters 不是越大越好。50 轮意味着最多 50 次模型调用 × 每次上下文增长，费用和延迟都是线性甚至更快上升。

优雅关闭：别让在途请求死在半路

应用启动与关闭由 lifespan 统一管理：所有有生命周期的资源都通过 AsyncExitStack 进入，关闭时按相反顺序拆除，启动中途失败也会清理已进入的资源 _lifespan.py:37。

关闭时 ChatRunRegistry 会取消所有在途 chat run，并等待它们释放会话锁 _chat_run_registry.py:117。 部署侧要配合：

  • Kubernetes 先摘流量，再发 SIGTERM：加 preStop 小睡几秒
  • terminationGracePeriodSeconds 要大于应用清理时间
  • uvicorn 设 --timeout-graceful-shutdown，给在途请求留窗口
  • SSE 客户端要能重连并从回放日志恢复（第 16 章）

Redis 里的会话锁有 TTL，进程被 SIGKILL 也不会永久死锁；但另一个副本要等租约到期 （默认 600 秒）才能接手。这就是为什么缩短关闭时间比直接 kill 更重要。

部署拓扑：单进程、多进程与独立 worker

形态 存储 / 总线 适合 注意
单进程 Redis / 内存总线 本地开发、桌面版 InMemoryMessageBus 不能跨进程
多副本 API RedisStorage + RedisMessageBus 生产水平扩展 共享 download_secret，调度/渠道只留一个
独立索引 worker Redis / SQL + blob store 大文档摄取 API 侧 enable_index_worker=False
独立渠道 worker Redis 飞书 / 钉钉 / Discord 长连接 只允许一个进程 enable_channel_worker=True
独立调度进程 Redis Cron 任务 只允许一个进程 enable_scheduler=True
多副本都开调度会重复执行

APScheduler 的 jobstore 在内存里，每个持有定时器的进程都会响应 cron。 多个副本各跑一遍，任务就会重复。用环境变量只在一个角色上开启。

enable_index_worker _app.py:121、 enable_channel_worker _app.py:125、 enable_scheduler _app.py:126 都是 create_app 的关键字参数。

create_app 生产参数

import os

from agentscope.app import create_app
from agentscope.app.message_bus import RedisMessageBus
from agentscope.app.storage import RedisStorage
from agentscope.app.workspace_manager import LocalWorkspaceManager

storage = RedisStorage(
    host=os.environ["REDIS_HOST"],
    port=int(os.environ.get("REDIS_PORT", "6379")),
)

    host=os.environ["REDIS_HOST"],
    port=int(os.environ.get("REDIS_PORT", "6379")),
)
workspace_manager = LocalWorkspaceManager(
    basedir="/data/workspaces",
    ttl=3600.0,
)

app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
    download_secret=os.environ["DOWNLOAD_SECRET"],
    enable_scheduler=os.getenv("ENABLE_SCHEDULER") == "1",
    enable_channel_worker=os.getenv("ENABLE_CHANNEL_WORKER") == "1",
    enable_index_worker=os.getenv("ENABLE_INDEX_WORKER") == "1",

参数 为什么生产必须管
storage / message_bus 多副本共享状态、会话锁、回放与唤醒
workspace_manager 工作目录与 TTL；容器里要给持久卷
download_secret_app.py:135 负载均衡后必须共享，否则下载令牌跨副本失效

enable_channel_worker 平台长连接只应有一条

多 worker 启动用 uvicorn app:app --workers N 即可； 前提是存储与消息总线都是 Redis 或外部共享实现。用 InMemoryMessageBus 时不要开多 worker。

健康检查：I/O-free，但需要身份头

GET /health _health.py:34 返回各组件状态：ok / not_ready / disabled。它刻意不做 I/O，只检查 app.state 上是否挂好了组件 _health.py:41： 任一组件的 not_ready 会把 HTTP 状态降为 503 _health.py:83。 

components:
  storage: ok
  message_bus: ok
  workspace_manager: ok
  chat_service: ok
  scheduler_manager: ok
  mcp_hubs: disabled
  knowledge_base: disabled
/health 需要 X-User-ID

它依赖 get_current_user_id _health.py:37， 默认实现从 X-User-ID 头取身份 deps.py:35。 裸的 k8s probe 会得到 401。要么给 probe 加请求头，要么另加一个只检查进程的 /livez。

  • liveness 只判断进程是否活着，别依赖外部 Redis
  • readiness 用 /health，覆盖组件是否挂好
  • 把应用挂成子应用（mount）时，Starlette 不会运行子应用 lifespan， /health 会一直 not_ready，这正是它想帮你抓到的配置错误

鉴权与密钥：默认的 X-User-ID 不是鉴权

X-User-ID 只是占位：任何客户端都能自称任意用户。 生产必须替换成 JWT / OAuth / session token： 

from fastapi import Header, HTTPException, status

from agentscope.app.deps import get_current_user_id as default_dependency


async def verify_token(token: str) -> str | None:
    """替换成你的 JWT / OAuth 校验。"""
    return None


async def get_current_user_id(
    authorization: str = Header(...),
) -> str:
    token = authorization.removeprefix("Bearer ").strip()
    user_id = await verify_token(token)
    if not user_id:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="Invalid token.",
        )
    return user_id


app.dependency_overrides[default_dependency] = get_current_user_id

容器化：一个能跑的最小镜像

ENV PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

    && mkdir -p /data/workspaces \

陷阱与窍门

三层重试全开

AgentScope + SDK + Agent 各试几次，最坏是几十次请求。先数清楚总尝试上限， 再决定哪一层负责退避。

只设了 HTTP 超时

模型调用没超时，但一次 reply 可能包含十几次调用和工具。没有整体上限， 请求仍可能挂很久。网关侧也要有总超时。

以为工具超时会停掉工具

ToolOffloadMiddleware 是转后台继续跑，不是取消。对有副作用、 不能被延迟执行的操作要单独设计。

多副本都开 scheduler / channel worker

Cron 会重复执行，IM 长连接会重复消费或互相顶掉。用环境变量把这两个角色限制在 一个进程。

多副本不设 download_secret

每个进程各自生成密钥，A 副本签发的下载令牌到 B 副本会被拒绝，表现为随机 401/403。

把 /health 当 liveness 且不带请求头

默认依赖会返回 401。要么给 probe 加 X-User-ID， 要么写一个不依赖身份的 /livez。

生产用 InMemoryMessageBus

它只在单进程内有效，多 worker 下锁、回放、唤醒全部失效。水平扩展必须换 RedisMessageBus。

把限流和预算分开

限流控制「同时打多少请求」，预算控制「一次能花多少 token」。 两者解决不同问题，缺一个都会在高峰期失控。
