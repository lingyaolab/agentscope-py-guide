16 · 会话与 SSE

15 章把服务跑起来了，但前端只拿到一个 session_id 和一条 SSE 连接。 这一章讲清楚：会话怎么建、消息怎么发、事件帧长什么样、断线怎么续、状态怎么判断。 写前端的人看完应该能不看源码就把界面接出来。

读完你能做到

  • 用正确的最小请求体创建一个会话，并知道哪些配置可以后补
  • 解释 POST /chat 为什么立刻返回，事件从哪里来
  • 处理 SSE 的 data: 帧、心跳、重放游标与重复事件
  • 用 before 做消息分页，用四种状态驱动界面指示器

先说为什么：SSE 不是「把 JSON 一行行发出去」

一个能用的聊天前端，要同时处理五件事：

问题 服务端的答案
断线了怎么办？回放日志 + after 游标
多个标签页同时看？扇出 + 按 entry id 去重
代理把流缓冲了？X-Accel-Buffering: no + 心跳
现在到底在跑还是等人？四值 SessionStatus
历史消息怎么翻？before 游标分页

这些都不是「发 JSON」本身，而是围绕事件流的协议。

创建会话

POST /sessions _session.py:294 的请求体里，只有 agent_id 必填：

字段 必填 说明
agent_id_session.py:60是会话归属的 Agent 模板
workspace_id否显式绑定工作区；省略时由 manager 按策略分配
name否展示名；省略时服务会在首轮后自动命名
chat_model_config_schema/_session.py:76否模型与凭证；可以后补
fallback_chat_model_config否主模型失败时的备用
tts_model_config / realtime_model_config否语音相关
knowledge_config否绑定的知识库与 RAG 参数
 
POST /sessions
X-User-ID: alice
{
  "agent_id": "agent-xxx",
  "chat_model_config": {
    "type": "deepseek_credential",
    "credential_id": "cred-xxx",

一个 (user_id, agent_id, workspace_id) 三元组最多只有一个会话： 同样的三元组再建一次，会更新已有会话，而不是新建 _session.py:303。

触发运行

POST /chat _chat.py:54 是 fire-and-forget：立刻返回 {"status": "started"}，真正的事件通过 SSE 推。

input 支持五种形态：

输入 含义
Msg一条新用户消息
list[Msg]一批消息
UserConfirmResultEventHITL 确认结果
ExternalExecutionResultEvent外部执行结果
None继续当前状态
 
POST /chat
X-User-ID: alice
{
  "agent_id": "agent-xxx",
  "session_id": "session-xxx",
  "input": {
    "name": "alice",
    "role": "user",
    "content": [{"type": "text", "text": "Hello"}]
  }
}
同一会话同时只能跑一次

会话被某个 worker 持有运行锁时，第二次 POST /chat 返回 HTTP 409。要并行，用多个会话。

SSE 帧

GET /sessions/{id}/stream _session.py:815 返回 text/event-stream。每一帧： 

data: {"type":"TEXT_BLOCK_DELTA","reply_id":"...","block_id":"...","delta":"你",...}

data: {"type":"TEXT_BLOCK_DELTA",...}

:   ← 每 30 秒一条心跳注释帧
  • 没有 event: 字段：类型在 JSON 的 type 里
  • JSON 来自 event.model_dump(mode="json")，枚举已是字符串
  • 心跳是 :\n\n，间隔 30 秒 _session.py:750
  • 响应头带 Cache-Control: no-cache 与 X-Accel-Buffering: no _session.py:971

一个最小 Python 客户端

import json

import httpx


async def consume(url: str, headers: dict) -> None:
    async with httpx.AsyncClient(timeout=None) as client:
        async with client.stream("GET", url, headers=headers) as resp:
            resp.raise_for_status()
            async for line in resp.aiter_lines():
                if not line.startswith("data: "):
                    continue
                event = json.loads(line[6:])
                handle(event)


def handle(event: dict) -> None:
    match event["type"]:
        case "TEXT_BLOCK_DELTA":
            print(event["delta"], end="", flush=True)
        case "REPLY_END":
            print(f"\n[done] {event['finished_reason']}")

重放与断线重连

连接建立时，服务先订阅、再回放：先拿到实时事件，再从回放日志读历史， 两条路径重叠的部分按 entry id 去重 _session.py:893。 

GET /sessions/session-xxx/stream?agent_id=agent-xxx&after=<cursor>

after 是回放游标，不是消息 ID。它来自消息接口返回的 event_cursor：

来源 用途
GET /sessions/{id}/messages → event_cursor下次连 SSE 时传给 after
SSE 帧里的 _entry_id内部去重键，不会出现在发给客户端的 payload 里

连接会一直保持打开，同一会话后续的多次 run 都复用同一条连接。 所以前端不需要每条消息重建 EventSource，只需要在断线后带游标重连。

先订阅，再发消息

推荐顺序是「先连 SSE，再 POST /chat」。这样不会漏掉第一帧； 即使先发了，回放日志也能补上。

扇出与去重

多个客户端可以同时订阅同一会话。服务端从消息总线同时做两件事：

  1. 回放：从日志读 after 之后的条目 _session.py:900
  2. 实时：从订阅队列持续取新事件 _session.py:942

同一条事件可能同时出现在回放和实时流里。服务端用 seen_entry_ids 去重；客户端如果自己做重连，也应保存已处理的事件 id，避免重复追加文本。

另外，团队场景下某个 worker 的 HITL 卡片会被投影到 leader 的会话流里， 以 CustomEvent 的形式出现（SubagentHitlProjector）， 前端按 name 分派即可。

消息历史：游标分页

GET /sessions/{id}/messages _session.py:591 用消息 ID 游标，不是 offset：

参数 说明
before_session.py:594上一页最后一条消息的 ID；省略拿最新一页
limit_session.py:6121–200，默认 50
offset已废弃，永远被忽略

返回四个字段：

字段 用途
messages这一页消息
event_cursorSSE 的 after 游标；只在请求最新一页时返回
is_running会话是否被 worker 持有
has_more是否还有更早的消息
用 before 时拿不到 event_cursor

只有不带 before / offset 的「最新一页」请求才会读检查点游标 _session.py:659。 翻历史时它返回 None，这是设计行为。

状态探测：四个值

GET /sessions/{id}/status _session.py:695 返回 SessionStatus _session.py:61：

值 含义
running_session.py:92某个 worker 持有运行锁
idle_session.py:93没在跑，也没有挂起工具调用
awaiting_permission_session.py:94没在跑，但上下文尾部有工具调用在等用户确认
awaiting_external_result_session.py:95没在跑，但外部执行工具在等结果

优先级：先看运行锁，只有没被任何 worker 持有时，才根据持久化上下文尾部判断挂起类型。 前端只需要渲染一个状态指示器，不用自己组合多个布尔值。 

GET /sessions/session-xxx/status?agent_id=agent-xxx

→ {
  "session_id": "session-xxx",
  "status": "awaiting_permission"
}

中断与续接

POST /sessions/{id}/interrupt _session.py:426 中断正在运行或 HITL 暂停的 run。返回 202，实际取消是异步的： 

POST /sessions/session-xxx/interrupt?agent_id=agent-xxx
X-User-ID: alice

→ 202 {"session_id": "session-xxx"}

中断后，会话会回到可以接受下一次输入的状态。续接有两条路：

  • HITL：POST /chat，input 传 UserConfirmResultEvent / ExternalExecutionResultEvent
  • 普通继续：input: null，从当前状态继续
202 不代表已经停

中断要先广播取消、等运行锁释放。刚返回 202 时再查 /status，可能仍显示 running。前端轮询到 idle / awaiting_* 再允许下一次发送。

AG-UI 协议适配

原生流输出的是 AgentScope 的 AgentEvent。如果前端用的是 AG-UI 协议，装一个协议中间件即可： 

from fastapi.middleware import Middleware
from agentscope.app import create_app
from agentscope.app.middleware import AGUIProtocolMiddleware

app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
    extra_middlewares=[
        Middleware(AGUIProtocolMiddleware),
    ],
)

ProtocolMiddlewareBase _base.py:17 拦截会话流端点的 StreamingResponse，把每帧反序列化回 AgentEvent，调用 _convert_to_protocol() 转成目标格式再重新序列化。

AGUIProtocolMiddleware _agui.py:44 内置了到 AG-UI 事件的映射。要接别的协议，继承 ProtocolMiddlewareBase 并实现一个转换方法即可。

装了协议中间件，帧格式就变了

前端必须按目标协议解析，不能再用原生 type 字段。 两条流不要混用同一个客户端。

前端契约：五条硬规则

  1. 按 reply_id 隔离：一条会话流里可能混着多次 run， 甚至团队成员的回复。别把所有 delta 拼到一个字符串。
  2. 按 block_id / tool_call_id 定位块： TEXT_BLOCK_START 建块，DELTA 累加， END 收尾。找不到块就跳过，别抛错。
  3. 忽略心跳与未知类型：: 开头的帧不是数据； 新事件类型要能静默跳过。
  4. 去重：重连时回放与实时可能重叠，按事件 id 或 _entry_id 去重。
  5. 状态驱动 UI：用 /status 的四个值决定 「正在输入」「等待确认」「可发送」，不要靠猜。

这些规则和 03 章的 Msg.append_event() 是同一套语义。 服务端持久化用的也是它，所以前端 reducer 与后端重建结果应当一致。

陷阱与窍门

把 after 当成消息 ID

after 是事件回放游标，来自消息接口的 event_cursor。 传消息 ID 可能从错误的位置开始回放。

用 offset 翻页

offset 已废弃且永远被忽略。用 before + has_more 做游标分页。

重连后文本重复

回放和实时流会重叠。按事件 id 去重；如果只按文本拼接， 重连后会出现整段重复。

反代缓冲 SSE

服务端已经带 X-Accel-Buffering: no，但 nginx 仍需 proxy_buffering off，否则用户看到的是「一次性全部出现」。

中断后立刻再发

202 只表示「已请求取消」。运行锁还没释放时再发会 409。 等 /status 变成非 running。

先建 SSE，再发 POST /chat

这样不会漏掉第一帧。即使顺序反了，回放日志也能补上，但前端逻辑会简单很多。

用 is_running 做发送按钮

消息接口同时返回 is_running，比额外查一次 /status 更省往返。

  1. 用 curl -N 订阅会话流，再另开终端发 POST /chat，观察帧顺序。
  2. 把连接断开，记录最后的 event_cursor，带 after 重连，确认没有丢帧。
  3. 用 before 翻两页消息，确认 has_more 与 event_cursor 的行为。
  4. 触发一个需要确认的工具，查 /status 是否为 awaiting_permission，再发确认。
