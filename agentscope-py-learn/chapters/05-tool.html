05 · 工具系统

02 章用 FunctionTool 包装过一个函数，但只够跑通 demo。这一章把它展开： 函数工具与类工具的边界、schema 到底怎么生成、 Toolkit 的工具组与并发、错误怎么变成模型能读懂的结果， 以及怎么把外部 MCP 服务接进来。

读完你能做到

  • 判断一个能力该用 FunctionTool 还是继承 ToolBase
  • 写出带 Pydantic schema、权限决策与流式结果的工具
  • 用 ToolGroup 管理「按需激活」的工具，并解释哪些调用会并发
  • 接入一个 stdio / HTTP MCP 服务，知道工具名为什么变成 mcp__xxx__yyy

先说为什么：工具是「给模型的手」，不是普通函数

普通函数只对调用者负责；工具要同时面对三个读者：模型看 schema 决定调不调、 框架负责权限与并发、你的代码负责真正执行。 三者任何一个没对齐，表现都是「模型不调用」或「调用了但结果不对」。

tool schema（给模型看）
名字、描述、参数 JSON Schema。模型只能依据这些决定是否调用、怎么填参数。
permission（给框架看）
只读？可并发？要不要问用户？权限引擎在真正执行前做决策。
call（给你看）
拿到关键字参数，返回一个 ToolChunk 或一串 chunk。

ToolBase _base.py:100 就是这三件事的协议。所有工具——包括内置的 Bash、文件工具、MCP 工具——都实现它。

FunctionTool：把函数交给模型

FunctionTool _adapters.py:39 是最轻的适配器：给一个函数，它负责生成 schema、调用函数、把返回值规整成 ToolChunk。适合「逻辑很短、没有复杂状态」的工具。 

from agentscope.message import TextBlock
from agentscope.tool import FunctionTool, ToolChunk


async def count_up(n: int):
    """从 1 数到 n，每数一个就产出一块。

    Args:
        n: 上限，1 到 10。
    """
    for i in range(1, n + 1):
        yield ToolChunk(content=[TextBlock(text=f"{i}\n")])


tool = FunctionTool(count_up, is_read_only=True)

它支持的返回形态有四种 _adapters.py:140：

返回 行为
ToolChunk 一次性结果
AsyncGenerator[ToolChunk] 流式结果，框架逐个转发
Generator[ToolChunk] 同步生成器，框架转成异步流
其他普通返回值（str / dict / list 等） 自动包装成 ToolChunk；只有自定义 ToolBase.call() 返回不支持的类型才会抛 DeveloperOrientedException

两个构造参数决定权限行为

is_concurrency_safe 默认 True，is_read_only 默认 False _adapters.py:63。 后者很关键：FunctionTool 默认返回 ASK _adapters.py:134， 不处理就会停住等用户确认（02 章踩过这个坑）。

三种放行方式，按推荐顺序：

  1. 确实是只读：FunctionTool(fn, is_read_only=True)
  2. 不是只读但可信任：FunctionTool(fn, permission=PermissionDecision(behavior=PermissionBehavior.ALLOW, ...))_adapters.py:67
  3. 交给权限系统：保持 ASK，在 08 章用规则 / 模式处理

ToolBase：什么时候必须自己写类

下面这些需求，FunctionTool 就力不从心了，应该继承 ToolBase：

  • 需要根据输入做细粒度权限判断（比如只允许读某个目录）
  • 需要流式输出并控制每一块的内容
  • 需要在工具内部访问 AgentState（is_state_injected=True）
  • 需要自定义 is_read_only / is_concurrency_safe 的动态判定
from agentscope.message import TextBlock
from agentscope.permission import (
    PermissionBehavior,
    PermissionContext,
    PermissionDecision,
)
from agentscope.tool import ParamsBase, ToolBase, ToolChunk


class SearchParams(ParamsBase):
    query: str


class FakeSearch(ToolBase):
    name = "FakeSearch"
    description = "Search an internal index and return the top result."
    input_schema = SearchParams.model_json_schema()
    is_concurrency_safe = True
    is_read_only = True

    async def check_permissions(
        self,
        tool_input: dict,
        context: PermissionContext,
    ) -> PermissionDecision:
        return PermissionDecision(
            behavior=PermissionBehavior.ALLOW,
            message="Read-only internal search.",
        )

    async def call(self, query: str) -> ToolChunk:
        results = [f"{query}: result 1", f"{query}: result 2"]
        return ToolChunk(content=[TextBlock(text="\n".join(results))])

ParamsBase _base.py:29 只是帮你把 JSON Schema 里的 title 去掉，让模型看到的 schema 更干净； 不强制使用，手写 dict 也可以。

必须实现的方法

成员 是否必须 说明
name / description / input_schema 是 模型看到的三件套
check_permissions()_base.py:266 是（抽象方法） 返回 PermissionDecision
call()_base.py:159 是（外部工具除外） 真正执行，返回 chunk
check_read_only()_base.py:298 否 默认返回静态 is_read_only
match_rule()_base.py:322 否 自定义权限规则匹配
generate_suggestions()_base.py:355 否 给用户生成「以后都允许」的规则
不要覆写 __call__

ToolBase.__call__ _base.py:190 负责中间件洋葱链，真正的执行入口是 call()。覆写 __call__ 会绕过所有中间件。另外它只接受关键字参数，传位置参数会直接抛 TypeError _base.py:210。

schema 从哪来：注解、docstring 与 Pydantic

FunctionTool 的 schema 生成分两步：

  1. 从 func.__name__ 取工具名；从 docstring 的短描述 + 长描述取说明
  2. 用 inspect.signature + 类型注解构造一个临时 Pydantic 模型，再把模型导出成 JSON Schema _utils.py:190

docstring 里的 Args: 会变成每个参数的 description _utils.py:211。 没有类型注解的参数会退化成 Any，schema 里就没有类型约束。

三种表达约束的方式

from typing import Annotated, Literal
from pydantic import Field


def search(
    query: str,
    mode: Literal["fast", "deep"] = "fast",
    limit: Annotated[int, Field(ge=1, le=20)] = 5,
) -> str:
    """搜索内部索引。

    Args:
        query: 搜索词。
        mode: fast 只搜标题，deep 搜全文。
        limit: 最多返回几条。
    """
    return "..."
约束 写法
枚举 Literal["fast", "deep"]
数值范围 Annotated[int, Field(ge=1, le=20)]
复杂嵌套 直接传 Pydantic 模型的 input_schema
schema 不是越详细越好

参数描述应该回答「什么时候填、填什么算合法」，而不是重复参数名。 limit: 最多返回几条 比 limit: 数量 有用得多。

Toolkit：工具组、注册与调用

Toolkit _toolkit.py:66 是 Agent 访问工具的唯一入口。它的构造参数有四类 _toolkit.py:88： 

Toolkit(
    tools=[...],                  # 普通工具
    skills_or_loaders=[...],      # 技能目录
    mcps=[...],                   # MCP 客户端
    tool_groups=[...],            # 额外工具组
)

tools、skills_or_loaders、mcps 会被放进名为 basic 的默认组，永远激活。

工具组：按需激活

from agentscope.tool import ToolGroup, Toolkit

toolkit = Toolkit(
    tools=[FakeSearch()],
    tool_groups=[
        ToolGroup(
            name="browser",
            description="浏览器自动化：打开网页、点击、截图。",
            tools=[...],
        ),
    ],
)

非 basic 组必须有 description _tool_group.py:71， 因为模型要靠它判断「什么时候该激活这个组」。只要存在额外组，框架会自动注册元工具 reset_tools（类名 ResetTools） _meta.py:21， 让模型自己开关工具组。

运行时增删

async def manage_tools(toolkit):
    await toolkit.add_tool(MyTool())              # 默认加入 basic
    await toolkit.add_tool(MyTool(), "browser")   # 加入指定组
    await toolkit.remove_tool("MyTool")

同名工具会覆盖旧工具，只记一条 warning _toolkit.py:660。 这在动态换工具时很方便，但也容易悄悄替换掉内置工具。

调用链

Agent 执行工具时最终走的是 Toolkit.call_tool() _toolkit.py:225： 查可用工具 → 解析参数 → 注入状态 → 调用 → 逐块 yield → 最后 yield 一个完整的 ToolResponse。工具自己只负责产出 chunk，聚合由 Toolkit 做。

并发与顺序：哪些工具能一起跑

模型一条回复里可能请求多个工具。Agent 不会无脑并发，而是先按 is_concurrency_safe 分批 _agent.py:2097： 

tool_calls = [A, B, C, D]

A.is_concurrency_safe = True
B.is_concurrency_safe = True
C.is_concurrency_safe = False
D.is_concurrency_safe = True

# 分批结果：
# [A, B] 并发 → [C] 串行 → [D] 并发

注意分批是按连续区间做的，不是把所有安全工具抽出来放一起。 这样可以保留模型给出的调用顺序。

批次 执行方式 失败行为
concurrent 全部同时启动_agent.py:2189 其余任务不取消，结束后汇总成 ExceptionGroup
sequential 一个接一个_agent.py:2137 单个失败会以错误结果继续，不中断整轮

未注册的工具会被当作「并发安全」处理 _agent.py:2114， 因为它最终只会返回一个 ToolNotFoundError，没有副作用。

有副作用的工具必须标 is_concurrency_safe=False

写文件、发消息、改数据库都属于有副作用。两个这样的工具并发跑，结果取决于调度顺序， 很难复现。默认值在 FunctionTool 里是 True， 这是最容易忽略的一处。

错误怎么回给模型：异常、ToolChunk 与状态

工具抛异常不会让整个 Agent 崩掉。Toolkit.call_tool 会把大多数异常转换成一条 state=error 的 ToolChunk，模型会像读普通结果一样读到错误文本， 然后决定重试、换参数或直接回答。

情况 模型看到 是否中断
工具不存在 ToolNotFoundError: The tool named 'x' doesn't exist._toolkit.py:283 否
工具组未激活 ToolGroupInactiveError: ...，提示先调用元工具_toolkit.py:265 否
MCP 调用失败 Error occurred when calling MCP tool: ..._toolkit.py:343 否
普通异常 str(e)，状态 error_toolkit.py:356 否
被取消 「The tool call has been interrupted by the user.」_toolkit.py:374 是（中断本轮）
返回类型不对 DeveloperOrientedException 是（开发错误）

最后一定会 yield 一个完整的 ToolResponse _toolkit.py:390， 它把前面所有 chunk 按 block id 合并；error 永远优先， interrupted 与 denied 之间则是后到的覆盖先到的 _response.py:138。

抛异常也是一种「给模型的提示」

错误文本会被模型读到。写成「文件不存在：/tmp/x，请先调用 Read 确认路径」， 比写 FileNotFoundError 堆栈更有用。但不要把密钥、内网地址拼进错误信息。

另外，模型生成的工具参数是 JSON 字符串，可能不合法。Toolkit 会先尝试修复 _toolkit.py:300， 再按 schema 校验；所以偶发的缺引号、尾逗号不一定直接失败。

MCP：把外部工具接进来

MCP 是「工具的 USB 接口」：外部进程或服务按协议暴露工具，AgentScope 把它们适配成 MCPTool _adapters.py:200， 对模型来说和普通工具没有区别。

两种配置

配置 字段 适用
StdioMCPConfig_config.py:9 command、args、env、cwd 本地子进程，必须 stateful
HttpMCPConfig_config.py:44 url、headers、timeout 远程服务，可 stateful 也可 stateless

接入一个本地文件系统 MCP

import asyncio

from agentscope.mcp import MCPClient, StdioMCPConfig
from agentscope.tool import Toolkit


async def main() -> None:
    client = MCPClient(
        name="filesystem",
        is_stateful=True,
        mcp_config=StdioMCPConfig(
            command="npx",
            args=["-y", "@modelcontextprotocol/server-filesystem", "."],
        ),
    )

    await client.connect()
    try:
        toolkit = Toolkit(mcps=[client])
        # ... 交给 Agent 使用 ...
    finally:
        await client.close()


asyncio.run(main())

接入一个无状态 HTTP MCP

from agentscope.mcp import HttpMCPConfig, MCPClient

client = MCPClient(
    name="weather",
    is_stateful=False,
    mcp_config=HttpMCPConfig(url="https://example.com/mcp"),
    execution_timeout=30,
)

is_stateful=False 时不需要 connect() / close()， 每次调用创建临时连接 _mcp_client.py:32。 stateful 连接则必须显式生命周期管理 _mcp_client.py:337。

工具名为什么变了

MCP 工具会被重命名成 mcp__{服务名}__{工具名}，并把非法字符替换成 x _adapters.py:256。 这是为了避免多个 MCP 服务之间的重名冲突，也为了满足模型厂商对工具名的字符限制。

权限与容错

  • MCP 工具默认 ASK；只有服务声明了 read_only_hint 才自动放行_adapters.py:316
  • MCP 工具禁止状态注入（出于安全）_adapters.py:207
  • 单个 MCP 不可达时只记 warning 并跳过它的工具，不会让整轮回复失败_toolkit.py:526
  • enable_tools / disable_tools 可以白名单或黑名单过滤工具

内置工具：Bash / 文件 / 任务 / AskUser

开箱即用的工具都在 agentscope.tool 里导出。它们的权限行为已经针对场景调过：

工具 能力 只读 权限特点
Bash / PowerShell 执行命令 否（按命令判定） 静态分析危险命令、注入、危险路径
Read 读文件，支持分页与图片/PDF 是 只读自动放行
Write / Edit 写文件 / 精确替换 否 要求先 Read；危险文件返回免疫 ASK
Glob / Grep 按文件名 / 内容搜索 是 只读自动放行
TaskCreate / Get / List / Update 结构化任务清单 — 计划工具默认放行
AskUser 向用户提多选题 — 外部执行工具，不自己执行

Bash 的 check_read_only() 是动态的：ls 算只读， rm 不算 _base.py:305。 这也是「不要只看静态 is_read_only」的原因。

完整的内置工具清单在 __init__.py:9。

陷阱与窍门

工具被调用了两次 / 顺序乱了

检查 is_concurrency_safe。默认值是 True， 有副作用的工具如果没改成 False，会和其他安全工具一起并发执行。

同名工具被悄悄覆盖

add_tool 遇到同名工具会替换旧的并只记 warning _toolkit.py:660。 自定义工具名最好加前缀，别和 Read、Bash 撞。

MCP 工具名带点号，模型厂商拒绝

框架已经把 MCP 工具名清洗成 [a-zA-Z0-9_-] 并加前缀 _adapters.py:255。 如果你在提示词里手写原始工具名，模型会对不上，应该用 list_tools() 返回的名字。

MCP 连接忘了关

stateful 的 MCP 必须 await client.close()。放在 try/finally 里，否则子进程或长连接会一直挂着。

工具描述写「何时用」，不是「是什么」

description 的第一句应该是触发条件：Use when the user asks about weather in a city. 而不是 Weather tool.。 模型选工具主要看这一句。
