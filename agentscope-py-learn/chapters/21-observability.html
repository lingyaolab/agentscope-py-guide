21 · 可观测性

前 20 章把 Agent 从能跑到能上线都讲完了，但上线之后才是真正的问题开始： 这次回复为什么慢？刚才那轮花了多少 token？工具报错在哪一层？ 这一章讲 AgentScope 内建的 OpenTelemetry 追踪，以及怎么把 token 变成成本。

读完你能做到

  • 注册 TracerProvider，把 TracingMiddleware 装到 Agent 上
  • 看懂一次 reply 产生的 span 树，知道每层 span 来自哪个 hook
  • 从 ModelCallEndEvent 或 Msg.usage 里取 token，自己算成本
  • 用 ReplyBudgetControlMiddleware 给单次 reply 设上限
  • 判断哪些内容会进 span，以及采样到底能省什么

先说为什么：日志回答不了「慢在哪」

最原始的观测是 print。它能告诉你「开始了」「结束了」，但回答不了下面这些问题：

线上问题 日志能给什么 追踪能给什么
这轮回复为什么 40 秒？ 开始和结束时间 每次模型调用、每次工具调用各占多少毫秒
第 3 轮工具为什么失败？ 一行报错文本 失败 span 的入参、结果、异常与父级 reply
这一轮花了多少 token？ 要自己拼日志 每个 chat span 带 input / output / cache token
同一个用户的多轮会话怎么串起来？ 靠自己加 request id 所有 span 共享 conversation id（session id）

AgentScope 的答案不是自造一套日志格式，而是接 OpenTelemetry 和 GenAI 语义约定：你的采集、存储、看板都可以复用现有基础设施。

三层：事件、Span、指标

AgentScope 内部其实有三类可观测信号，别混用：

层 产生者 适合回答 生命周期
事件流（AgentEvent） Agent 的 reply 过程 前端实时渲染、增量文本、工具进度 随流消费，不自动持久化
Span TracingMiddleware 延迟拆解、调用链、错误定位、token 归属 由 OTel SDK 批量导出
指标 / 日志 你的应用或 OTel Collector QPS、P95、错误率、告警 取决于你的后端

事件流是给用户看的，Span 是给运维看的。 两者都从同一轮 reply 里产生，但不要拿事件流当追踪存起来。

注册 TracerProvider

OpenTelemetry 相关包已经是 AgentScope 的必装依赖，不需要额外 extras： opentelemetry-api pyproject.toml:36、 opentelemetry-sdk pyproject.toml:37、 opentelemetry-exporter-otlp pyproject.toml:38。 

from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter

provider = TracerProvider()
provider.add_span_processor(
    BatchSpanProcessor(
        OTLPSpanExporter(endpoint="http://localhost:4318/v1/traces"),
    ),
)
trace.set_tracer_provider(provider)
  • 必须在创建 Agent 之前注册，set_tracer_provider 只有第一次生效
  • 4318 是 OTLP/HTTP，4317 是 OTLP/gRPC，端口和协议别配错
  • 本地调试可以换成 SimpleSpanProcessor(ConsoleSpanExporter())，直接打印到终端
  • 生产环境用 BatchSpanProcessor，避免每次调用都同步发网络请求
AgentScope 只负责产生 span

导出到 Jaeger、Tempo、Langfuse、云厂商 APM 都由 OTel 生态决定。 AgentScope 不绑定任何后端。

装上 TracingMiddleware

TracingMiddleware _trace.py:117 只有三个 hook： on_reply _trace.py:137、 on_model_call _trace.py:259、 on_acting _trace.py:312， 正好对应 Agent、模型、工具三层。 

from agentscope.agent import Agent
from agentscope.middleware import TracingMiddleware

agent = Agent(
    name="assistant",
    system_prompt="You are a helpful assistant.",
    model=model,
    toolkit=toolkit,
    middlewares=[TracingMiddleware()],
)

tracer 的名字固定为 agentscope，版本取当前包版本 _setup.py:11， 所以在后端按 service.name / instrumentation scope 过滤时很好找。

如果没注册真正的 SDK provider，每个 hook 会直接短路到 next_handler _trace.py:59， 不建 span、不算属性，几乎零开销。这个判断每次 hook 都会做一次。

放在中间件列表第一位

洋葱式中间件里，列表第一个在最外层。把 TracingMiddleware 放最前， reply span 才能包住后面的所有中间件与 ReAct 轮次。

Span 树：一次 reply 长什么样

一次 reply 会产出下面这棵树（工具调用几轮就有几个 chat / execute_tool 兄弟节点）： 

invoke_agent assistant                <- on_reply
├── chat qwen-plus                    <- on_model_call，第 1 轮
├── execute_tool search               <- on_acting，工具 1
├── execute_tool read_file            <- on_acting，工具 2
├── chat qwen-plus                    <- 第 2 轮
└── execute_tool write_file           <- 工具 3

三类 span 的名字格式在源码里写死：

Span 名 来源 说明
invoke_agent {name} on_reply 整个 reply，包含所有 ReAct 轮次
chat {model} on_model_call 一次底层模型 API 调用
execute_tool {tool} on_acting 一次工具执行

所有 span 都带 gen_ai.conversation.id，值就是 session id；没有 session 时写 [no_session_id] _extractor.py:52。 这就是把同一用户多轮串起来的依据。

注意：invoke_agent span 不汇总 token。 要算一轮或一个会话的总量，得自己把 chat span 加起来，或者监听 ModelCallEndEvent。

三类 Span 各记什么

AgentScope 用的是 OpenTelemetry 的 GenAI 语义约定 _attributes.py:8， 外加几个 agentscope.* 扩展属性。

Agent reply span

  • operation name、Agent 名称、Agent 类文档字符串
  • 输入消息（完整内容）、最终输出消息
  • agentscope.agent.reply_id：HITL / 外部执行恢复时用它对上两次调用
  • agentscope.agent.hitl_pending_tools：等待人工确认的工具名 JSON 列表
  • agentscope.agent.external_execution_pending_tools：等待外部执行的工具名列表
  • agentscope.agent.incoming_event_type：恢复时是确认结果还是外部执行结果

请求属性来自 _extractor.py:459， 输出消息来自 _extractor.py:527， reply_id / HITL / 外部执行属性在 _trace.py:231 写入；键名常量在 _attributes.py:8 的 SpanAttributes 里。

Model call span

  • provider、模型名、temperature / top_p / top_k / max_tokens / penalty / stop / seed
  • 工具定义（转成 OTel 的扁平格式）与完整输入消息
  • 响应 id、finish reason、输入 / 输出 token、缓存 token
  • 完整输出消息

请求属性在 _extractor.py:171， 响应属性在 _extractor.py:338。 缓存 token 只有非零才写入，键名是 agentscope.usage.cache_input_tokens _attributes.py:107。

Tool execution span

  • 工具名、调用 id、入参 JSON
  • 工具描述（如果能在 Toolkit 里查到）
  • 工具结果（序列化成字符串）

请求属性在 _extractor.py:548。 工具抛异常时，span 会被标成 ERROR 并记录异常。

流式、HITL 与外部执行

流式响应有个麻烦：调用开始时还不知道 token 和输出内容。 on_model_call 因此不直接结束 span，而是用 end_on_exit=False _trace.py:293 把结束权交给一个包装器，等最后一个 chunk 到了再写响应属性。 

with tracer.start_as_current_span(..., end_on_exit=False) as span:
    result = await next_handler(**input_kwargs)
    if isinstance(result, AsyncGenerator):
        return _trace_async_generator_wrapper(result, span)  # 收尾时写属性
    span.set_attributes(_get_llm_response_attributes(result))
    _set_span_success_status(span)

流被正常消费完，包装器从最后一个 chunk 里取 usage 和内容；中途抛错，则把 span 标成 ERROR 并记录异常。

HITL：两次调用，一个 reply

人工确认会把一次 reply 拆成两次 agent(...) 调用。追踪里会看到两个 invoke_agent span，它们共享同一个 agentscope.agent.reply_id； 第一个带 hitl_pending_tools，第二个带 incoming_event_type=user_confirm_result。按 reply id 分组就能还原完整链路。

外部执行：补偿 span

工具在 Agent 进程外执行时，on_acting 根本看不到它。Agent 收到 ExternalExecutionResultEvent 后，on_reply 会为每条结果补一个 execute_tool span _trace.py:173， 并标记 agentscope.agent.is_external_execution=true。

补偿 span 的时间戳不是真实执行时间

它记录的是结果收到的时刻，不是工具在外部系统真正运行的时刻。 想看真实耗时，得让外部系统自己上报。

在 Agent Service 里接追踪

create_app 不会自动安装 TracingMiddleware。要用 extra_agent_middlewares _app.py:129 传入一个工厂： 

from agentscope.app import create_app
from agentscope.middleware import TracingMiddleware


async def extra_middlewares(user_id, agent_id, session_id, workspace):
    return [TracingMiddleware()]


app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
    extra_agent_middlewares=extra_middlewares,
)

工厂在每个聊天回合被调用，参数是 (user_id, agent_id, session_id)，如果签名接受第四个参数还会多传 workspace _chat.py:1015。 返回的中间件会追加到框架自带的 InboxMiddleware / StateChangeMiddleware / ToolOffloadMiddleware 之后 _chat.py:1010。

参数 作用域 典型用途
extra_middlewares FastAPI / ASGI HTTP 层追踪、请求日志、CORS
extra_agent_middlewares 每个聊天回合的 Agent TracingMiddleware、成本统计、审计

两者名字很像，作用层完全不同：前者包 HTTP 请求，后者包 Agent 的 reply。

追踪是进程级配置，中间件是会话级装配

TracerProvider 在进程启动时注册一次；工厂每回合返回一个新的 TracingMiddleware 也无所谓——它本身无状态，真正的开销在 span。

自定义 Span

业务代码想在同一棵树上加节点，直接用同一个 tracer 名： 

from opentelemetry import trace

from agentscope import __version__

tracer = trace.get_tracer("agentscope", __version__)


async def enrich_profile(profile_id: str) -> dict:
    with tracer.start_as_current_span(
        name="enrich_profile",
        attributes={"profile.id": profile_id},
    ) as span:
        profile = await fetch_profile(profile_id)
        span.set_attribute("profile.fields", len(profile))
        return profile

在工具函数、模型调用回调或 Agent 生命周期内调用时，当前 span 上下文已经挂好， 自定义 span 会自动挂到对应的 invoke_agent / execute_tool 下面。

异步生成器里别长期持有 context

TracingMiddleware 只在推进生成器的瞬间 attach context，yield 期间不持有。 你自己写中间件时也要遵守这个边界，否则跨任务关闭生成器会触发 OTel detach 错误。

Token 从哪来

token 不是 AgentScope 估的，来自模型供应商返回的 usage。数据形状有三处：

位置 内容 用途
ChatUsage_model_usage.py:10 input / output / time / cache / metadata 模型层最完整的用法记录
ModelCallEndEvent_event.py:138 input / output / cache token、finish reason 中间件与 UI 实时统计
Msg.usage_base.py:96 写入上下文的 Usage 回看某条助手消息花了多少

每个模型调用结束都会发出一个 ModelCallEndEvent _agent.py:1801， 字段就是 provider 返回的 usage _event.py:145。 如果 provider 没返回 usage，这里会写 0，而不是估算。

上下文里保存的助手消息则通过 _save_to_context _agent.py:3440 把 ChatUsage 转成 Usage 持久化 _base.py:57。 注意 Usage 没有 time 字段，耗时只活在 ChatUsage 与 span 里。

另外还有 model.count_tokens(messages, tools) _base.py:379， 但它默认按「UTF-8 字节数 / 4」估算文本，另加每个 DataBlock 2000 token， 并把工具 schema 的 JSON 也计入；只用于上下文压缩判断，不能当账单。

CLI / TUI 里看到的那行 tokens: 1234 in / 567 out 就是控制台渲染器读 ModelCallEndEvent 打的 _renderer.py:368。

成本：没有内置价目表

AgentScope 只记录 token，不记录钱。价格随供应商、模型、缓存命中、 批量折扣变化，框架不维护这张表。要算成本，自己乘： 

from collections import defaultdict

from agentscope.event import (
    ModelCallEndEvent,
    ModelCallStartEvent,
    ReplyEndEvent,
)
from agentscope.middleware import MiddlewareBase

# 示例价格：美元 / 百万 token，务必换成你账单页上的数字
PRICES = {
    "qwen-plus": {"input": 0.4, "output": 1.2},
}


class CostMiddleware(MiddlewareBase):
    def __init__(self) -> None:
        self._cost: dict[str, float] = defaultdict(float)
        self._model: dict[str, str] = {}

    async def on_reply(self, agent, input_kwargs, next_handler):
        async for event in next_handler(**input_kwargs):
            if isinstance(event, ModelCallStartEvent):
                self._model[event.reply_id] = event.model_name
            elif isinstance(event, ModelCallEndEvent):
                price = PRICES.get(self._model.get(event.reply_id, ""))
                if price is not None:
                    self._cost[event.reply_id] += (
                        event.input_tokens * price["input"]
                        + event.output_tokens * price["output"]
                    ) / 1_000_000
            elif isinstance(event, ReplyEndEvent):
                cost = self._cost.pop(event.reply_id, 0.0)
                self._model.pop(event.reply_id, None)
                print(f"[cost] {event.reply_id}: ${cost:.6f}")
            yield event
别用 agent.model.model 配价

模型路由中间件会在一次 reply 内替换 agent.model。用 ModelCallStartEvent.model_name 记录本次实际调用的模型， 才能对上正确单价。

三个容易算错的地方：

  • 缓存 token 单价不同：cache_input_tokens 通常打折， cache_creation_input_tokens 通常加价，别一股脑按 input 价算
  • 钱要用 Decimal：示例用 float 是为了短；真实计费别让浮点误差累积
  • 会话级汇总要自己映射：ModelCallEndEvent 只有 reply_id， 想按用户 / 会话出报表，需要把 reply 映射回 session

预算兜底：单次 reply 的上限

成本看得见还不够，还要能刹车。ReplyBudgetControlMiddleware _budget.py:29 给单次 reply 设一个加权 token 预算： 

cost = input_token_weight * input_tokens
     + output_token_weight * output_tokens

累计成本达到上限后，它会做两件事：

  1. 往上下文最后一条本 Agent 的助手消息追加一个 HintBlock；如果没有，就新建一条 AssistantMsg
  2. 把下一步 tool_choice 强制设成 none，禁止继续调工具

如果还有结构化输出没交，则只允许调用结构化输出那个工具，而不是全禁。 

from agentscope.agent import Agent
from agentscope.middleware import ReplyBudgetControlMiddleware

agent = Agent(
    name="assistant",
    system_prompt="You are a helpful assistant.",
    model=model,
    toolkit=toolkit,
    middlewares=[
        ReplyBudgetControlMiddleware(
            token_budget=10_000,
            input_token_weight=1.0,
            output_token_weight=2.0,
        ),
    ],
)
  • token_budget 必填，按加权成本计算
  • output_token_weight 通常设得比 input 高，因为输出更贵
  • 累计发生在 on_reply _budget.py:107， 拦截发生在 on_reasoning _budget.py:151
  • 状态存在 agent.state.middle_context，所以同一个中间件实例可以给多个 Agent 共用
文档说「reply 结束清理」，源码是「下一次 reply 开始时清理」

on_reply 在收到新的 ReplyStartEvent 时直接用新字典覆盖旧状态 _budget.py:135， 并不会在 ReplyEndEvent 清理。源码注释解释了原因：外层中间件可能吞掉结束事件， 同一 reply 还要继续花钱。HITL 恢复因此不会把预算清零。

预算是 per reply，不是 per session。用户连续发十轮，每轮都重新计数。 要做会话级总额，得自己在中间件里跨 reply 累计。

隐私与体积：span 里有什么

AgentScope 的追踪默认非常详细，它记录的是内容，不只是元数据：

内容 是否进 span 风险
用户输入、系统提示、上下文消息 是，JSON 字符串 PII、内部提示词泄露
模型完整输出 是 可能含敏感业务数据
工具入参与结果 是 可能含密钥、数据库内容
图片 / 音频 base64 是，DataBlock 转成 blob part 体积巨大，且是原始内容
凭证 key 否 不在消息里，除非你的提示或工具参数自己带了

图片和音频的转换在 _converter.py:30， Base64Source 会把 data 原样写进 gen_ai.input.messages _converter.py:55。 一次带图的请求，span 可能比请求本身还大。

AgentScope 没有内建的脱敏 / 截断开关。可选做法：

  • 在 OTel Collector 或自定义 SpanProcessor 里删除敏感属性
  • 给高敏租户不装 TracingMiddleware，只保留指标
  • 用采样降低导出量（但采样不能替代脱敏，见下节）
  • 把 span 存到符合数据合规要求的后端

开销与采样

开销分两段，别混为一谈：

阶段 没注册 provider 注册了 provider
hook 调用 一次 isinstance 判断后短路 正常进入
属性序列化 不执行 总是执行，在创建 span 之前
span 创建 / 导出 无 由 SDK 采样与批处理决定

on_reply 先算 request_attributes 再 start_span _trace.py:152； on_model_call 同理 _trace.py:281。 所以采样只能减少「导出与存储」，省不掉消息 JSON 的序列化。

生产建议：

  • 用 BatchSpanProcessor，别用同步导出
  • 高 QPS 场景配 ParentBased(TraceIdRatioBased(0.1)) 之类的采样器
  • 长会话注意 span 属性里的完整上下文，必要时在 Collector 侧截断
  • 把追踪初始化放在进程入口，避免每次创建 Agent 都重复设置 provider

陷阱与窍门

装了中间件却没注册 provider

所有 hook 静默短路，不报错也不出 span。先确认 trace.get_tracer_provider() 是真正的 SDK provider。

在 Agent Service 里找不到追踪

create_app 不会自动装 TracingMiddleware。 要用 extra_agent_middlewares 工厂返回它。

指望 reply span 直接给总 token

invoke_agent 只记输入输出消息，不汇总 token。 总量要在 chat span 或 ModelCallEndEvent 上算。

以为采样能省掉序列化

请求属性在 span 创建前就已序列化。采样减少的是导出量与存储，不是 CPU。

把 base64 图片塞进 span

DataBlock 会原样进属性。多模态场景务必在 Collector 侧裁剪， 否则存储和带宽都会被拖垮。

用估算 token 算钱

count_tokens 是「字节 / 4」的近似值，只服务上下文压缩。 计费必须用 provider 返回的 usage。

预算中间件无状态，可以共享

运行时状态在 agent.state.middle_context，不在中间件实例上。 一个实例挂到多个 Agent 是安全的，但预算仍然是每 Agent、每 reply 独立。

自检三问

  1. 一次 reply 的 span 树有哪几层？token 记在哪一层？
  2. 采样率调到 10%，请求消息的 JSON 序列化会减少 90% 吗？为什么？
  3. ReplyBudgetControlMiddleware 的预算作用域是什么？HITL 恢复后会不会清零？

20 分钟动手练习

  1. 用 ConsoleSpanExporter 跑一轮带工具的 reply，数一数 span 树有几个节点。
  2. 写一个中间件，在 ReplyEndEvent 时打印本轮 input / output token 总和。
  3. 给 CostMiddleware 加上缓存 token 的单独单价，并换成 Decimal。
  4. 把 ReplyBudgetControlMiddleware 的预算调到很小，观察它如何阻止下一轮工具调用。
  5. 检查一个带图片的消息，看看 span 属性有多大，再决定要不要在 Collector 侧裁剪。
