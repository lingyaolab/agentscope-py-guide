11 · RAG 与长期记忆

06 章的上下文管理解决「这一轮装不下」。这一章解决两个不同的问题： RAG 让模型在回答前查到外部文档，长期记忆让它跨会话记住用户偏好与历史决策。 两者都通过中间件接入，但存储、触发时机和隔离维度完全不同。

读完你能做到

  • 说清 RAG 的五个可替换模块，以及 KnowledgeBase 绑定了什么
  • 完成一次「解析 → 切分 → 嵌入入库 → 检索」的闭环
  • 选择 RAGMiddleware 的 static / agentic 模式，并知道工具要手动注册
  • 区分 Agentic Memory、ReMe、Mem0 三种长期记忆的存储与写入方式

先说为什么：RAG 不是「把文档塞进提示词」

把整份文档放进系统提示有三个问题：贵（每次都付全量 token）、慢、而且模型会在一大段文本里迷失。 RAG 的做法是先检索、再注入：只把和当前问题最相关的几个片段放进上下文。

离线：索引
文件 → 解析成 Section → 切成 Chunk → 嵌入成向量 → 写进向量库。慢，但只做一次。
在线：检索
查询 → 嵌入 → 向量检索 → 去重排序 → 取 top_k。每次提问都做。
接入：中间件
检索结果包成 HintBlock 注入，或暴露成工具让模型自己调。

长期记忆是另一条线：它不是「文档」，而是从对话里沉淀下来的事实—— 用户住哪儿、偏好什么、上次做了什么决定。它的写入发生在回复之后，检索发生在回复之前或模型主动调用时。

五个可替换模块：Parser / Chunker / Embedding / Store / KnowledgeBase

模块 职责 内置实现
Parser 原始文件 → Section，按自然边界切（PDF 页、PPT 幻灯片、Markdown 段） TextParser、PDFParser、PPTParser、WordParser、ExcelParser、ImageParser
Chunker Section → Chunk，不跨 Section 合并 ApproxTokenChunker
Embedding Chunk → 向量 DashScopeEmbeddingModel 等
Vector Store 存向量与元信息，支持检索 QdrantStore、MilvusLiteStore、MongoDBStore、ElasticsearchStore
KnowledgeBase 把嵌入模型 + 向量库 + collection 绑在一起 KnowledgeBase

Section _document.py:31 和 Chunk _document.py:71 都是 Pydantic 模型。Chunk 比 Section 多两个字段： chunk_index 和 total_chunks，用于后续去重与展示。

KnowledgeBase _knowledge.py:44 的构造函数 _knowledge.py:74 只有六个参数：name、description、embedding_model、 vector_store、collection、metadata_filter。

KnowledgeBase 不管理向量库连接

vector_store 必须已经进入 async with 上下文。KnowledgeBase 只负责 「用这个库、这个 collection」，不负责打开或关闭连接。

索引三步：解析 → 切分 → 入库

from agentscope.credential import DashScopeCredential
from agentscope.embedding import DashScopeEmbeddingModel
from agentscope.rag import ApproxTokenChunker, KnowledgeBase, TextParser


async def index_docs(store) -> str:
    parser = TextParser()
    sections = await parser.parse(
        file=b"# Cats\nCats sleep 12-16 hours per day.\n",
        filename="cats.md",
    )

    chunker = ApproxTokenChunker(
        parameters=ApproxTokenChunker.Parameters(
            chunk_size=256,
            overlap=32,
        ),
    )
    chunks = await chunker.chunk(sections)

    embedding_model = DashScopeEmbeddingModel(
        credential=DashScopeCredential(api_key="YOUR_API_KEY"),
        model="text-embedding-v4",
        dimensions=1024,
    )

    kb = KnowledgeBase(
        name="demo-kb",
        description="A toy corpus about cats.",
        embedding_model=embedding_model,
        vector_store=store,          # 必须已经在 async with 里
        collection="demo-kb",
    )

    return await kb.insert_document(
        chunks,
        document_metadata={"filename": "cats.md"},
    )

同一文档的所有 chunk 共享一个 document_id，后续可以按文档整体删除。 collection 会在第一次操作时按 embedding_model.dimensions 懒创建。

parse(file, filename) 的 file 既可以是 bytes， 也可以是路径字符串。二进制解析器把字符串当路径；TextParser 会先判断这个字符串 是不是存在的文件。

嵌入模型：维度与多模态

EmbeddingModelBase _embedding_base.py:34 有两个关键属性：

属性 作用
dimensions_embedding_base.py:78 向量维度；必须和向量库 collection 的维度一致
supports_multimodal_embedding_base.py:98 能否直接嵌入图片 / 音频等 DataBlock

索引和检索必须用同一个嵌入模型。换了模型就要重新入库，否则向量不可比。 如果模型不支持多模态，KnowledgeBase.search 会静默丢弃 DataBlock 查询，不会报错。

检索：top_k、阈值与去重

async def ask(kb) -> None:
    results = await kb.search(
        queries=["When do cats sleep?"],
        top_k=3,
        score_threshold=None,
    )
    for r in results:
        print(r.score, r.document_id, r.chunk.content)

search _knowledge.py:197 内部做了四件事：

  1. 过滤不可用查询（嵌入模型不支持多模态时丢掉 DataBlock）
  2. 所有查询批量嵌入，再并发检索
  3. 按 (document_id, chunk_index) 去重，保留最高分
  4. 按分数降序排序，截断到 top_k
分数统一为「越大越相关」

使用 L2 距离的向量库会在返回前取负，所以这类知识库的分数是负数， score_threshold 也要填负数。不同嵌入模型 / 不同度量的分数不可比。

KnowledgeBase 还提供文档级管理： insert_document _knowledge.py:286、 delete_document、list_documents、list_chunks。

RAGMiddleware：static 与 agentic

RAGMiddleware _rag.py:626 不拥有嵌入模型或向量库，它消费的是一组已经构造好的 KnowledgeBase。 参数在嵌套的 Parameters _rag.py:648 里：

字段 默认 说明
mode_rag.py:662 "agentic" "static" 或 "agentic"
top_k_rag.py:671 5 跨所有知识库与查询去重后截断
score_threshold_rag.py:682 None 命中分数下限
rerank_candidate_k_rag.py:691 2 × top_k 交给重排模型的候选数，上限 50
emit_hint_event_rag.py:704 True static 模式是否发 HintBlockEvent
persist_hint_rag.py:713 False static 注入是否留在上下文；默认推理后移除

static：每轮自动检索

每次 reply 的首次推理前，把输入消息当查询去检索，结果包成 HintBlock 注入。 默认推理后移除，避免污染下一轮。 

from agentscope.middleware import RAGMiddleware


def build_static(kb):
    mw = RAGMiddleware(
        knowledge_bases=[kb],
        parameters=RAGMiddleware.Parameters(
            mode="static",
            top_k=3,
        ),
    )
    return mw

agentic：把检索做成工具

中间件暴露一个 search_knowledge 工具 _rag.py:131， 由模型自己决定何时检索、用什么 query。 工具不会自动进 Toolkit，必须手动注册： 

from agentscope.tool import Toolkit


async def build_agentic(kb):
    mw = RAGMiddleware(
        knowledge_bases=[kb],
        parameters=RAGMiddleware.Parameters(mode="agentic", top_k=3),
    )
    toolkit = Toolkit(tools=await mw.list_tools())
    return mw, toolkit

两种模式可以叠加：static 给首轮一个背景，agentic 让模型在需要时补检索。 叠加时仍然只需要把 agentic 那份的 search_knowledge 注册进 Toolkit。

工具的说明里会自动列出所有知识库的 name / description， 模型也可以通过 knowledge_bases=[...] 参数把搜索限定到子集。

重排：多一次模型调用

向量检索按嵌入相似度排序，但「语义最像」不等于「最有用」。给 RAGMiddleware 传 rerank_model（一个普通 ChatModelBase），它会先取 rerank_candidate_k 条候选，再让模型读完挑出最终 top_k 条。 

mw = RAGMiddleware(
    knowledge_bases=[kb],
    rerank_model=rerank_chat_model,
    parameters=RAGMiddleware.Parameters(
        mode="agentic",
        top_k=3,
        rerank_candidate_k=10,
    ),
)
  • rerank_candidate_k 必须不小于 top_k，默认 2 × top_k，上限 50
  • 重排失败时记一条 warning，回退到向量检索顺序，不中断本次检索
  • 重排模型读不了的模态会被排到最后或剔除
  • 每个检索都多一次模型调用，延迟和成本都会上去

长期记忆：三种中间件

长期记忆都实现为 MiddlewareBase 子类，挂到 Agent(middlewares=[...]) 上， 但写回与检索时机不同： Agentic Memory 由模型通过 Read / Write / Edit 自主决定保存什么； Mem0 只有在 static_control / both 模式下才自动写回， agent_control 不自动检索或写回；ReMe 会在回复后自动写回并在后续检索。 具体行为以各自的 Parameters 为准。

Agentic Memory：Markdown 文件

AgenticMemoryMiddleware _middleware.py:359 把记忆写成 <workdir>/Memory/ 下的 Markdown 文件，并用一个简短的 MEMORY.md 做索引，自动注入系统提示 _middleware.py:513。 

from agentscope.middleware import AgenticMemoryMiddleware
from agentscope.tool import Edit, Read, Toolkit, Write

memory = AgenticMemoryMiddleware(workdir="/tmp/agentscope_memory")

agent = Agent(
    name="assistant",
    system_prompt="You are a helpful assistant.",
    model=model,
    toolkit=Toolkit(tools=[Read(), Write(), Edit()]),
    middlewares=[memory],
)

它在 on_reply 里启动一个异步检索任务，在 on_reasoning 前检查是否完成； 完成就把选中的 Markdown 文件以 HintBlock 注入。写入靠智能体自己调用 Read / Write / Edit，所以这几个工具必须给它。

ReMe：进程内文件型记忆

ReMeMiddleware _middleware.py:88 由 ReMe 驱动，回复后通过 auto_memory 自动抽取并写回，智能体不需要手动保存。 

from agentscope.middleware import ReMeMiddleware


async def build_reme(chat_model, embedding_model):
    memory = ReMeMiddleware(
        workspace_dir=".reme",
        parameters=ReMeMiddleware.Parameters(
            chat_model=chat_model,
            embedding_model=embedding_model,
            mode="both",
            top_k=5,
        ),
    )
    toolkit = Toolkit(tools=await memory.list_tools())
    return memory, toolkit

检索模式有三种：static_control（自动检索注入）、agent_control （只暴露 memory_search 工具）、both（默认）。 无论哪种，对话写回都会自动执行。用完要 await memory.close()。

Mem0：开箱即用的记忆后端

Mem0Middleware _middleware.py:86 由 mem0 驱动，支持开源版 AsyncMemory 与托管版 AsyncMemoryClient。 

from agentscope.middleware import Mem0Middleware


async def build_mem0(chat_model, embedding_model):
    mw = Mem0Middleware(
        user_id="alice",
        chat_model=chat_model,
        embedding_model=embedding_model,
        mode="both",
    )
    toolkit = Toolkit(tools=await mw.list_tools())
    return mw, toolkit

agent_control / both 模式下，list_tools() 会返回 search_memory _tools.py:61 和 add_memory _tools.py:151 两个工具。和 RAG 一样，不会自动进 Toolkit。

Agentic / ReMe / Mem0 怎么选

维度 Agentic Memory ReMe Mem0
存储 Markdown 文件 + MEMORY.md 索引 ReMe 工作区（文件 + 索引） mem0 后端（默认 Qdrant）
写入 智能体自己用 Write / Edit 回复后 auto_memory 自动抽取 回复后自动写回，或 add_memory 工具
检索 LLM 选文件 + MEMORY.md 索引 BM25 或向量，三种模式 向量检索，search_memory 工具
隔离键 workdir session_id 写入 / workspace_dir 检索 user_id，可选 agent_id
额外依赖 无（内置） agentscope[reme] agentscope[mem0]
适合 想完全掌控、可读可改的记忆 文件型、自动抽取 开箱即用、按用户隔离

RAG vs 长期记忆 vs 上下文压缩

机制 数据来源 生命周期 解决什么
上下文压缩（06） 当前会话的历史 一次会话内 窗口装不下
RAG（本章） 外部文档 长期，需重新索引 模型不知道你的私有知识
长期记忆（本章） 对话中沉淀的事实 跨会话 用户偏好、历史决策

三者可以同时用：压缩管窗口，RAG 管知识，长期记忆管人。 它们都通过中间件 / 配置接入，不需要改 Agent 源码。

陷阱与窍门

KnowledgeBase 建好了但检索报错

先看 vector_store 是否在 async with 里。KnowledgeBase 不会替你打开连接； 没进入上下文就操作 collection，会直接失败。

维度对不上

collection 的维度由 embedding_model.dimensions 决定。换嵌入模型后必须重建 collection， 否则写入或检索会报维度不匹配。索引与检索也必须是同一个模型。

agentic 模式检索工具没生效

RAGMiddleware.list_tools() 返回的 search_knowledge 不会自动注册。 必须 Toolkit(tools=await mw.list_tools())，否则模型根本看不到这个工具。 长期记忆的 search_memory / add_memory 也一样。

把 static 注入当成永久上下文

persist_hint=False 是默认值：检索结果在推理后会被移出上下文。 如果你希望它留在后续轮次，显式设 persist_hint=True，并接受它占用 token。

重排候选数小于 top_k

rerank_candidate_k 必须不小于 top_k，否则重排只能在不足的结果里换顺序， 等于没起作用。默认取 2 × top_k 是个合理起点。

知识库描述要写「什么时候该查」

KnowledgeBase.description 会出现在 search_knowledge 的工具说明里。 写「产品文档，包含 API 与计费规则；问价格或接口时查它」比写「文档库」有用得多。

ReMe 用完要 close

ReMeMiddleware 会启动后台任务与索引。应用退出前 await memory.close()，否则进程可能挂住。
