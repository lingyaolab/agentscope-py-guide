03 · 消息与事件

02 章你看到事件流是 Agent 的「对外语言」，但只是打印了一下 delta。这一章把它拆开： 消息（Msg）是结果，事件（AgentEvent）是过程。理解这两层，你才能自己写前端、做持久化、 甚至把服务端换成任何语言实现。

读完你能做到

  • 说清 Msg 的三个必填字段与六种内容块，知道哪种角色允许哪种块
  • 看懂 EventType 的全景，并能把一条事件流按生命周期分组
  • 用 append_event() 的规则在前端重建一条完整消息，理解 reply_id / block_id 为什么必须对齐
  • 写出一个能消费 SSE 帧的最小客户端

先说为什么：消息是「结果」，事件是「过程」

如果只关心最终答案，一个 Msg 就够了：谁说的、说了什么、什么时候结束。但只要你想做打字机效果、 展示工具调用过程、支持断线重放、或者把一次回复存进数据库，就需要过程。

AgentEvent（过程）
细粒度、只增不改的增量：一个 token、一次工具调用开始、一条工具结果。 适合实时传输，不适合直接展示给用户。
Msg（结果）
结构化、可持久化的完整消息：内容块列表 + 结束原因 + token 用量。 由事件流应用出来，也是下一次模型调用的输入。
两者的桥梁
Msg.append_event(event)：把一条事件应用到消息上。服务端持久化用它，前端重建也用它。

关键点：事件不是消息的「另一种表示」，而是消息的「施工日志」。 同样是 TEXT_BLOCK_DELTA，来了 50 条，最终只合并成一个 TextBlock。

Msg 的结构：三个必填字段 + 一组控制字段

Msg 是所有消息的基类 _base.py:70， 必填字段只有三个：name、content、role。

字段 类型 作用
name str 发送者标识，例如 "user" 或 Agent 的名字
content list[ContentBlock] 内容块列表，不是字符串
role "user" | "assistant" | "system" 决定这次消息在模型侧的角色
id str 自动生成；一次 reply 里它同时是 reply_id
metadata dict 业务自定义字段，不参与模型输入
created_at / finished_at str ISO 8601 时间戳
usage Usage | None 累计 token 用量
finished_reason ReplyFinishedReason | None completed / exceed_max_iters / interrupted / error
structured_output dict | None 结构化输出结果
error ErrorInfo | None 仅当结束原因是 error

三个便捷构造器负责补默认值：UserMsg() _base.py:569、 AssistantMsg() _base.py:622、 SystemMsg() _base.py:680。 它们会把字符串自动包成 TextBlock。

角色不同，允许的内容块也不同，这是 Msg 构造时的硬校验：

role 允许的块 校验位置
user TextBlock、DataBlock（文字 + 图片/音频） _base.py:32
system 只允许 TextBlock _base.py:47
assistant 任意内容块（文本、思考、工具调用、工具结果） 不额外限制

三个常用读取方法

msg.get_text_content()          # 拼接所有 TextBlock，没有则返回 None
msg.get_content_blocks("text")  # 按类型过滤，返回对应子类
msg.has_content_blocks("tool_call")  # 是否包含某类块

它们分别定义在 _base.py:155、 _base.py:161、 _base.py:131。

六种内容块：消息到底能装什么

ContentBlock 是一个联合类型 _block.py:219， 共六种。每种都有 type、id、created_at、finished_at， 区别在业务字段。

块 type 关键字段 什么时候出现
TextBlock_block.py:11 text text 模型输出的正文、用户输入的文本
ThinkingBlock_block.py:26 thinking thinking 推理模型的思考过程；也承载 Anthropic 的加密思考
HintBlock_block.py:101 hint hint、source 框架注入的提示（压缩提醒、轮次超限提醒）；发给模型时会被转成 user 消息
ToolCallBlock_block.py:138 tool_call name、input（JSON 字符串）、state 模型请求调用工具
ToolResultBlock_block.py:195 tool_result output、state、metadata 工具执行完，结果回填
DataBlock_block.py:83 data source（base64 或 URL）、name 图片、音频、视频、PDF 等二进制内容

两个状态枚举值得单独记

ToolCallBlock.state 有五个值 _block.py:128： 

pending → asking → allowed → finished
              └→ finished（用户拒绝）
pending → allowed（权限直接放行）
pending → submitted（外部执行工具）→ finished

ToolResultBlock.state 有五个值 _block.py:185： success、error、interrupted、denied、running。 前端展示工具卡片时，这两个状态就够了，不需要自己再发明一套。

为什么 ToolCallBlock.input 是字符串

流式传输时，模型返回的工具参数是一段段 JSON 片段，框架按顺序拼起来 _base.py:406。 在 TOOL_CALL_END 之前，它可能不是一个合法的 JSON 字符串，别急着 json.loads。

事件全景：三类生命周期与四条流

所有事件的类型都在 EventType _event.py:25， 取值是**大写下划线字符串**，不是 Python 类名。按用途可以分成五组：

分组 事件 用途
回复生命周期 REPLY_START、REPLY_END 一次 reply 的开始与结束；结束事件带 finished_reason
模型调用 MODEL_CALL_START、MODEL_CALL_END 每次调用模型的边界；结束事件带 token 用量
内容块流 TEXT_BLOCK_*、THINKING_BLOCK_*、DATA_BLOCK_*、HINT_BLOCK 正文、思考、多模态内容的增量
工具流 TOOL_CALL_*、TOOL_RESULT_* 工具调用参数与执行结果
交互与扩展 REQUIRE_USER_CONFIRM、REQUIRE_EXTERNAL_EXECUTION、USER_CONFIRM_RESULT、USER_INTERRUPT、EXTERNAL_EXECUTION_RESULT、CUSTOM 人机确认、外部执行、前端通知

所有事件共享一个基类 _event.py:69： id、created_at、metadata、type； 绝大多数还带 reply_id，块级事件再带 block_id 或 tool_call_id。

官方把全部事件收成一个联合类型 AgentEvent _event.py:570。 SDK 的 reply_stream() 产出的就是它的实例。

事件是「只增不改」的

同一条消息的文本不会被某条事件「覆盖」成新状态，而是由 delta 累加出来 （END 事件可选带最终全文做校正）。这让你可以安全地回放、续传、并行处理。

事件怎么拼回消息：append_event 的映射规则

这是本章最重要的一段。Msg.append_event() _base.py:243 定义了「事件 → 消息」的全部规则。它只做三件事：改 content、写 finished_at、 累加 usage。

事件 对消息做什么
REPLY_END 写 finished_at、finished_reason、error
MODEL_CALL_END 把 input / output / cache token 累加到 usage
TEXT_BLOCK_START 追加一个空的 TextBlock(id=block_id, text="")
TEXT_BLOCK_DELTA block.text += delta
TEXT_BLOCK_END 可选地用 event.text 校正全文，写 finished_at
THINKING_BLOCK_* 与文本同构，字段是 thinking
DATA_BLOCK_* base64 分片先解码再拼接，避免 padding 破坏字节流；URL 直接替换 source
HINT_BLOCK 一次性追加完整 HintBlock
TOOL_CALL_START 追加 ToolCallBlock(input="")
TOOL_CALL_DELTA block.input += delta（JSON 字符串片段）
TOOL_RESULT_START 追加 ToolResultBlock(output=[], state=running)
TOOL_RESULT_TEXT_DELTA 追加或合并 TextBlock
TOOL_RESULT_END 写 state / metadata，并把配对的 ToolCallBlock 置为 finished
REQUIRE_USER_CONFIRM 把对应 tool call 置为 asking，记录建议规则
USER_CONFIRM_RESULT asking → allowed 或 finished
REQUIRE_EXTERNAL_EXECUTION 置为 submitted
EXTERNAL_EXECUTION_RESULT 追加外部执行返回的 ToolResultBlock
CUSTOM 直接跳过，不影响消息内容

两条「静默丢弃」规则，前端必须照做

if event.reply_id != msg.id:        # 不是这条回复的事件
    return                          # 跳过并告警

if 目标 block 找不到:                # 例如 delta 先于 start 到达
    return                          # 跳过并告警

append_event 对这两种情况都只记一条 warning，然后继续 _base.py:267。 这意味着：客户端 reducer 必须用 reply_id 隔离不同回复，用 block_id / tool_call_id 定位块，不能只按到达顺序盲拼。

自己验证一遍

抓一组真实事件，建一个空的 AssistantMsg(id=reply_id, name="Friday", content=[])， 逐条 append_event()，最后和 agent.reply() 的返回值比较 content：两者应该一致。这就是服务端持久化时做的事。

块级事件的三段式：start / delta / end

除了 HINT_BLOCK 这种一次性事件，所有内容块都遵循同一个三段式： 

XXX_START  →  带 block_id，创建空块
XXX_DELTA  →  带 block_id，增量累加（0..N 条）
XXX_END    →  带 block_id，收尾（可选带最终全文）

这对前端的意义是：你可以用「块」为单位渲染，而不是用「消息」为单位。

流 START 之后就能渲染吗 END 才拿得到的东西
text 可以，占位空文本 最终全文（如有校正）、finished_at
thinking 可以，通常折叠显示 finished_at
tool call 可以显示「正在调用 X」 完整 JSON 参数（input 拼完）
tool result 可以显示进度 state、metadata、配对的 tool call 状态
data 不建议，base64 可能不完整 完整图片/音频
别在 DELTA 上做重活

文本 delta 可能非常碎。前端如果每条都触发整棵组件树重渲染，长回答会明显卡顿。 正确做法是累积到字符串、按帧（requestAnimationFrame）刷新。

前后端契约：SSE 帧、reply_id 与断线重放

SDK 的 reply_stream() 给你的是 Python 对象。一旦部署成 Agent Service，事件就会变成 SSE。服务端在 _session.py:961 处的实现很直接： 

data: {"type":"TEXT_BLOCK_DELTA","reply_id":"...","block_id":"...","delta":"你","id":"...","created_at":"...","metadata":{}}

data: {"type":"TEXT_BLOCK_DELTA","reply_id":"...","block_id":"...","delta":"好",...}

:   ← 每 30 秒一条心跳注释帧

契约可以总结成六条：

  1. 每个帧都是 data: <json>\n\n，没有 event: 字段； 事件类型在 JSON 的 type 里 _session.py:960。
  2. JSON 来自 event.model_dump(mode="json") _chat.py:483， 所以枚举已经是字符串，可以直接 JSON.parse。
  3. 心跳是 :\n\n，间隔 30 秒 _session.py:750， 用于穿过反向代理，不携带数据。
  4. 服务端会先重放当前 run 的缓冲事件，再转入实时流；客户端要按 reply_id 去重， 不能假设同一条事件只来一次 _session.py:829。
  5. 断线重连可以带 ?after=<cursor> 从游标之后重放 _session.py:818。
  6. 连接保持打开，同一会话后续的 run 会复用同一条连接 _session.py:833。

一个最小客户端

import json

import httpx


async def consume(url: str, headers: dict) -> None:
    async with httpx.AsyncClient(timeout=None) as client:
        async with client.stream("GET", url, headers=headers) as resp:
            resp.raise_for_status()
            async for line in resp.aiter_lines():
                if not line.startswith("data: "):
                    continue          # 空行、心跳注释都跳过
                event = json.loads(line[6:])
                handle(event)


def handle(event: dict) -> None:
    match event["type"]:
        case "TEXT_BLOCK_DELTA":
            print(event["delta"], end="", flush=True)
        case "TOOL_CALL_START":
            print(f"\n[tool] {event['tool_call_name']}")
        case "REPLY_END":
            print(f"\n[done] {event['finished_reason']}")
SDK 层可以不用 SSE

本章的 SSE 契约属于服务层（15、16 章）。自己写脚本时直接用 async for event in agent.reply_stream(...) 就够了，不需要经过 HTTP。 但两层的事件模型是同一套，所以这里学一次，两边都能用。

序列化：model_dump 与持久化

Msg 和事件都是 Pydantic 模型，序列化只有两个常用入口： 

msg.model_dump(mode="json")      # → dict，适合塞进 JSON 列
msg.model_dump_json()            # → str，适合直接写文件 / 发 HTTP
msg.model_validate(data)         # 反序列化
event.model_dump(mode="json")    # 事件同理

两个容易踩的点：

  • 一定要用 mode="json"。model_dump() 默认会留下 AnyUrl、SecretStr 这类 Python 对象，不能直接 json.dumps。
  • DataBlock 的 base64 很大。一条带图片的消息可能几 MB， 落库前想清楚是存 base64、存对象存储 URL，还是只存引用。

持久化时通常保存两份东西：事件日志用于重放，最终 Msg 用于下一次模型调用和列表展示。服务层用 append_event 在内存里同时维护这两份， 再做定期检查点 _chat.py:479。

陷阱与窍门

把 event.type 和小写字符串比较

事件类型的值是 "TEXT_BLOCK_DELTA"，不是 "text_block_delta"。 Python 里用 EventType.TEXT_BLOCK_DELTA 比较最稳；前端里注意大小写。

收到的 delta 拼不出完整文本

先检查是不是把不同 block_id 的 delta 拼到了一起，或者把 tool_result 的文本混进了正文。文本和工具结果是两条独立的流。

重连后出现重复内容

服务端会先重放缓冲事件再转实时 _session.py:829， 同一条事件可能被投递两次。按事件 id 或 reply_id + block_id + 序号 去重， 不要盲目追加。

TEXT_BLOCK_END 可能带全文

某些模型实现会在结束事件里给出完整文本。如果最终文本对不上，优先相信 END 的 text，它是有意用来校正流式拼接误差的。

thinking 块不一定可展示

推理模型的思考内容可能被加密（Anthropic 的 redacted thinking 就是 thinking="" + 额外字段）。前端按 type=="thinking" 过滤时会同时拿到可见和加密块， 展示前先判断 thinking 是否为空。
