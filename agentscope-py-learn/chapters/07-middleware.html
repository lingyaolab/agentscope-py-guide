07 · 中间件

06 章的压缩、卸载、注入都是框架内置行为。如果你想加自己的逻辑——审计、限流、模型降级、 动态系统提示——又不想改 Agent 源码，就用中间件。 这一章讲清七个钩子的位置、洋葱顺序，以及哪些事不该在中间件里做。

读完你能做到

  • 说出七个钩子分别包住哪一段流程，以及哪个是洋葱式、哪个是变换式
  • 写一个能同时观察 reply / 推理 / 模型调用 / 工具执行的审计中间件
  • 用 on_check_permission 拦截危险工具，而不改权限引擎
  • 解释为什么中间件实例不能随便存「当前回复」状态

先说为什么：横切逻辑不该散落在 Agent 里

日志、计时、限流、模型降级、动态提示，这些东西会横穿整个流程，但不属于 Agent 的核心职责。 如果直接改 Agent，每加一个需求就要动一次核心代码，还会和框架升级打架。

中间件的做法是：在生命周期的固定位置留钩子，你自己的类实现需要的钩子即可。 Agent 在构造时扫描每个实例，按实际实现了哪些钩子分配到不同链上 _agent.py:219； 没实现的钩子不产生任何调用开销。

Onion（洋葱式）
中间件包住下一层：before → next_handler() → after。
Transformer（变换式）
串成流水线：上一个的输出是下一个的输入，没有「内层」。
Tool source（工具来源）
声明工具，但不在 reply 路径上，Agent 不会自动调用。

七个钩子：一张表看清

钩子 类型 包住什么 能拿到
on_reply_base.py:68 Onion 一次完整 reply（所有 ReAct 轮次） inputs
on_reasoning_base.py:101 Onion 一轮推理（组装输入 → 模型调用 → 解码） tool_choice
on_acting_base.py:124 Onion 仅 toolkit.call_tool 的执行 tool_call
on_check_permission_base.py:170 Onion 一次工具调用的权限决策 tool_call、tool、tool_input
on_model_call_base.py:213 Onion 一次底层模型 API 调用 messages、tools、tool_choice、current_model
on_compress_context_base.py:241 Onion Agent.compress_context() context_config、instructions
on_system_prompt_base.py:264 Transformer 每次组装系统提示 current_prompt（字符串）
list_tools_base.py:286 Tool source 不在执行路径上 —

一个中间件类可以实现任意子集。Agent 构造时会分成七条链 _agent.py:221。

on_acting 不包含权限与上下文写入

它只包住 toolkit.call_tool 这一层纯执行 _base.py:132。 权限检查在它之前，工具结果的上下文写入在它之后。所以「统计工具耗时」用 on_acting，「拦截工具」用 on_check_permission。

顺序：谁在外面，谁在里面

洋葱型钩子：列表里第一个中间件在最外层。 

middlewares = [mw1, mw2]
# mw1 前 → mw2 前 → 内部逻辑 → mw2 后 → mw1 后

流式钩子还有一层细节：内层先看到每一个 yield 出来的事件。 

mw1_pre → mw2_pre → mw2_event → mw1_event → ... → mw2_post → mw1_post

变换式的 on_system_prompt 则是从左到右接力 _agent.py:3248： 

original_prompt → mw1.on_system_prompt() → mw2.on_system_prompt() → final

整体嵌套关系

on_reply
  └── 每一轮 ReAct：
        ├── on_compress_context → compress_context()
        │     └── on_system_prompt（压缩前数 token）
        ├── on_reasoning
        │     ├── on_system_prompt（组装模型输入）
        │     └── on_model_call
        └── on_acting（本轮每个工具调用一次）

对应到源码：_reply _agent.py:915、 _reasoning _agent.py:1664、 _acting _agent.py:2752、 _check_permission _agent.py:2366、 _call_model _agent.py:3334 各有一段「有中间件 / 无中间件」的分支。

上手：一个审计中间件

下面这个中间件同时观察 reply、模型调用和工具执行，足够覆盖大多数排查场景： 

import time

from agentscope.middleware import MiddlewareBase


class AuditMiddleware(MiddlewareBase):
    async def on_reply(self, agent, input_kwargs, next_handler):
        print(f"[reply] {agent.name} start")
        async for item in next_handler(**input_kwargs):
            yield item
        print(f"[reply] {agent.name} end")

    async def on_model_call(self, agent, input_kwargs, next_handler):
        model = input_kwargs["current_model"].model
        start = time.time()
        result = await next_handler(**input_kwargs)
        print(f"[model] {model} {time.time() - start:.2f}s")
        return result

    async def on_acting(self, agent, input_kwargs, next_handler):
        tool_call = input_kwargs["tool_call"]
        start = time.time()
        async for chunk in next_handler(**input_kwargs):
            yield chunk
        print(f"[tool] {tool_call.name} {time.time() - start:.2f}s")

挂载方式：

agent = Agent(
    name="Friday",
    system_prompt="...",
    model=model,
    toolkit=toolkit,
    middlewares=[AuditMiddleware()],
)
一个类实现多个钩子就够了

不需要为每个钩子建一个类。把它们放在同一个类里，Agent 会按钩子把同一个实例分到多条链上。 想按顺序控制，就把需要在外层的实例放在列表前面。

工具钩子：在工具执行前后插手

on_acting 的 next_handler 产出的是 ToolChunk 流，最后一个是完整的 ToolResponse。 你可以观察、修改、甚至替换整段流： 

from agentscope.tool import ToolChunk, ToolResponse


class ToolAuditMiddleware(MiddlewareBase):
    async def on_acting(self, agent, input_kwargs, next_handler):
        tool_call = input_kwargs["tool_call"]
        print(f"[tool] {tool_call.name} input={tool_call.input}")
        async for chunk in next_handler(**input_kwargs):
            if isinstance(chunk, ToolChunk):
                print(f"[chunk] {len(chunk.content)} blocks")
            else:
                print(f"[response] state={chunk.state}")
            yield chunk
别在 on_acting 里做权限判断

走到 on_acting 时，工具已经被解析、参数已验证、权限也已经通过 _base.py:178。 在这里抛异常虽然能中断执行，但不会产生权限系统的事件与规则，前端既看不到 REQUIRE_USER_CONFIRM，也拿不到 DENIED 的工具结果。 要拒绝工具，用 on_check_permission。

模型调用钩子：改输入、改输出

on_model_call 是最贴近模型的一层，能拿到四个字段 _base.py:226： messages、tools、tool_choice、current_model。 改 messages 可以注入临时上下文；换 current_model 可以做降级。 

class ModelFallbackMiddleware(MiddlewareBase):
    def __init__(self, fallback_model):
        self._fallback = fallback_model

    async def on_model_call(self, agent, input_kwargs, next_handler):
        try:
            return await next_handler(**input_kwargs)
        except Exception as e:
            print(f"primary failed: {e}")
            return await next_handler(current_model=self._fallback)
流式调用的失败可能发生在「返回之后」

next_handler 返回的是 ChatResponse 或 AsyncGenerator。流式时，连接错误可能在你拿到 generator 之后才抛。 想做可靠的降级，要么先把流消费成非流式，要么在生成器内部捕获 _base.py:219。

权限钩子：拦截与放行

on_check_permission 在工具解析、参数校验之后，决策被消费之前执行 _base.py:178。 它拿到的是 tool_call 与 tool_input 的副本， tool 则是真实实例。改副本不会影响真正执行，但改 tool 的字段 可能影响后续工具调用 _agent.py:2373。 

from agentscope.permission import PermissionBehavior, PermissionDecision


class DenyBashMiddleware(MiddlewareBase):
    async def on_check_permission(self, agent, input_kwargs, next_handler):
        if input_kwargs["tool_call"].name == "Bash":
            return PermissionDecision(
                behavior=PermissionBehavior.DENY,
                message="Bash is disabled in this environment.",
            )
        return await next_handler(**input_kwargs)

不调用 next_handler 就直接返回，会跳过内置权限引擎 _base.py:187。 这既是能力也是风险：你等于接管了这次调用的全部判断。

如果只是想「加一条规则」，更稳的做法是调用 next_handler 拿到原决策， 再按需要升级或降级，而不是完全替换。

进阶：吞掉 ReplyEndEvent，强制再来一轮

on_reply 不只能观察。如果它收到 ReplyEndEvent 却不 yield， reply 就不会结束，Agent 会再走一轮推理 _base.py:76。 

from agentscope.event import ReplyEndEvent
from agentscope.message import HintBlock
from agentscope.types import ReplyFinishedReason


class ContinueOnceMiddleware(MiddlewareBase):
    async def on_reply(self, agent, input_kwargs, next_handler):
        continued = False
        async for item in next_handler(**input_kwargs):
            can_continue = (
                isinstance(item, ReplyEndEvent)
                and item.finished_reason
                in {
                    ReplyFinishedReason.COMPLETED,
                    ReplyFinishedReason.EXCEED_MAX_ITERS,
                }
                and not continued
            )
            if can_continue:
                continued = True
                agent.state.cur_iter = min(
                    agent.state.cur_iter,
                    agent.react_config.max_iters - 1,
                )
                agent.state.append_context(
                    agent.name,
                    [HintBlock(hint="结束前请再检查一遍结果。")],
                )
                continue
            yield item
这是最容易写出死循环的钩子

必须自己设重试上限；如果吞的是 EXCEED_MAX_ITERS，还要先释放轮次 （如上例调整 cur_iter），否则下一轮没有预算。 INTERRUPTED 的结束事件不能用这个机制续命，应原样传出。

预算控制

加权成本 = input_token_weight × input + output_token_weight × output _budget.py:35。 达到预算后，它会往最后一条本 Agent 的 assistant 消息追加 HintBlock （否则新建一条），并把下一步的 tool_choice 强制改成 none，逼模型收尾； 如果还有结构化输出没交，则只允许结构化输出工具，不是全禁 _budget.py:230。 

from agentscope.middleware import ReplyBudgetControlMiddleware

agent = Agent(
    ...,
    middlewares=[
        ReplyBudgetControlMiddleware(
            token_budget=10000,
            input_token_weight=1.0,
            output_token_weight=2.0,
        ),
    ],
)

它的状态不放在实例上，而是放在 agent.state.middle_context，按中间件 key 和 reply_id 索引 _budget.py:45。 这样同一个实例可以跨 Agent、跨 HITL 恢复安全复用。

模型路由

每次 reply 开始时选一次模型，回复期间替换 agent.model，结束后在 finally 里恢复 _model_router.py:109。 路由失败或输入里没有用户文本时，沿用原模型，不中断回复。

陷阱与窍门

在实例属性里存「当前回复」状态

中间件实例可能被多个 Agent、多次 reply 复用。把 self.current_reply_id 这类状态放实例上，并发时会串。正确做法是放 agent.state.middle_context， 用 reply_id 隔离，像 ReplyBudgetControlMiddleware 那样。

把流式返回值当普通值 await

on_model_call 的 next_handler 可能返回 AsyncGenerator。直接 await 它不会消费内容。 on_acting 则总是在处理异步生成器，必须 async for。

误以为 on_acting 能看到权限事件

权限确认发生在 on_check_permission 和 _execute_tool_call， 不在 on_acting 里。想审计「哪些工具被拒绝」，应该挂 on_check_permission 或从事件流里读。

只实现需要的钩子

没实现的钩子会被 is_implemented 过滤掉 _base.py:55， 不会产生调用。不要为了「统一」把七个钩子都写一遍，只留空实现反而增加维护成本。

用 get_middleware_key() 区分状态

默认 key 是类名。同一个类挂两份、又都要在 middle_context 里存状态时， 覆写 get_middleware_key() 返回不同值 _base.py:296。
