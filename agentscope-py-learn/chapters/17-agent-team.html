17 · Agent Team

09 章的 TeamPipeline 是 SDK 内的固定编排：队长调 TeamAssign， 成员在自己的上下文里跑。服务层的 Agent Team 不一样——每个 Worker 是一个完整会话， 有自己的状态、工作区绑定和事件流，可以分布在不同进程。这一章讲它怎么协作。

读完你能做到

  • 说清 Leader、Worker、Team、Session 四者的关系
  • 知道五个内置 team 工具分别由谁调用、做什么
  • 用 SubAgentTemplate 给不同角色设置不同权限
  • 解释 TeamSay 为什么不是「直接调用」，而是「投递 + 唤醒」

先说为什么：服务层还要一套 Team

SDK 的 TeamPipeline 适合「一个进程里、固定流程」的协作。 服务层的团队要解决另外几个问题：

问题 服务层 Team 的答案
Worker 要能独立观察 每个 Worker 是一个独立 Session，有自己的 SSE 流
Worker 要能并行、分布 通过消息总线投递，跨进程 / 跨节点
Worker 要能被单独中断 / 恢复 复用 13、16 章的会话状态与 HITL
团队要能持久化 TeamRecord 存成员关系

所以服务层 Team 不是「另一套编排框架」，而是四个内置工具 + 会话 + 消息总线。 没有新的运行时。

Leader / Worker / Session / Team

概念 说明
Team 一个用户拥有的一组持久化成员，TeamRecord 存名称、描述与成员列表
Leader 创建团队的会话。只有它能加 / 删成员或解散团队
Worker 被派生出的会话，跑自己的 ReAct 循环，继承 Leader 的聊天模型与工作区上下文
Team Message 通过消息总线在成员间路由，以 HintBlock 投递，外层包 <team-message from="…">

关键点：Worker 不是 Leader 协程里的子任务，而是同一服务里并发运行的另一个会话。 Leader 通过读 Worker 的流、或等 Worker 用 TeamSay 回报来观察进展。

五个内置工具

Leader 会话自动获得这些工具；Worker 只看到 TeamSay。

工具 谁用 作用
TeamCreate_team_create.py:30 Leader 以当前会话为根创建团队，并成为 leader
AgentCreate_agent_create.py:146 Leader 派生一个 Worker，给名称、角色、首任务；创建后立即执行
AgentInvite_agent_invite.py:141 Leader 邀请一个已有 Agent 加入，为它新建会话
TeamSay_team_say.py:78 Leader + Worker 向指定成员或广播消息
TeamDelete_team_delete.py:12 Leader 解散团队并清理成员会话

Team 工具都继承同一个基类 _team_tool_base.py:22， 权限硬编码为 ALLOW _team_tool_base.py:152： 它们本身不碰文件系统，真正的危险操作发生在 Worker 自己的工具里，仍按 Worker 的权限上下文检查。

AgentCreate：派生 Worker

参数模型在 _agent_create.py:115。 一次创建至少包含：

信息 作用
name_agent_create.py:118 成员名，也是 TeamSay(to=...) 的地址；团队内必须唯一
角色描述 写进 Worker 的系统提示，告诉它自己负责什么
首个任务 创建后立即交给 Worker 执行
subagent_type 注册了自定义模板时才出现，选择角色蓝图

Worker 创建后立刻开始执行，不是先挂起等指令。所以 Leader 不要在 AgentCreate 后马上再发 TeamSay 重复任务；等它回报或读它的流。

AgentInvite：借用已有 Agent

AgentInvite 和 AgentCreate 的区别：

AgentCreate AgentInvite
来源 全新 Worker 已存在的 Agent
工作区 继承 Leader 的 借用发起方在该 Agent 下的主会话
团队解散 永久删除 只删团队会话，Agent 本身不受影响

候选池由 Leader 可见的 Agent 构成，且必须同时满足 Invitable=true 与 Invite description 非空。两者缺一，或候选池为空时， Leader 根本不会拿到 AgentInvite 工具。

邀请别人的 Agent 不带对方环境

借用会话的工作区与模型取自发起方自己在该 Agent 下的主会话， 不会带上属主的 MCP、技能、缓存与会话权限。Agent 定义（系统提示、上下文与 ReAct 配置） 仍来自原记录。

TeamSay：消息怎么到

TeamSay _team_say.py:78 不是同步调用。完整链路是： 

1. 发送方调用 TeamSay
2. 消息总线把 HintBlock 推到接收方会话的收件箱
3. 为接收方入队一个唤醒信号
4. 任意进程的 wakeup dispatcher 取走唤醒
5. ChatService.run 驱动接收方会话
6. InboxMiddleware 在下一次推理前清空收件箱
7. 团队消息以 HintBlockEvent 落入接收方上下文

这也解释了为什么团队天然支持分布式：Leader 和 Worker 可以在不同进程、不同节点， 只要共享同一个 Redis 消息总线。

消息是「投递」不是「等待」

TeamSay 返回时，接收方可能还没开始处理。Leader 要拿到结果， 要么等对方再 TeamSay 回来，要么读对方的会话事件流。

SubAgentTemplate：角色化 Worker

默认所有 Worker 共用同一套系统提示与权限。要区分「只读 explorer」和「可写 coder」， 注册 SubAgentTemplate _types.py:114：

字段 说明
type_types.py:132模板标识，成为 subagent_type 的枚举值
description_types.py:140给 Leader 看的选择依据
system_prompt_template_types.py:148Worker 系统提示模板
permission_context_types.py:167角色权限边界，比如 EXPLORE
context_config / react_config上下文与循环配置
tasks_context_types.py:214预置任务

系统提示模板支持五个占位符：

{team_name}          {team_description}
{member_name}        {member_description}
{leader_name}
from agentscope.app import create_app, SubAgentTemplate
from agentscope.permission import PermissionContext, PermissionMode

app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
    custom_subagent_templates=[
        SubAgentTemplate(
            type="explorer",
            description="只读探索代码库，不做任何修改。",
            system_prompt_template=(
                "你是 {member_name}，团队 '{team_name}' 的 explorer。\n"
                "团队目标：{team_description}\n"
                "你的角色：{member_description}\n"
                "完成任务后用 TeamSay 向 {leader_name} 汇报。"
            ),
            permission_context=PermissionContext(
                mode=PermissionMode.EXPLORE,
            ),
        ),
    ],
)
参数名以源码为准

官方文档写的是 sub_agent_templates，但 2.0.11 源码里 create_app 的参数名是 custom_subagent_templates _app.py:131。 按源码写，避免 TypeError。

没注册模板时，AgentCreate 不暴露 subagent_type； 注册后自动出现枚举，包含 "default"。注册一个 type="default" 的模板会覆盖内置默认模板；type 重复会在启动时抛 ValueError。

团队里的 HITL

Worker 也是普通会话，所以它的工具确认按 08、16 章的规则走：

  • Worker 停在确认上时，请求原样流到它的会话流
  • 答复按 reply_id 路由回该 Worker
  • Worker 挂起期间，Leader 停在对应的分派上，等它完成再继续
  • 其他未挂起的 Worker 照常跑完，已完成结果先交回 Leader

Leader 的会话流里还会出现子 Agent 的 HITL 卡片投影（CustomEvent）， 前端可以据此在 Leader 界面直接提示。

框架还用 TeamMemberLoopMiddleware _team_member_middleware.py:21 提醒成员「干完要回报」，避免 Worker 自己结束却什么都不说。

生命周期与成本

只有 Leader 能解散团队。解散时的语义：

成员来源 团队解散后
AgentCreate 派生的 Worker 永久删除
AgentInvite 邀请的 Agent 只删该团队会话，Agent 本身保留
每个 Worker 都是一份完整 token 开销

Worker 不是轻量协程，而是独立会话：自己的模型调用、工具调用、上下文压缩。 派生 5 个 Worker，成本大致是 6 份（Leader + 5）。先想清楚是否真的需要这么多。

SDK TeamPipeline vs Service Agent Team

维度 SDK TeamPipeline Service Agent Team
运行位置 同一进程 任意进程 / 节点
成员形态 内存里的 Agent 实例 完整 Session
通信 直接调用 reply_stream 消息总线 + 收件箱 + 唤醒
前端可观察 你自己消费一个流 每个成员独立 SSE 流
持久化 无 TeamRecord + 会话状态
适合 脚本、固定协作流程 产品级多智能体、多用户

陷阱与窍门

把 TeamSay 当同步函数

它只负责投递 + 唤醒。返回时对方可能还没处理。要结果就等对方回报，或读对方会话流。

以为 Worker 能继续派生 Worker

Worker 只看到 TeamSay。派生、邀请、解散都只有 Leader 能做。

在 AgentCreate 后立刻再发一遍任务

Worker 创建后立即执行首任务。再发一遍会重复劳动，甚至互相覆盖。

用文档里的 sub_agent_templates

2.0.11 源码参数是 custom_subagent_templates。以源码为准， 否则启动时 TypeError。

忘记设 Invitable

候选池为空时，Leader 根本看不到 AgentInvite。 Invitable 和 Invite description 两个都要填。

给 Worker 设置更窄的权限

默认 Worker 继承 Leader 的权限设置。只读角色用 PermissionContext(mode=PermissionMode.EXPLORE)， 比在提示词里写「不要改文件」可靠得多。

20 分钟动手练习

  1. 在示例服务里让 Leader 组一个两人团队，观察 TeamCreate / AgentCreate 的调用。
  2. 注册一个 explorer 模板（EXPLORE 模式），让 Leader 派生它，确认它不能写文件。
  3. 用 TeamSay 给 Worker 追加一条指令，观察它在下一次唤醒时处理。
  4. 让一个 Worker 停在工具确认上，确认答复按 reply_id 回到正确的成员。
