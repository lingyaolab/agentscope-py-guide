26 · 综合案例

前面 25 章各讲一块积木。这一章把它们拼成一个真的能上线的服务： Atlas，一个面向团队的文档与运维助手。 它有多租户、工具、长期记忆、知识库、团队共享、IM 渠道、追踪、评测与部署清单， 最后逐项对照 AgentScope Java 2.0.4。

读完你能做到

  • 用一份 create_app 装配出带存储、总线、工作区、知识库与渠道的服务
  • 把工具、长期记忆、追踪、共享策略挂到每个聊天回合上
  • 按正确顺序初始化凭证、Agent、会话与知识库
  • 用上线清单与运行手册判断「能不能发」
  • 说清 Python 2.0.11 与 Java 2.0.4 在 Agent、服务、响应式与部署上的差异

装配：一份 create_app

create_app _app.py:113 是唯一入口。下面这份 app.py 把存储、总线、工作区、知识库、中心、 渠道、共享策略、中间件与工具全部接上： 

import os

from fastapi.middleware import Middleware
from fastapi.middleware.cors import CORSMiddleware

from agentscope.app import create_app
from agentscope.app.hub import ClawSkillHub, GitHubMCPHub
from agentscope.app.message_bus import RedisMessageBus
from agentscope.app.rag.knowledge_base_manager import CollectionPerKbManager
from agentscope.app.storage import RedisStorage
from agentscope.app.workspace_manager import LocalWorkspaceManager
from agentscope.middleware import AgenticMemoryMiddleware, TracingMiddleware
from agentscope.rag import ApproxTokenChunker, QdrantStore

from policy import TeamResourcePolicy
from tools import build_tools


async def build_middlewares(
    user_id: str,
    agent_id: str,
    session_id: str,
    workspace,
):
    return [
        TracingMiddleware(),
        AgenticMemoryMiddleware(
            workdir=workspace.workdir,
            backend=workspace.get_backend(),
        ),
    ]


storage = RedisStorage(
    host=os.environ["REDIS_HOST"],
    port=int(os.environ.get("REDIS_PORT", "6379")),
)
message_bus = RedisMessageBus(
    host=os.environ["REDIS_HOST"],
    port=int(os.environ.get("REDIS_PORT", "6379")),

    basedir="/data/workspaces",

    storage=storage,

app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
    knowledge_base_manager=knowledge_base_manager,

工具：只给该给的人

extra_agent_tools 在每次组装 Agent 时被调用，签名是 (user_id, agent_id, session_id)。用它按租户注入工具， 比把所有工具塞进全局 Toolkit 安全得多。 

from agentscope.permission import PermissionBehavior, PermissionDecision
from agentscope.tool import FunctionTool


async def build_tools(user_id: str, agent_id: str, session_id: str):
    allow_read = PermissionDecision(
        behavior=PermissionBehavior.ALLOW,
        decision_reason="handbook is read-only",
        message="allowed",
    )

    async def search_handbook(query: str) -> str:
        """Search the team handbook and return relevant passages."""
        # 这里换成你的检索服务，并按 user_id 做权限过滤
        return f"[{user_id}] results for: {query}"

    return [
        FunctionTool(
            search_handbook,
            permission=allow_read,
            is_read_only=True,
        ),
    ]
工具描述就是提示词

FunctionTool 从函数签名与 docstring 生成 schema。 参数名、类型、docstring 写得含糊，模型就会乱传参。 工具描述要和系统提示一起 review。

写操作不要给 ALLOW。用 ASK 或权限模式限制， 让第 08 章的确认流程接管；有副作用的工具还应该配沙箱工作区。

记忆与知识库：一个存偏好，一个存事实

这两件事经常被混在一起：

能力 存什么 实现
长期记忆 用户偏好、上次结论、跨会话事实 AgenticMemoryMiddleware_middleware.py:359
知识库 产品手册、政策、工单等可检索文档 CollectionPerKbManager + KnowledgeBase

记忆放在工作区里，跟随 Agent 的隔离策略；知识库是独立资源，可以被共享。 不要在记忆里重复存整份手册，也不要把用户偏好塞进知识库。

共享：团队额度与只读边界

Atlas 里 alice 是管理员，她配置的 OpenAI 凭证供团队使用，但成员不能看到 key。 这正是第 20 章的 ResourceAccessPolicyBase： 

from agentscope.app.access import (
    ResourceAccessPolicyBase,
    ResourceKind,
    ResourcePermission,
    ResourceRef,
)

# 生产环境从 IAM / 数据库查询，这里用常量演示
GRANTS = {
    ("bob", ResourceKind.CREDENTIAL): [
        ("alice", "cred-openai-prod", ResourcePermission.READ),
    ],
    ("carol", ResourceKind.KNOWLEDGE_BASE): [
        ("alice", "kb-handbook", ResourcePermission.READ),
    ],
}


class TeamResourcePolicy(ResourceAccessPolicyBase):
    async def list_accessible(self, viewer_id, kind, storage):
        return [
            ResourceRef(
                kind=kind,
                owner_id=owner_id,
                resource_id=resource_id,
                permission=permission,
            )
            for owner_id, resource_id, permission in GRANTS.get(
                (viewer_id, kind),
                [],
            )
        ]
  • 凭证共享只给「使用能力」，任何列表 / 详情都不会返回 key
  • 知识库 READ 可以检索，EDIT 才能改文档
  • 共享 Agent 只共享配置，不共享工作区、MCP、技能与记忆
  • list_accessible 只返回跨属主资源，自己的资源由服务合并

渠道与中心：让用户自助扩展

渠道把 Agent 放进飞书 / 钉钉 / Discord；中心让用户自己装 MCP 与技能。 两者都是「用户不经过你的代码就能扩展能力」。

  • channels=[FeishuChannel, DingTalkChannel] 注册适配器
  • 长连接只允许一个进程持有：enable_channel_worker 只在一个副本为真
  • mcp_hubs=[GitHubMCPHub()] 让用户浏览并安装 MCP
  • skill_hubs=[ClawSkillHub()] 让用户安装技能
  • 安装 ≠ 装配：装进资源池后，还要在工作区里装配给某个 Agent
渠道与 Web 共用同一套会话

渠道消息最终也走 ChatService，所以权限、记忆、追踪、预算对两边一致。 不需要为 IM 单独写一套 Agent 逻辑。

语音与 A2A：按需开启，不要默认全开

能力 开启方式 代价
浏览器语音 配置 realtime_ice_servers，走 /realtime/sessions/{id}/offer 带宽、音频 token、TURN 成本
TTS 播报 给 Agent 加 TTSMiddleware 首字延迟、TTS 费用
A2A 客户端 安装 agentscope[a2a]，用 A2AAgent 外部依赖、跨组织信任
A2A 服务端 官方 a2a-sdk + AgentExecutor 额外的鉴权、限流、TaskStore

Atlas 默认只开文本与手册检索；语音和 A2A 作为独立开关， 先在小范围用户上验证，再放量。

上线前：按顺序初始化资源

Agent Service 是资源驱动的：没有凭证和 Agent，会话无从创建。 推荐顺序如下：

步骤 端点 注意
1. 建凭证 GET /credential/schemas → POST /credential 前端按 schema 渲染；密钥由存储层保存，API 返回脱敏，静态加密需自行补
2. 建 Agent 模板 GET /agent/schema/v2 → POST /agent 系统提示、context / ReAct 配置
3. 建会话 POST /sessions 绑定 agent_id、credential_id 与模型
4. 建知识库 POST /knowledge_bases → 上传文档 等索引状态变成可用再检索
5. 装配 MCP / 技能 POST /workspace/mcp / POST /workspace/skill/upload（或 /workspace/skill/from-library） 安装只是进资源池，装配才生效
6. 开始对话 POST /chat 立即返回 started_chat.py:136
7. 订阅事件 GET /sessions/{id}/stream 后接入会先收到回放再收实时

重复提交同一会话的 /chat 会得到 409 _chat.py:154， 因为同一会话只允许一个在途 run。前端应显示「正在回答」，而不是重试。

评测：上线前的最后一道门

Atlas 至少要有四类用例：

类型 怎么测 跑在什么时候
工具契约 假模型脚本 + 事件断言 每个 PR
检索质量 recall@k / MRR，固定问题集 每个 PR（不需要模型）

发布门禁只看两个数：通过率不低于基线， 单次评测成本不超过预算。只盯通过率会纵容成本膨胀， 只盯成本会砍掉该测的样本。

运行手册：先看现象，再看层

现象 先查 处理
401 鉴权依赖、凭证是否共享 换 token；检查 resource_access_policy
409 会话是否已有在途 run 等待、订阅事件，或调用 interrupt
429 网关配额、provider 限流 退避、提高配额、切 fallback
503 /health 哪个组件 not_ready 检查 Redis / 存储 / 工作区初始化
工具迟迟不返回 是否被卸载到后台 查后台任务与收件箱，不要重复触发
fallback 比例升高 主模型错误率与延迟 修主模型配置，别长期靠备用
索引队列积压 index worker 是否在跑 扩容 worker 或检查 blob store
成本突增 迭代轮次、上下文、TTS/语音 降 max_iters、开预算、查异常租户

这份手册要跟告警绑在一起：告警里直接写「先查哪一行」， 比写「请联系管理员」有用得多。

两个版本概念相近，但工程形态不同。把同一件事放在一起看：

迁移时最容易踩的四个坑

  1. 不要照搬 Java Service 的拆分：Python 的 create_app 已经把网关、存储、会话、SSE 放在一起，先跑通单体，再按需要拆 worker。
  2. Reactor 不是 asyncio：Flux 的背压与取消语义，对应到 Python 是异步生成器的消费与 aclose，不能机械翻译。
  3. 工具注解不同：Java 的 @Tool 对应 Python 的 FunctionTool 或 ToolBase 子类，schema 生成规则也不同。
  4. 服务存储不同：Java Service 是 Java Gateway + Dataplane、Go Control（aistiod）与 PostgreSQL；Python 侧选 Redis 或 SQLAlchemy，迁移脚本与备份策略要重做。

Java 站第 11 章的「笔记 Agent」是 SDK 级综合案例，第 19–26 章才是服务与运维； Python 站把两者合在 15–26 章。读的时候按「SDK → 服务 → 运维」三段对照， 不要按章节号硬对齐。

陷阱与窍门

把 Atlas 当成一个巨型 Agent

一个 Agent 塞进所有工具、所有知识库、所有权限，最后谁都管不清。 按职责拆 Agent 模板，用团队 / 子 Agent 组合。

用记忆存手册

记忆是用户偏好与结论，知识库是可检索事实。混用会让上下文膨胀， 而且共享与更新都变难。

共享凭证时顺手共享工作区

共享 Agent 只共享配置，工作区、MCP、技能、记忆都不跟过去。 需要共享知识就共享知识库，不要共享别人的工作区。

所有能力默认开启

语音、A2A、渠道、中心都会增加攻击面与成本。做成开关，按租户灰度， 默认只开文本与检索。

上线只看 demo

demo 能跑不代表能上线。至少过一遍本章的上线清单、运行手册与回归集。

先单体，后拆分

create_app 的多副本已经够大多数团队用。真的需要独立索引、 渠道或调度 worker 时再拆，不要一开始就上微服务。

  1. 把 app.py 跑起来，用 /health 确认所有组件 ok。
  2. 按顺序建凭证、Agent、会话，发一条 /chat 并订阅 SSE。
  3. 上传一份手册到知识库，问一个只有手册里才有答案的问题。
  4. 给 alice 的凭证加一条共享给 bob 的策略，确认 bob 能用但看不到 key。
  5. 加一个 TracingMiddleware，在 Jaeger / Tempo 里找到这次 reply 的 span 树。
  6. 写 3 条假模型回归用例 + 1 条真实模型冒烟，接进 CI。
