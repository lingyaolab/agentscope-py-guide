10 · 计划模式与 SOP

09 章的流水线由开发者固定「谁先谁后」。这一章是另一种思路： 计划模式让模型自己维护任务清单，SOP让开发者把流程定义成 一串必须逐个验收的里程碑。两者都解决「多步任务」，但控制权在谁手里完全不同。

读完你能做到

  • 用四个任务工具让模型自己拆解、认领、完成工作
  • 说清 blocks / blocked_by 的双向关系，以及为什么 deleted 不是状态
  • 用 SOP + SOPEngine 定义一个带验收的固定流程
  • 把运行状态落盘，隔一个进程再接着跑

先说为什么：任务清单不是给用户看的

多步任务最容易出的问题不是「不会做」，而是「做着做着忘了」。上下文一压缩，前面定的步骤就没了； 模型开始即兴发挥，最后交付的东西和最初要求对不上。

两种机制分别从两个方向解决它：

机制 谁决定步骤 适合
计划模式 模型通过工具调用自己维护 步骤无法预先确定，需要边做边调整
SOP 开发者在构造时写死 步骤固定、每步都有明确验收标准

两者都不是「多 Agent 通信协议」，而是让多步工作有外部记忆和外部约束。

计划模式：四个任务工具

AgentScope 内置四个任务工具，它们都继承同一个基类 _task_tool_base.py:14：

工具 操作 只读
TaskCreate_create_task.py:25 向清单末尾追加任务 否
TaskGet_get_task.py:18 按 ID 读取完整任务 是
TaskList_list_task.py:16 列出所有任务与状态 是
TaskUpdate_update_task.py:54 改状态、字段、依赖，或删除 否

四个工具都是状态注入式：is_state_injected=True _task_tool_base.py:25， 运行时会把 AgentState 注入，工具直接读写 agent.state.tasks_context。

权限也全部硬编码为 ALLOW _task_tool_base.py:40： 它们只改内存状态，不会触发用户确认。

装配方式和普通工具一样：

from agentscope.tool import TaskCreate, TaskGet, TaskList, TaskUpdate, Toolkit

toolkit = Toolkit(
    tools=[
        TaskCreate(),
        TaskGet(),
        TaskList(),
        TaskUpdate(),
    ],
)

任务模型：状态、依赖与 owner

任务定义在 Task _task.py:10：

字段 说明
id_task.py:28单调递增的数字串，由 TaskCreate 分配
subject_task.py:13一句话命令式描述
description_task.py:16详细需求与上下文
state_task.py:25pending / in_progress / completed
owner_task.py:31多智能体场景下的认领者
blocks_task.py:34被本任务阻塞的任务 ID
blocked_by_task.py:37必须先完成的任务 ID
deleted 不是状态，是操作

Task.state 只接受三个值。把 status 设为 deleted 会硬删除任务，并修正所有引用它的依赖边 _update_task.py:142。 删除后任务不会以「已删除」状态留在列表里。

依赖是双向的

TaskUpdate 的 add_blocked_by 会同时改两端 _update_task.py:199： 让任务 2 依赖任务 1 时，2.blocked_by 加 "1"， 1.blocks 自动加 "2"。手动改 tasks_context 时， 这两端要自己保持同步。

阻塞只是建议性的：TaskList 会标注未解依赖， 但运行时不会阻止模型去做一个被阻塞的任务。它是给模型看的优先级信号，不是硬锁。

所有任务存在 agent.state.tasks_context _state.py:175 里，跟着 AgentState 一起序列化。两个 Agent 默认不共享任务清单。

计划怎么推进：创建 → 认领 → 完成

典型的计划循环：

  1. 收到新指令，对每个离散步骤调用一次 TaskCreate，给一句 subject 和更详细的 description
  2. TaskList 看队列，挑 ID 最小、没有未解 blocked_by 的 pending 任务
  3. 开工前 TaskUpdate(status="in_progress", owner=...)
  4. 描述很长时先 TaskGet 拿完整上下文
  5. 完成后 TaskUpdate(status="completed")；发现新工作就回到 TaskCreate；不做了就 deleted
async def add_dependency(agent) -> None:
    # 让任务 2 依赖任务 1
    await TaskUpdate()(
        task_id="2",
        add_blocked_by=["1"],
        _agent_state=agent.state,
    )
    # 结果：task "2".blocked_by == ["1"]，task "1".blocks == ["2"]

预置任务

任务就是普通 Pydantic 模型，可以在第一次 reply 之前直接写进去： 

from agentscope.state import Task

agent.state.tasks_context.tasks.extend(
    [
        Task(
            id="1",
            subject="读需求",
            description="阅读 README.md 与 CONTRIBUTING.md。",
            metadata={"source": "seed"},
        ),
        Task(
            id="2",
            subject="写实现计划",
            description="基于需求产出分步计划。",
            blocked_by=["1"],
            metadata={"source": "seed"},
        ),
    ],
)
# 手动维护反向边
agent.state.tasks_context.tasks[0].blocks.append("2")

手动修改时有三条硬要求：ID 用数字串（TaskCreate 取 max(int(id)) + 1 _create_task.py:105）、 依赖边双向一致、状态值合法。

任务注入：让模型记得还有活

计划模式真正起作用，靠的是 06 章的运行时状态注入。当存在 pending 或 in_progress 任务，且上下文中既没有任务相关工具调用、也没有旧的任务注入时， 框架会插一条提示，告诉模型还有多少活没干 _agent.py:1393。

这条注入在上下文压缩后尤其重要：任务工具调用可能已经被摘要掉，但任务本身还在 agent.state.tasks_context 里。注入让模型重新「看见」它。

框架靠 InjectionConfig.task_tool_names 识别「模型已经知道任务了」 _config.py:326， 默认是四个任务工具。如果你自定义了任务工具名，要同步改这个列表，否则会重复注入。

SOP：把流程定义成可验收步骤

SOP（标准作业流程）把「有哪些步骤、每步要证明什么」写死在代码里。 SOP _schema.py:415 只有三个字段： 

SOP(
    name="write-article",
    description="先大纲，后正文",
    steps=[...],
)

最常用的步骤是 SOPStep _schema.py:193：

参数 默认 说明
subject_schema.py:203必填步骤短名
description_schema.py:204必填这一步必须达成的结果，只写终点不写路线
executor_schema.py:205必填执行者，满足 AgentLike
verifier_schema.py:206None验证者；为 None 时交付即通过
max_attempts_schema.py:2073最多被驳回几次，超出后整个运行失败
 
from agentscope.sop import SOP, SOPStep

sop = SOP(
    name="write-article",
    description="先大纲，后正文",
    steps=[
        SOPStep(
            subject="列出大纲",
            description="给出一份至少包含三个章节的文章大纲。",
            executor=writer,
            verifier=reviewer,
            max_attempts=3,
        ),
        SOPStep(
            subject="撰写正文",
            description="严格按照上一步的大纲写出完整正文。",
            executor=writer,
        ),
    ],
)

同一个 Agent 用在多个步骤里，它的上下文在这些步骤间是连续的；每步换不同的 Agent， 上下文就互相独立。

验收不要单独写成一步

如果「检查大纲」是一个独立步骤，被驳回后重跑的是检查本身，结论不会变，直到次数用尽。 验收是 verifier 的职责，不是流程里的一个里程碑。

SOP 怎么跑：执行 → 验收 → 交接

SOPEngine _engine.py:24 按顺序推进，已完成的步骤跳过。每一步的一次尝试分两半：

阶段 发生什么
执行 执行者收到步骤说明与上一步交接，完成后以结构化输出交出 handover
验收 验证者看到步骤说明、输入与交付，以结构化输出给出 passed 与 message
通过 步骤完成，交付成为下一步的输入
驳回 清空交付，把 message 与「第几次尝试」交给执行者重做

步骤之间只传交付内容，不传文件或对话。第一步收到运行的输入，之后每一步收到的是 上一步的 handover，包在 <handover from="上一步名称"> 标签里。 所以执行者写交接时，要假设后续步骤没看过它的工作过程。

两种「重来」都消耗 max_attempts

和 GoalPipeline 不同，SOP 里下面三种情况都算一次驳回：

  • 验证者判 passed=False
  • 执行者结束了，但没给出结构化交付
  • 验证者结束了，但没给出结论

没有单独的 max_retries。这也是为什么 max_attempts 要留够余量。

进度事件

每次尝试前后各产出一个 CustomEvent：

事件名 value
SOP_STEP_STARTEDstep、attempt
SOP_STEP_ENDEDstep、phase

运行阶段由各步骤推算 _state.py:132： 全部未开始 PENDING、任一步失败 FAILED、全部完成 COMPLETED、 任一步挂起 AWAITING、其余 RUNNING。

运行状态与挂起恢复

SOPRunState _state.py:104 是纯数据：运行的输入、每一步的阶段、交付与历次结论。它可以直接存 JSON： 

from agentscope.sop import SOPEngine, SOPRunState

# 挂起后保存
saved = engine.state.model_dump_json()

# 之后用同一份定义 + 保存的状态重建
engine = SOPEngine(
    sop,
    SOPRunState.model_validate_json(saved),
)
SOPRunState 不包含 Agent 的上下文

执行者和验证者各自是 Agent，它们的对话与摘要要按 Agent 自己的方式另存， 再用它们重新构造 SOP。只恢复 SOPRunState 是不够的。

如果保存之后改了 sop.steps 的数量，重建时 SOPEngine 会抛 ValueError _engine.py:51。

挂起与恢复

执行者或验证者停在工具授权 / 外部执行上时，这一步进入 AWAITING， reply_stream 直接结束，不挂起协程。恢复时把结果事件喂回去， 引擎按 reply_id 找到挂起的那一步。 

async def resume(engine, confirm_event) -> None:
    async for event in engine.reply_stream(confirm_event):
        ...

UserInterruptEvent 是放弃：本次尝试作废，但不计入驳回次数， 这一步回到 PENDING。

自定义步骤

不是「一人执行、一人验收」的步骤，可以继承 SOPStepBase。 引擎只要求「一次调用就是一次尝试」，并在传入的 state 上记下结论： 

from agentscope.sop import SOPPhase, SOPStepBase, SOPStepRunState


class RunTests(SOPStepBase):
    async def reply_stream(self, inputs, state: SOPStepRunState):
        state.phase = SOPPhase.RUNNING
        passed, report = await run_test_suite()
        self.record(state, passed, message=report, verifier="pytest")
        return
        yield

record() 负责写结论；驳回时会清空交付并回到 PENDING。

Plan vs SOP vs Pipeline

场景 用什么 原因
步骤要边做边定 计划模式 模型自己拆解、调整，工具只是外部记忆
步骤固定，每步有验收 SOP 顺序与验收标准由开发者固定，可持久化
只有一个目标，反复逼近 GoalPipeline 执行者 + 验证者循环，只有一个验收闸门
多人分工，分派由模型决定 TeamPipeline 队长按成员描述分派，成员各用各的工具
固定流程图式的多 Agent 自己写代码编排 现有 Pipeline 只覆盖两种模式，复杂图用代码更清楚

陷阱与窍门

手动改任务时依赖只改一边

TaskUpdate 会自动维护 blocks 与 blocked_by 两端； 直接改 tasks_context 不会。只写 blocked_by 会让 TaskList 的阻塞提示和实际依赖对不上。

用非数字 ID

TaskCreate 用 max(int(id)) + 1 分配下一个 ID _create_task.py:105。 非数字 ID 会被忽略，之后自动分配的 ID 可能和它冲突。统一用 "1"、"2"。

以为阻塞会阻止执行

blocked_by 只是给模型的建议。运行时不会拦截一个被阻塞的任务， 真正要强制顺序，用 SOP 或流水线。

SOP 的失败次数比想象中少

执行者没交出结构化结果、验证者没给出结论，都会消耗 max_attempts。 如果你按 GoalPipeline 的「只有判 fail 才算」来设，很容易提前用尽。

SOP 的 description 只写终点

SOPStep.description 应该写「这一步交付什么、什么算完成」， 不要写具体操作步骤。执行者自己决定怎么做，验证者按同一段描述验收。

任务清单是 Agent 级的

两个 Agent 默认不共享 tasks_context。多智能体要共用计划， 需要显式把同一个 TaskContext 传进去，或由外层统一分发任务。

  1. Task.state 有几个合法值？把 status 设为 deleted 后任务还在列表里吗？
  2. 计划模式靠什么让模型在上下文压缩后还记得任务？
  3. SOP 里验证者判 fail 和「执行者没给结构化交付」，对 max_attempts 的影响一样吗？

20 分钟动手练习

  1. 用四个任务工具让 Agent 做一个三步任务，观察 TaskList 的输出与任务注入提示。
  2. 把两个任务设成依赖关系，再让模型故意先做被阻塞的那个，确认运行时不阻止。
  3. 定义一个两步 SOP，第一步带验证者、第二步不带，观察 SOP_STEP_STARTED / SOP_STEP_ENDED 事件。
  4. 把 engine.state 存成 JSON，重建引擎后继续跑。
