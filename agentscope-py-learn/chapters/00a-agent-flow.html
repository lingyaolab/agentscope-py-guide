最小链路：一条 reply 的 9 个节点

        

          L1 只有 9 个节点：消息进来，拼上下文，模型决定「说话还是调工具」，
          工具结果回填后再让模型收尾。这条链路里没有 Agent Service、工作区、SSE。
        

        

          

            
              
节点它做什么输出给谁

            
            
              
UserMsg用户输入的统一消息结构Agent.reply_stream

              
Agent创建 reply、组装本轮输入中间件 / 上下文

              
Context拼历史、system prompt、工具 schemaChatModel

              
ChatModel第一次推理，可能产出工具调用PermissionEngine

              
Permission决定工具调用是放行、询问还是拒绝Toolkit / HITL

              
Toolkit执行工具，产出 ToolResultBlock下一轮上下文

              
ChatModel 2带着工具结果再次推理AgentState

              
AgentState保存上下文、reply id、usage事件流 / 调用方

              
Output最终 Msg 与事件流业务代码或前端

            
          

        


        
服务化：加的 5 个节点

        

          L2 不是另起一条链路：它在 L1 的 9 个节点上新增 5 个，共 14 个。
          新增的是 Session、Workspace、Middleware、Offloader、SSE。
        

        

          

            
              
L2 的层插在哪它改变什么

            
            
              
Session +L2进入 Agent 之前user_id / agent_id / session_id、权限上下文与持久化

              
Workspace +L2Agent 组装时文件、MCP、技能、卸载内容进入工具面

              
Middleware +L2模型与工具前后追踪、预算、记忆、RAG、动态提示

              
Offloader +L2上下文变长时压缩历史或把大结果挪到工作区

              
SSE +L2Agent 之外事件扇出、回放、重连

            
          

        


        
生产化：再加 8 个外围节点

        

          L3 在 L2 的 14 个节点上再加 8 个，共 22 个：
          Auth、Gateway、Scheduler、Channel、Hubs、Sharing、Realtime、A2A。
          注意它们不是都塞进 ReAct 循环：Auth / Gateway 在入口，Scheduler 在触发层，
          Hubs 在资源层，Realtime / A2A 是旁路或对端。
        

        

          

            
              
外围设施接在哪对信息流的影响

            
            
              
Auth入站之前把请求变成可信 user_id

              
Gateway / 限流入站之后路由到会话、排队、配额检查

              
Scheduler触发层没有人类消息，也能按时间造一次调用

              
Channel入站把 IM 事件转成 Msg 与回复目标

              
Hubs资源层用户安装 MCP / 技能，再装配到工作区

              
Sharing资源解析跨用户凭证 / Agent / 知识库可见性

              
Realtime旁路音频进出模型，事件流仍走 Agent

              
A2A对端把远端 Agent 的事件流翻译成本地事件
