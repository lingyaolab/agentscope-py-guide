20 · 资源与多租户

15 章说每个请求都解析出 user_id，资源严格按用户隔离。但真实组织里， API key 是团队共用、Agent 要发布给部门、知识库要大家共建。 这一章讲 AgentScope 怎么在不引入用户/群组模型的前提下，把资源共享做安全。

读完你能做到

  • 说清 ResourceKind、ResourcePermission、ResourceRef 三个类型
  • 实现 ResourceAccessPolicyBase 并接到 create_app
  • 解释为什么共享凭证永远不会把密钥返回给访问者
  • 知道共享 Agent 时哪些东西不共享

先说为什么：多租户不是「加个 user_id」

默认隔离很容易：每条记录带 user_id，查询时按它过滤。但一旦要共享，问题就变成：

问题 不能怎么答
谁能看到这个 Agent？ 在服务里建一套用户/群组表 —— 会和公司现有 IAM 重复
共享的 key 会不会泄露？ 把凭证记录原样返回 —— 等于把密钥发给所有人
只读和可编辑怎么区分？ 再加一个布尔字段 —— 很快就会不够用
共享的 Agent 带不带原主人的工具和记忆？ 想当然地「一起共享」—— 会串数据

AgentScope 的答案是：服务不建模用户关系，只提供一个策略接口， 由部署者把任何身份系统（IAM、LDAP、配置、数据库）映射成资源引用。

三类可共享资源

ResourceKind _policy.py:19 只有三个值：

资源 共享后对方能做什么 不能做什么
CREDENTIAL_policy.py:22 用自己的会话使用该凭证调用模型 看到密钥原文
AGENT_policy.py:25 基于该配置创建会话、直接对话 继承原主人的工作区内容
KNOWLEDGE_BASE_policy.py:28 检索、引用其中的文档 在只读权限下修改文档

权限只有两级：READ 与 EDIT _policy.py:32。 EDIT 隐含 READ _policy.py:41。

ResourceRef：共享关系的四条信息

一个 ResourceRef _policy.py:51 就是一条授权：

字段 说明
kind_policy.py:60凭证 / Agent / 知识库
owner_id_policy.py:63资源属主的 user_id
resource_id_policy.py:68属主下的资源 ID
permission_policy.py:73READ 或 EDIT，默认 READ

注意：list_accessible 只返回跨属主的资源。 访问者自己的资源由服务从存储里合并，不需要策略重复返回。

ResourceAccessPolicyBase：两个方法

ResourceAccessPolicyBase _policy.py:79 只有两件事：

方法 必需 作用
list_accessible(viewer_id, kind, storage)_policy.py:91 是（抽象） 返回访问者可见的跨属主资源
can_edit(viewer_id, kind, owner_id, resource_id, storage)_policy.py:114 否 是否可修改；默认从 list_accessible 推导

can_edit 的默认实现很直接：属主永远可编辑 _policy.py:140； 否则在 list_accessible 里找匹配的 EDIT 引用 _policy.py:143。 如果你的 IAM 有更直接的权限查询，覆写它会更高效。

两个方法都会收到 storage，可以用于只读查询；策略本身不在 AgentScope 存储里维护用户、群组、成员关系。

默认策略：DenyAll

不传策略时，服务安装 DenyAllResourceAccessPolicy _policy.py:153， list_accessible 永远返回空 _policy.py:156。 也就是 15 章说的严格按用户隔离。 

app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
    # 不传 = DenyAll
)

create_app 的参数在 _app.py:133， 默认值在 _app.py:344 生效。

解析链：list / get / 运行时

ResourceAccessService _access.py:204 把存储与策略拼起来，提供三类入口：

入口 用途
list_resource(...)_access.py:232列表：自己的 + 策略返回的共享资源
get_resource(...)_access.py:324单条读取，同样合并两种来源

运行时的解析方法分别是 _access.py:410、 _access.py:437、 _access.py:480。 写操作前会调用 resolve_for_edit _access.py:516。

editable 视图：403 与 404 的区别

返回给前端的资源视图带一个 editable 标志，由引用权限算出。 这样前端不用再发一次鉴权请求，就能决定渲染只读还是可编辑。

情况 结果
只读共享，尝试 PATCH / DELETE403
完全不可见404
可编辑共享正常修改

这个区分很重要：404 不泄露「这个资源存在但你没权限」， 403 则明确告诉前端「你能看，但不能改」。

凭证共享：可以用，永远看不到

共享凭证只把「使用能力」给出去，不把密钥给出去：

  • 所有 list / get 响应里，凭证都脱敏，只显示 type 与 name
  • 原始密钥只在运行时构造 chat / embedding / TTS 模型时解析
  • 不要新增任何把已解析凭证返回给客户端的端点
ResourceRef(
    kind=ResourceKind.CREDENTIAL,
    owner_id="alice",
    resource_id="cred-openai-prod",
    permission=ResourcePermission.READ,
)

Bob 可以用这个凭证建会话、跑模型，但在任何 API 响应里都看不到 key。

Agent 共享：共享配置，不共享工作区

共享一个 Agent，共享的是它的配置：显示名、系统提示、context / ReAct 设置。

工作区内容不会跟着共享

MCP 客户端配置、技能、累积的记忆（MEMORY.md）都在按用户隔离的 workspace 里。 共享的 Agent 对每个访问者都是从干净 workspace 开始，不会继承属主的工具与记忆。 这是当前已知的缺口。

另外，如果 Agent 开启了 Invitable，访问者的 Leader 还可以用 AgentInvite 把它邀请进团队（17 章）。

知识库共享：检索与共建

ResourceKind.KNOWLEDGE_BASE 的 READ 表示可以检索、引用文档； EDIT 表示还可以修改知识库与文档。 

ResourceRef(
    kind=ResourceKind.KNOWLEDGE_BASE,
    owner_id="alice",
    resource_id="kb-handbook",
    permission=ResourcePermission.READ,
)

知识库功能本身要启用 knowledge_base_manager（15 章），否则共享也无处落地。

实现策略：接 IAM / LDAP / 配置

子类只需要把「访问者能触达谁」翻译成 ResourceRef： 

from agentscope.app.access import (
    ResourceAccessPolicyBase,
    ResourceKind,
    ResourceRef,
)
from agentscope.app.storage import StorageBase


class TeamResourceAccessPolicy(ResourceAccessPolicyBase):
    async def list_accessible(
        self,
        viewer_id: str,
        kind: ResourceKind,
        storage: StorageBase,
    ) -> list[ResourceRef]:
        refs = []
        for owner_id, resource_id, permission in await my_team_grants(
            viewer_id,
            kind,
        ):
            refs.append(
                ResourceRef(
                    kind=kind,
                    owner_id=owner_id,
                    resource_id=resource_id,
                    permission=permission,
                ),
            )
        return refs

    async def can_edit(
        self,
        viewer_id: str,
        kind: ResourceKind,
        owner_id: str,
        resource_id: str,
        storage: StorageBase,
    ) -> bool:
        if await my_is_team_admin(viewer_id, owner_id):
            return True
        return await super().can_edit(
            viewer_id,
            kind,
            owner_id,
            resource_id,
            storage,
        )
app = create_app(
    storage=storage,
    message_bus=message_bus,
    workspace_manager=workspace_manager,
    resource_access_policy=TeamResourceAccessPolicy(),
)
策略可以是纯配置

不必接 IAM。开发环境用一份字典把 viewer_id 映射到资源列表就够了； 生产再换成 LDAP / 数据库查询。

陷阱与窍门

在 list_accessible 里返回自己的资源

服务会把访问者自己的资源再合并一次，导致重复。策略只返回跨属主的部分。

忘了按 kind 过滤

一次调用只问一种资源类型。把凭证、Agent、知识库混在一个列表里返回， 会导致鉴权错位。

以为策略装了就会自动共享

策略只负责「谁可见」。没有引用、没有配置，默认还是 DenyAll 的效果。

自定义端点返回已解析凭证

共享凭证的唯一安全边界是「只在运行时解析」。任何把 key 返回给客户端的接口 都会把整套设计毁掉。

以为共享 Agent 会带工具和记忆

workspace 是按用户隔离的。共享的 Agent 对访问者是干净环境，MCP、技能、 MEMORY.md 都不会跟过去。

用 editable 驱动 UI

前端不需要自己猜权限：列表已经返回 editable。 只有 READ 的条目就不要渲染编辑与删除按钮。

自检三问

  1. list_accessible 为什么不能返回访问者自己的资源？
  2. 共享凭证后，访问者能看到密钥吗？密钥在什么时候被解析？
  3. 只读共享的资源被 PATCH 和完全不可见的资源被 GET，分别返回什么状态码？
