06 · 上下文管理

02–05 章里，上下文一直在悄悄增长：每轮对话、每次工具调用、每条工具结果都会追加进去。 这一章讲清三种机制——注入、压缩、卸载—— 以及三个决定「什么时候压、留多少」的比例。

读完你能做到

  • 用 trigger_ratio / reserve_ratio / context_buffer_ratio 算出压缩阈值与保留量
  • 说清一次自动压缩的五个步骤，以及摘要失败时的两条退路
  • 接一个 Offloader，让被压缩的消息和截断的工具结果还能被 Read / Grep 找回
  • 解释运行时状态注入为什么用 HintBlock 而不是改系统提示

先说为什么：上下文不是「越大越好」

上下文是智能体的工作记忆。它由三层拼成，每次模型调用前重新组装：

系统提示
你传入的 system_prompt + 技能指令 + on_system_prompt 中间件的改动。 这部分相对固定。
摘要
较早消息被压缩后的结构化摘要；只有发生过压缩后才存在。
最近上下文
尚未压缩的消息，以及运行时状态注入的 HintBlock。

上下文变长有三个代价：贵（token 费）、慢（首字延迟）、 笨（关键信息被稀释）。所以框架不是等撞墙才处理，而是持续做三件事：

机制 解决什么 代价
注入 让模型知道「现在几点、任务到哪、上下文快满了」 每轮多几十个 token
压缩 把较早的消息变成一份摘要 一次额外的模型调用；细节会丢
卸载 把被移除的内容写到文件，之后还能查 需要存储与生命周期管理

预算：三个比例决定「什么时候压、留多少」

预算的基准是 model.context_size，不是模型卡片上的真实窗口 （04 章讲过两者的区别）。三个比例定义在 ContextConfig _config.py:51：

比例 默认 作用
trigger_ratio_config.py:57 0.8（上限 0.9） 超过这个比例就触发硬压缩
reserve_ratio_config.py:62 0.1 压缩后保留最近多少比例的 token
context_buffer_ratio_config.py:66 0.2 提前多少比例开始提示「快满了」，也是自主压缩的生效区间

以 DeepSeek 默认的 context_size=65536 为例： 

硬压缩阈值 = 0.8 × 65536 ≈ 52429 tokens
开始提示   = (0.8 - 0.2) × 65536 ≈ 39322 tokens
压缩后保留 = 0.1 × 65536 ≈ 6554 tokens

也就是说：上下文到 60% 时模型会收到「快满了」的提示；到 80% 时框架强制压缩； 压缩后只留最近约 10% 的消息。剩下的 10%（0.9 - 0.8 以上）是留给压缩调用本身生成摘要的空间。

两条硬校验

这些比例不是随便填的，构造 Agent 时会校验 _agent.py:247：

  • reserve_ratio 必须小于 trigger_ratio_agent.py:256
  • 如果开了运行时注入或自主压缩，context_buffer_ratio 也必须小于 trigger_ratio_agent.py:269

否则抛 ValueError，因为「提示还没发出去就已经开始硬压缩」没有意义。

压缩是自动的，不用你手动调

每次推理前都会先调用一次 compress_context() _agent.py:1186； 没超过阈值时它是空操作。你手动调只是提前触发。

自动压缩：一次压缩的五个步骤

入口是 compress_context() _agent.py:387， 真正实现是 _compress_context_impl() _agent.py:491。

步骤 做什么 关键点
1. 限制图片 超过 max_image_num 的旧图片先卸载或删除_agent.py:512 先减图片，再算 token 才准
2. 数 token 把系统提示、摘要、上下文、工具 schema 一起估算_agent.py:516 用 count_tokens，是字节/4 的粗估
3. 判阈值 低于 trigger_ratio × context_size 直接返回_agent.py:519 空操作，不产生模型调用
4. 切分 按 reserve_ratio 留最近消息，其余待压缩_agent.py:549 工具调用 / 结果对保持成对，未完成的调用不移动
5. 生成摘要并更新 用结构化输出生成五字段摘要，替换旧消息_agent.py:642 摘要本身也消耗 token，会计入用量

摘要长什么样

SummarySchema _config.py:9 固定了五个字段，避免模型写成一锅粥：

字段 要求模型写什么
task_overview 用户的核心请求、成功标准、约束
current_state 已完成什么、改过哪些文件、产出什么
important_discoveries 技术约束、做过的决定、踩过的坑
next_steps 下一步做什么、阻塞点、优先级
context_to_preserve 用户偏好、领域细节、承诺过的事

摘要提示词还专门要求「自包含」：时间转成绝对日期，文件用完整路径，命令和报错原样保留 _config.py:82。 因为这份摘要之后可能被再次压缩，指代「上面那个文件」会彻底失效。

失败时的四条退路

情况 行为
系统提示 + 摘要本身就超阈值 直接抛 RuntimeError，无法压缩_agent.py:531
reserve_ratio 太大，没有可压的消息 把保留量降为 0 再切一次_agent.py:554
压缩调用本身超长 从最旧的消息开始丢，再重试_agent.py:647
摘要始终生成失败 默认退化为「截断最早消息」；compression_fallback_to_truncation=False 则抛错_agent.py:688

手动压缩与自主压缩

from agentscope.agent import ContextConfig
from agentscope.message import HintBlock


async def compress_now(agent) -> None:
    # 用 Agent 自己的配置
    await agent.compress_context()

    # 单次覆盖：更激进地压
    await agent.compress_context(
        context_config=ContextConfig(trigger_ratio=0.6, reserve_ratio=0.1),
    )

    # 告诉摘要「必须保留什么」
    await agent.compress_context(
        instructions=HintBlock(hint="保留所有文件路径与 API 签名。"),
    )

把 compression_tool_enabled 设为 True 后，模型会拿到一个 CompressContext 工具，可以自己决定「在两件事的交界处」压缩，而不是等硬阈值 _agent.py:443。 工具内部按 trigger_ratio - context_buffer_ratio 判断，没进缓冲区调用也不会变化； 它始终放行，不受权限确认影响。

工具结果截断：先保留，再卸载

工具结果是最容易撑爆上下文的东西：一次 cat 或一次搜索可能几十万字符。 每次工具执行完后，框架会单独检查它是否超过 tool_result_limit（默认 50000 token） _config.py:146。 

超出限额时：

[保留部分] + <<<TRUNCATED>>>
<system-reminder>The remaining content has been omitted for limited context.
You can refer to the file in '/path/to/tool_result-xxx.txt' for the truncated content if needed.
</system-reminder>

切分逻辑在 _split_tool_result_for_compression() _agent.py:3071： 按 token 找边界，文本块按比例截断，剩下的部分交给 offloader。标记的拼接在 _agent.py:2650。

没有 offloader 时，截断的部分就真的没了

标记只会写「已被省略」，不会给路径。模型之后想查也查不到，只能重新执行工具。 长任务建议一开始就挂上 offloader。

卸载：Offloader 协议与工作区目录

Offloader 是一个结构化协议 _offload_protocol.py:11， 实际有三个方法：

方法 持久化什么 返回
offload_data_block(block)_offload_protocol.py:11 图片、音频等二进制块 改成 workspace:// URL 的块
offload_context(session_id, msgs)_offload_protocol.py:25 被压缩的整段消息 可读路径
offload_tool_result(session_id, tool_result)_offload_protocol.py:43 被截断的工具结果 可读路径

所有内置工作区都实现了它。用 LocalWorkspace _local_workspace.py:65 挂载最简单： 

from agentscope.agent import Agent, ContextConfig, InjectionConfig
from agentscope.workspace import LocalWorkspace


async def build_agent(model, toolkit):
    workspace = LocalWorkspace(workdir="/tmp/agent_workspace")
    await workspace.initialize()

    agent = Agent(
        name="Friday",
        system_prompt="You are a helpful assistant.",
        model=model,
        toolkit=toolkit,
        offloader=workspace,
        context_config=ContextConfig(
            trigger_ratio=0.8,
            reserve_ratio=0.1,
            context_buffer_ratio=0.2,
            tool_result_limit=3000,
            max_image_num=5,
            compression_tool_enabled=True,
        ),
        injection_config=InjectionConfig(
            timezone="Asia/Shanghai",
            time_interval=1.0,
        ),
    )
    return agent, workspace

用完记得 await workspace.close()。目录结构是固定的：

{workdir}/
├── data/
│   └── {sha256}.png                 # 多模态文件，按内容哈希去重
└── sessions/
    └── {session_id}/
        ├── context.jsonl            # 被压缩的消息，一行一条
        └── tool_result-{id}.txt     # 被截断的工具结果

按 session_id 隔离，多个会话并发也不会互相覆盖 _base.py:1013。

自定义 Offloader

协议是结构化的，不需要继承，实现三个方法即可： 

class S3Offloader:
    async def offload_context(self, session_id: str, msgs: list) -> str:
        ...

    async def offload_tool_result(self, session_id: str, tool_result) -> str:
        ...

    async def offload_data_block(self, block):
        ...

把实例传给 Agent(offloader=...) 就生效。返回的字符串会原样写进提示里， 所以要么是模型能读的路径，要么是它能理解的 URL。

环境感知：四个维度的注入

压缩是「删」，注入是「补」。运行时状态会以 HintBlock 追加到上下文， 让模型持续感知四类会变化的信息 _agent.py:1366：

维度 注入内容 触发时机
时间 当前时间 + 时区 上下文里没有时间记录，或距上次超过 time_interval 小时
任务 进行中 / 待处理任务数量，提醒用 TaskList 有未完成任务，且上下文中没有任务工具调用或旧注入
上下文用量 当前 token 与压缩阈值；开了自主压缩还会提示「现在可以压」 回复第一轮，且进入 context_buffer_ratio 缓冲区
工具报错 「同一个调用连续失败 N 次，别再原样重试」 同名同参数连续失败达到 tool_retries_limit（默认 3）

一条典型注入长这样：

<system-reminder>Treat the following as the ground truth at this point of the
conversation. Anything stated earlier is outdated, and a later reminder, if any,
supersedes this one:
<current-time>2026-11-06T22:30:00</current-time>
<timezone>Asia/Shanghai</timezone>
<tasks>You have 1 in-progress tasks and 2 pending tasks. Use `TaskList` to view them.</tasks>
<tool-error>The last 3 calls to 'Bash' with the same arguments all failed. Stop retrying...</tool-error>
</system-reminder>

三个设计要点

  • 注入是持久的：它真的写进上下文，不是临时拼一下。这样模型能感知时间流逝 和每一步做了什么 _agent.py:1373。
  • 用 HintBlock 而不是改系统提示：系统提示不变，prompt caching 仍然有效 _agent.py:1377。
  • 只注入会变的信息：身份、长期指令这类固定内容应该放系统提示。混在一起会让缓存失效、 也让模型分不清哪条是长期约束 _agent.py:1381。

注入发生时，reply_stream() 会额外产出一个 HintBlockEvent （emit_hint_event=True 时），前端可以据此显示「环境已更新」。

陷阱与窍门

拿模型卡片的窗口当预算

压缩用的是 model.context_size（DeepSeek 默认 65536），不是卡片上的 1,000,000。 如果你希望按真实窗口预算，显式把 context_size 调到接近卡片值，否则会过早压缩。

比例组合直接抛 ValueError

reserve_ratio >= trigger_ratio，或开了注入时 context_buffer_ratio >= trigger_ratio，Agent 构造就会失败 _agent.py:247。 调参时先保证 buffer < trigger 且 reserve < trigger。

压缩发生在一件事做到一半

硬阈值不会等你收尾。开启 compression_tool_enabled，并在系统提示里要求模型 「完成任务后、开始下一件事前调用 CompressContext」，摘要质量会明显更好 _agent.py:447。

以为压缩是免费的

压缩本身是一次模型调用，输入是「系统提示 + 待压缩消息 + 压缩提示」，输出是摘要。 这次调用的 token 会记在上下文尾部 _agent.py:770。 频繁手动压缩会显著增加成本。

tool_result_limit 不是越小越好

设得太低，模型会错过关键输出（比如测试报错的最后几行），然后反复重跑工具。 先用默认 50000，发现某类结果特别大再针对性调。

卸载后要让模型知道去哪找

框架会自动在提示里写路径。如果你自定义 Offloader，返回的路径必须是模型能用 Read / Grep 打开的，否则等于没存。

自检三问

  1. context_size=100000、trigger_ratio=0.7、buffer=0.2 时，第几轮开始提示「快满了」？
  2. 压缩时为什么「未完成的工具调用」不能被移进摘要？
  3. 没有挂 offloader 时，被压缩的消息和被截断的工具结果分别去哪了？
