09 · 流水线

08 章之前，所有 Agent 都是「你问它答」。从这一章开始，多个 Agent 要协作。 流水线的价值不是「让 Agent 互相聊天」，而是把谁先谁后、失败怎么退回、最多几轮固定下来， 对外仍然只暴露一个 reply_stream。

读完你能做到

  • 解释 PipelineProtocol 为什么只需要一个方法，以及 Agent 为什么天然满足它
  • 用 GoalPipeline 搭一个「执行 → 验证 → 退回重做」的闭环
  • 用 TeamPipeline 让队长把任务分派给不同专长的成员，并知道并发边界
  • 用 reply_id 从统一事件流里区分是哪个 Agent 在说话

先说为什么：多 Agent 不该靠「互相喊话」

如果让几个 Agent 自由对话，问题会立刻出现：谁先说话？说到什么时候停？A 说完了 B 没听懂怎么办？ 某个工具要用户确认，整条链路停在哪？没有固定编排，这些问题只能靠提示词祈祷。

流水线把三件事固定下来：

职责 说明
固化运行逻辑 谁先谁后、什么条件退回、最多几轮，构造时确定，不交给模型临场决定
统一事件出口 内部所有 Agent 的事件从同一个 reply_stream 流出
处理人机交互 任一 Agent 停在工具授权上时，流水线结束事件流；恢复时按 reply_id 送回被挂起的那一个

AgentScope 目前有两种实现：GoalPipeline 与 TeamPipeline。 流水线模块仍标记为实验性，接口可能在后续版本调整。

PipelineProtocol：和 Agent 同一个入口

PipelineProtocol _base.py:15 只声明了一个方法： 

class PipelineProtocol(Protocol):
    def reply_stream(
        self,
        inputs: Msg
        | list[Msg]
        | UserConfirmResultEvent
        | UserInterruptEvent
        | ExternalExecutionResultEvent,
    ) -> AsyncGenerator[AgentEvent | Msg, None]:
        ...

注意它是普通 def，返回异步生成器，而不是 async def _base.py:18。 因为调用方是「调用它然后 async for」，不是「await 它」。

这个设计带来一个很实用的结果：Agent 本身就是「只有一个成员」的流水线。 凡是接受 Agent 的地方，都能直接传流水线： 

async def watch(target, inputs) -> None:
    async for event in target.reply_stream(inputs):
        print(event)


async def main() -> None:
    await watch(agent, msg)   # 单个 Agent
    await watch(pipe, msg)    # 流水线

终端调试器就是这样放宽的：launch_console(agent=pipe) 不需要任何适配代码。

GoalPipeline：执行者 + 验证者

GoalPipeline _goal_pipeline.py:55 的循环很固定：执行者产出，验证者判定，不通过就带着理由退回重做。 

        ┌────────── 不通过：带着理由退回 ──────────┐
        │                                        │
        ▼                                        │
输入 ─▶ 执行者 ── 产出 ──▶ 验证者 ──────────────┘
                            │
                            └── 通过 ──▶ 结束

构造参数 _goal_pipeline.py:59：

参数 默认 说明
executor 必填 干活的 Agent
verifier 必填 判定的 Agent
verifier_reset_context_goal_pipeline.py:63 True 每次 fail 后清空验证者上下文，避免被上一轮判词带偏
max_iters_goal_pipeline.py:64 10 最多被驳回几次
max_retries_goal_pipeline.py:65 3 任一方没给出合法结构化输出时，最多重问几次
目标不在构造函数里

构造时只给两个 Agent。目标来自第一次 reply_stream 的消息： 它既是交给执行者的任务，也是验证者对照的目标。 

from agentscope.agent import Agent
from agentscope.pipeline import GoalPipeline
from agentscope.tool import Toolkit


async def build_goal_pipe(workspace, model):
    tools = await workspace.list_tools()

    executor = Agent(
        name="Executor",
        system_prompt="You're a programmer named 'Executor'.",
        model=model,
        toolkit=Toolkit(tools=tools),
        offloader=workspace,
    )
    verifier = Agent(
        name="Verifier",
        system_prompt="You're a reviewer named 'Verifier'.",
        model=model,
        toolkit=Toolkit(tools=tools),
        offloader=workspace,
    )

    return GoalPipeline(
        executor=executor,
        verifier=verifier,
        max_iters=5,
    )

两个 Agent 共享同一个工作区很关键：验证者要能真的去读执行者写出的文件、跑测试， 而不是只听执行者说「我做完了」。

目标循环：pass / fail / impossible 与两套预算

执行者和验证者都通过结构化输出交付结果：

角色 字段 含义
执行者 report_goal_pipeline.py:22 成果说明：文件路径、入口、运行方式
验证者 result_goal_pipeline.py:34 pass / fail / impossible
验证者 message 未通过时说明缺什么、在哪改

判定后的走向：

  • pass 或 impossible → 结束_goal_pipeline.py:334
  • fail → message 包进提醒，交给执行者重做_goal_pipeline.py:357
  • 被驳回次数达到 max_iters → 停止，哪怕没通过_goal_pipeline.py:351

只有「判决失败」消耗 max_iters

情况 含义 消耗哪套预算
验证者判 fail 活儿确实没做好 max_iters
任一方没给出合法结构化输出 模型没按要求调工具，是故障不是判决 max_retries

这个区分很重要：把「模型忘了调 GenerateStructuredOutput」也算进驳回次数， 执行者会平白少几次机会。

另外，迭代预算记在流水线实例上 _goal_pipeline.py:90， 不是 reply_stream 的局部变量。所以中途因为 HITL 恢复，不会把已经用掉的次数清零。

TeamPipeline：队长 + 成员

TeamPipeline _team_pipeline.py:110 只固化「谁能被分派、结果回到哪里」，分派给谁、分派几次由队长自己决定。 

              ┌── TeamAssign(member="Researcher") ──▶ Researcher ──┐
              │                                                    │
输入 ─▶ 队长 ┤                                                    ├──▶ 结果 ─▶ 队长 ─▶ 输出
              │                                                    │
              └── TeamAssign(member="Coder") ───────▶ Coder ───────┘

构造参数 _team_pipeline.py:130： leader、members、reset_members=True。 成员用 TeamMember _team_pipeline.py:37 描述：

字段 说明
agent_team_pipeline.py:43 成员 Agent；它的 name 就是队长分派时引用的名字
description_team_pipeline.py:46 擅长什么、何时分派、会交回什么，会写进分派工具说明

成员名字必须互不相同，也不能和队长同名，否则构造时直接抛 ValueError _team_pipeline.py:149。 

from agentscope.agent import Agent
from agentscope.pipeline import TeamMember, TeamPipeline
from agentscope.tool import Toolkit


leader = Agent(
    name="Leader",
    system_prompt="You're a team leader named 'Leader'.",
    model=model,
    toolkit=Toolkit(),          # 必须带工具箱，流水线会注册 TeamAssign
)

pipe = TeamPipeline(
    leader=leader,
    members=[
        TeamMember(
            agent=researcher,
            description="Investigates a question and reports findings.",
        ),
        TeamMember(
            agent=coder,
            description="Writes and runs code in the workspace.",
        ),
    ],
    reset_members=True,
)

分派：TeamAssign 与结果回传

第一次运行时，流水线会往队长的工具箱注册一个外部工具 TeamAssign _team_pipeline.py:51。 它的参数只有两个：

参数 说明
member 成员名字，枚举限定在 members 里_team_pipeline.py:70
prompt 完整任务。成员看不到队长上下文，需要的信息都要写进来

TeamAssign 自己不执行，is_external_tool=True _team_pipeline.py:57； 流水线拦截它产生的 RequireExternalExecutionEvent，改去运行对应成员。 分派本身始终放行 _team_pipeline.py:89， 但成员自己的工具仍走各自的权限检查。

队长只看到最终回复

成员在自己的上下文里跑完，最终回复的文本与数据块被包装成 TeamAssign 的工具结果交回队长。 队长看不到成员中间的推理与工具调用，上下文不会被成员的过程撑满。

成员回复的结束原因决定工具结果状态：

结束原因 工具结果状态
completed / exceed_max_iters SUCCESS
interrupted INTERRUPTED
error ERROR

并发边界

  • 同一轮里，分派给不同成员的任务并发运行
  • 分派给同一成员的多个任务按调用顺序依次运行
  • 成员之间不直接通信，结果总是回到队长
  • 结果按队长调用的顺序排好，而不是按完成时间

实现上先按成员分组，每组内部串行，组之间用 asyncio.gather 并发 _team_pipeline.py:284； 最后按原始调用顺序排序再交回队长 _team_pipeline.py:374。

reset_members 默认是 True

同一次队长回复内，队长可以就同一件事追问成员；但队长回复结束后， 所有成员的上下文与摘要会被清空，下一次回复从头开始。要让成员跨回复保留记忆， 显式设 reset_members=False。

统一事件出口：reply_id 与 HITL

一条流水线只有一个 reply_stream，内部所有 Agent 的事件混在一起。 区分「谁在说话」靠 reply_id：它等于该 Agent 的 agent.state.reply_id。 

async def run(pipe, msg) -> None:
    async for event in pipe.reply_stream(msg):
        if hasattr(event, "reply_id"):
            print(event.reply_id, event.type)

HITL 怎么路由

任一 Agent 停在工具授权上时，流水线结束事件流，不挂起、不轮询。 恢复时把结果事件喂回去，流水线按 reply_id 找到被挂起的那一个：

流水线 路由规则
GoalPipeline 比 reply_id 是执行者还是验证者，交给对应方_goal_pipeline.py:175
TeamPipeline 不是队长的 reply_id 就交给挂起的成员；其余成员照常跑完，已完成结果先交回队长_team_pipeline.py:229 
async def resume(pipe, confirm_event) -> None:
    async for event in pipe.reply_stream(confirm_event):
        ...

UserInterruptEvent 是放弃：被挂起的 Agent 关掉未决工具调用，整条流水线随之结束。

怎么选：Goal vs Team vs 单 Agent

场景 用什么 理由
一个 Agent 就能完成 Agent 流水线不带来额外能力，只增加一层
有明确验收标准，需要反复改 GoalPipeline 验证者提供质量闸门，失败自动退回
任务需要不同专长，分派策略由模型决定 TeamPipeline 队长按成员描述决定给谁，成员各用各的工具
流程固定、步骤多、需要人工验收点 SOP / Plan（10 章） 任务清单与里程碑由框架维护，不是固定 Agent 图
部署成服务、多租户、团队工具 Agent Service / Agent Team（15、17 章） 那是服务层编排，不是 SDK 内的流水线

陷阱与窍门

GoalPipeline 构造时不传目标

目标来自第一次 reply_stream 的消息。如果你在构造函数里找一个 goal= 参数，会找不到；把任务写成第一条用户消息即可。

把 max_retries 和 max_iters 混了

前者是「结构化输出没生成对，重问几次」；后者是「验证者判 fail，允许重做几次」。 调大 max_retries 不会让执行者多几次机会。

验证者和执行者不共享工作区

验证者只能看到执行者写在 report 里的自述。如果它没有同一套文件工具与工作区， 所谓「验证」就退化成「听执行者汇报」。让两者共享 LocalWorkspace。

Team 的成员描述写得太泛

TeamMember.description 会写进 TeamAssign 的工具说明，是队长决定分派给谁的主要依据。 写「擅长写代码」不如写「修改工作区里的 Python 文件并运行测试，返回测试结果」。

用 reply_id 做前端分组

流水线事件是混流的。前端按 reply_id 分组成「执行者」「验证者」或「Leader / Researcher」， 比按事件到达顺序猜可靠得多。

自检三问

  1. GoalPipeline 里验证者判 impossible，会退回重做吗？会消耗 max_iters 吗？
  2. TeamPipeline 同一轮里分派给同一个成员两次，会并发吗？结果顺序怎么定？
  3. 流水线满足 PipelineProtocol，这对「把 Agent 换成流水线」有什么实际好处？

20 分钟动手练习

  1. 搭一个 GoalPipeline：执行者写一个排序函数，验证者跑测试并判定 pass / fail。
  2. 把 max_iters 设为 1，故意让验证者第一次判 fail，观察流水线何时停止。
  3. 搭一个 TeamPipeline，让队长把「查资料」和「写代码」分给两个成员，观察事件流里的 reply_id 切换。
