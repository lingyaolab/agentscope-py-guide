02 · 第一个 Agent

01 章的 Agent 没有工具，所以它只调用了一次模型就结束。这一章给它装上一个真正的工具，把 reasoning → acting → 再 reasoning 的循环跑出来，并讲清三件事： 工具函数怎么变成模型能看懂的 schema、一次 reply() 里到底转了几圈、以及它为什么会停。

读完你能做到

  • 用 FunctionTool 把一个普通 Python 函数变成 Agent 可调用的工具，并解释它生成的 schema 从哪来
  • 画出一次 reply() 的循环：哪一步调用模型、哪一步执行工具、cur_iter 什么时候加一
  • 看懂 finished_reason 的四种取值，知道 max_iters=50 限制的是什么

先说为什么：ReAct 不是「一次模型调用」

只调用一次模型时，模型只能基于「你给它的输入」回答。它没有办法在回答前查天气、读文件、跑测试—— 因为这些动作必须由外部代码执行，而模型只会输出文本。

ReAct 的做法是：把「可用的工具」一起告诉模型。模型如果觉得需要，就先输出一个工具调用请求； 框架执行工具，把结果追加回上下文；模型看到结果后继续推理，直到它输出一段纯文本作为最终回答。

Reasoning（推理）
把系统提示、历史消息、工具 schema 一起发给模型，拿回文本或工具调用请求。
Acting（行动）
对每个工具调用做权限检查，执行本地工具，把结果写成 ToolResultBlock 放回上下文。
Exit（退出）
模型这一轮只产出文本、没有工具调用，就把它作为最终 Msg 返回。

这个「下一步该做什么」的判断集中在 _agent.py:3512 的 _next_action()，返回三种动作之一：Reasoning、Acting、Exit。 整个循环就是一个 while True _agent.py:1143， 没有隐藏的递归。

最小可跑：一个能查天气的 Agent

在 01 章的环境里新建一个 main.py，只需要一个工具函数：

import asyncio
import os

from agentscope.agent import Agent
from agentscope.credential import DeepSeekCredential
from agentscope.message import UserMsg
from agentscope.model import DeepSeekChatModel
from agentscope.tool import FunctionTool, Toolkit


def get_weather(city: str) -> str:
    """查询指定城市的当前天气。

    Args:
        city: 城市名称，例如 "杭州"。
    """
    # 演示用假数据；真实项目里换成和风 / 高德 / OpenWeather 的 HTTP 调用
    fake = {"杭州": "晴，22°C", "北京": "多云，18°C"}
    return fake.get(city, f"暂无 {city} 的天气数据")


async def main() -> None:
    agent = Agent(
        name="Friday",
        system_prompt="你是一个乐于助人的助手。需要天气信息时调用 get_weather。",
        model=DeepSeekChatModel(
            credential=DeepSeekCredential(
                api_key=os.environ["DEEPSEEK_API_KEY"],
            ),
            model="deepseek-v4-flash",
        ),
        toolkit=Toolkit(tools=[FunctionTool(get_weather, is_read_only=True)]),
    )

    msg = await agent.reply(
        UserMsg(name="user", content="杭州今天天气怎么样？"),
    )

    print(msg.get_text_content())
    print("finished_reason:", msg.finished_reason)
    print("usage:", msg.usage)


if __name__ == "__main__":
    asyncio.run(main())

运行后你会看到类似这样的输出（天气内容来自工具，不是模型编的）：

杭州今天晴，气温 22°C。
finished_reason: completed
usage: Usage(input_tokens=..., output_tokens=..., ...)
为什么是 is_read_only=True

FunctionTool 默认走 ASK 权限 _adapters.py:134： 每次调用都要用户确认，否则 reply() 会停在「等待确认」。 查天气没有副作用，标记为只读后，DEFAULT 模式会走只读快速通道直接放行 _base.py:298。 权限系统本身是 08 章的主题，这里先借用「只读」这个语义。

逐行解读：工具函数怎么变成 schema

1. 工具名、描述、参数 schema 都是自动推导的

FunctionTool(func) 只做三件事 _adapters.py:57：

字段 来源 本例的值
name 函数名（可用 name= 覆盖） get_weather
description docstring 的短描述 + 长描述（可用 description= 覆盖） 「查询指定城市的当前天气。」
input_schema 类型注解 + docstring 的 Args:（可用 input_schema= 覆盖） {"city": {"type": "string", ...}}

这意味着两件事：函数最好有类型注解（缺失会退化成 Any，schema 失去类型约束）， docstring 用 Args: 格式。 少任何一个，模型看到的参数说明就会缺一块，工具调用成功率会明显下降。

2. 需要更复杂的约束时，直接传 Pydantic 模型

from pydantic import BaseModel, Field


class WeatherInput(BaseModel):
    city: str
    days: int = Field(default=1, ge=1, le=7)


def get_forecast(city: str, days: int = 1) -> str:
    return f"{city} 未来 {days} 天以晴为主"


weather_tool = FunctionTool(get_forecast, input_schema=WeatherInput)

枚举、数值范围、嵌套对象这类约束，用 Pydantic 模型表达最稳；自动推导只适合简单签名。

3. Toolkit 是工具的唯一入口

Toolkit(tools=[...]) 会把工具放进名为 basic 的默认工具组 _toolkit.py:88。 除了普通工具，它还负责注册 MCP 服务与技能——所以后面接 MCP 时，改的也是同一个对象。

4. 最终文本用 get_text_content() 取

Msg.content 是内容块列表，可能包含文本、思考、工具调用、工具结果。 get_text_content() _base.py:155 把所有 TextBlock 拼成一个字符串；没有文本时返回 None。

循环：一次 reply 里到底转了几圈

以「杭州天气」为例，一次 reply() 通常会转 两圈：

圈 这一步做什么 模型看到什么 模型输出什么
第 1 圈 reasoning 组装输入并调用模型 系统提示 + 用户问题 + get_weather 的 schema ToolCallBlock(name="get_weather", input="{\"city\":\"杭州\"}")
第 1 圈 acting 权限检查 → 执行工具 → 写回结果 — ToolResultBlock(output="晴，22°C")
第 2 圈 reasoning 带着工具结果再调用模型 上面的工具结果 纯文本「杭州今天晴，气温 22°C。」
Exit 没有工具调用，收口 — 最终 Msg，finished_reason=completed

对应到源码，关键调用点只有五个：

  1. 组装模型输入：_prepare_model_input() _agent.py:3253 把历史消息和工具 schema 一起准备好。
  2. 调用模型：_call_model() _agent.py:3291。
  3. 权限检查：_check_permission() _agent.py:2340。
  4. 执行工具：_execute_tool_call() _agent.py:2431 → _acting_impl() _agent.py:2785 → toolkit.call_tool()。
  5. 轮次计数：当这一轮产生的工具调用全部拿到结果后，cur_iter += 1 _agent.py:1269。
「一圈」的边界不是模型调用次数

如果模型一次返回了 3 个工具调用，框架会把它们都执行完，然后才把 cur_iter 加一。所以 max_iters 数的是完整的 reasoning-acting 轮次，不是模型调用次数，也不是工具调用次数。

终止条件：什么时候停，什么时候超限

reasoning-acting 循环的退出逻辑在 _next_action() 里，共有四种结局：

finished_reason 触发条件 你拿到什么
completed 模型这一轮只产出文本、没有工具调用 正常的最终回答_agent.py:3672
exceed_max_iters 轮次达到 max_iters，或强制收尾后仍无文本 通常是「已完成工作的总结」，也可能是一句超限提示_agent.py:3736
interrupted 用户中断，或流式响应被取消 已产出的内容 + 未完成工具调用的关闭结果_agent.py:1278
error 模型调用或框架内部抛错 结构化 error 字段

默认上限是 50 轮 _config.py:367， 可以这样改： 

from agentscope.agent import Agent, ReActConfig

agent = Agent(
    ...,
    react_config=ReActConfig(max_iters=10),
)
达到上限时框架还会再试一次

轮次刚好等于 max_iters 时，框架不会立刻放弃，而是追加一次 禁用工具的模型调用，要求它总结已有进展 _agent.py:3718。 这次调用有文本，你仍能拿到内容，但 finished_reason 是 exceed_max_iters。如果连这次也没有文本，才返回固定的超限提示。

另外，结构化输出会额外获得 structured_output_grace_iters（默认 5）轮宽限 _config.py:373， 防止模型因为忙着调工具而没来得及提交结果。结构化输出不在本章展开。

状态：对话历史放在哪，为什么 Agent 无状态

Agent 本身不保存对话；它把状态放在 self.state _agent.py:175。 不传 state 时新建一份 AgentState()，传了就复用。

AgentState 里和本章相关的是这几块：

字段 存什么 谁会读写
context 完整对话历史：用户消息、助手消息、工具调用与结果 每次 reasoning / acting 都追加
summary 上下文压缩后的摘要 06 章
reply_context 当前 reply 的 id、轮次、结构化输出 循环本身
permission_context 权限模式与规则 08 章
tool_context 工具激活状态、读文件缓存 工具系统

这就是「无状态引擎」的含义：同一个 Agent 实例连续调用 reply() 会记得上一轮， 因为状态还在 self.state 里；但换一个实例就什么都不记得，除非你把旧实例的 state 传过去。 

await agent.reply(UserMsg(name="user", content="我叫小明。"))
msg = await agent.reply(UserMsg(name="user", content="我叫什么？"))
print(msg.get_text_content())  # 会回答「小明」

只想让 Agent「看到」一条消息、但不触发回复，用 observe() _agent.py:382。 这是多智能体场景里传递上下文的标准做法。

状态可序列化

AgentState 是 Pydantic 模型，可以整体序列化成 JSON。跨进程恢复、会话服务、 断点续跑都建立在这个设计上，13 章与 15 章会展开。

流式：事件顺序与前端该怎么接

reply() 是「把事件流消费完，只给你最后一条消息」。想在界面上看到 「正在思考 → 正在调用工具 → 工具返回 → 继续回答」，要用 reply_stream() _agent.py:289。 

from agentscope.event import EventType
from agentscope.message import Msg

async for chunk in agent.reply_stream(
    UserMsg(name="user", content="杭州今天天气怎么样？"),
    yield_final_msg=True,
):
    if isinstance(chunk, Msg):
        print("\n[final]", chunk.get_text_content())
        continue

    if chunk.type == EventType.TEXT_BLOCK_DELTA:
        print(chunk.delta, end="", flush=True)
    elif chunk.type == EventType.TOOL_CALL_START:
        print(f"\n[tool] {chunk.tool_call_name}")

一次「工具 + 回答」的事件顺序大致是：

REPLY_START
  MODEL_CALL_START
  TEXT_BLOCK_START / TEXT_BLOCK_DELTA ... / TEXT_BLOCK_END
  TOOL_CALL_START / TOOL_CALL_DELTA ... / TOOL_CALL_END
  MODEL_CALL_END
  TOOL_RESULT_START / TOOL_RESULT_TEXT_DELTA ... / TOOL_RESULT_END
  MODEL_CALL_START              # 第二轮，模型看到了工具结果
  TEXT_BLOCK_START / TEXT_BLOCK_DELTA ... / TEXT_BLOCK_END
  MODEL_CALL_END
REPLY_END

事件类型定义在 _event.py:25。 两个容易忽略的点：

  • reply_stream() 默认不产出最终 Msg； 需要它时传 yield_final_msg=True _agent.py:298。
  • TOOL_CALL_DELTA 是 JSON 参数字符串的碎片，不是可以直接 json.loads 的完整对象； 要拿完整参数等 TOOL_CALL_END，或直接用 TOOL_RESULT_*。

陷阱与窍门

模型不调用工具，而是自己编答案

先检查三处：函数有没有类型注解、docstring 是不是 Args: 格式、description 有没有说清「什么时候该用它」。再确认模型本身支持工具调用（deepseek-v4-flash 支持）。 最后在 system_prompt 里明确要求「需要天气时调用 get_weather」。

程序卡住不动，reply() 一直不返回

大概率是工具权限走了 ASK：框架产出了 REQUIRE_USER_CONFIRM 事件并在等确认。 FunctionTool 默认就是 ASK _adapters.py:131。 只读工具加 is_read_only=True；需要执行副作用的工具，应该显式设计确认流程（08 章）， 而不是简单改成 BYPASS。

finished_reason 是 None

说明回复被挂起了，通常是等待用户确认或外部执行结果。不是失败，也不是完成； 需要把确认结果通过 UserConfirmResultEvent 传回去继续（08 章）。

同步工具会阻塞事件循环

FunctionTool 直接调用函数，只有返回 awaitable 时才 await _adapters.py:150。 工具里做慢速网络请求时，把它写成 async def 并用异步 HTTP 客户端，否则会卡住整个 Agent。

想强制工具自动放行，又不想改全局模式

FunctionTool 支持 permission= 参数，直接传一个 PermissionDecision(behavior=PermissionBehavior.ALLOW, ...) _adapters.py:67。 比把整个 Agent 切到 BYPASS 安全得多。
