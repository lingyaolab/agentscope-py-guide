22 · 测试与评测

改一句 prompt、换一个模型、调一次 temperature，Agent 的行为就可能变。 靠人工聊几句判断好坏，既不可重复，也不便宜。 这一章用 AgentScope 的公开接口搭一套分层回归集： 大部分测试不花钱，只有少量真实调用留给夜间任务。

读完你能做到

  • 写一个不访问网络的 ScriptedChatModel，按脚本返回模型响应
  • 从事件流里断言工具选择、工具结果与最终回答
  • 把一次运行固化成只包含稳定字段的黄金样本
  • 计算工具选择 / 成功率与检索的 recall@k、MRR
  • 设计一套按 PR、夜间、发布分层的 CI 门禁

先说为什么：评测不是「多跑几次」

「多跑几次看看」的问题不是不认真，而是不可比较：

做法 能回答 不能回答
人工聊几句 「这次感觉还行」 上次是不是更好？哪一类输入退化了？
跑一遍真实模型 「这次输出是什么」 同样的输入明天还会不会这样？
只断言最终文本 「答案对不对」 工具选错但碰巧答对；答案对但多花了五轮
回归集 + 行为断言 固定输入下的工具、状态、回答是否稳定 开放世界的全部情况，仍然需要抽样与人工

一个可用的评测至少要有三样东西：固定输入、 可观察的行为、可比较的基线。 好消息是，AgentScope 的事件流与消息块已经把行为暴露得很完整，不需要自己去猜。

AgentScope 2.0.11 没有内置 eval 模块

这一章不是调用某个 evaluate() API，而是用公开的 ChatModelBase、Agent 与事件类型搭一套最小回归集。 上游自己的单元测试也是这么做的。

测试金字塔：三层，三种花钱方式

层 模型 单次耗时 跑在什么时候 成本
L1 单元 / 契约 假模型 毫秒级 每个 PR、每次本地保存 0
L2 回放 / 黄金 固定响应或录制的消息 秒级 每个 PR 0
L3 真实模型冒烟 真实 provider 分钟级 夜间、发布前 按 token 计费
L4 模型裁判 / 人工 强模型或标注员 分钟到小时 周级、重大改版 最贵

原则是：能用确定性断言的就不要调模型； 必须调模型的，控制样本量；必须用裁判的，只做趋势判断，不做单次硬门禁。

假模型替身：ScriptedChatModel

假模型的关键不是「返回一段假文本」，而是控制每次调用的返回值， 这样才能构造「先调工具、再回答」这类多轮场景。 AgentScope 的模型基类只要求实现 _call_api _base.py:303， 上游测试里的 MockModel utils.py:51 就是同一个思路。 

from collections import deque

from pydantic import BaseModel

from agentscope.credential import CredentialBase
from agentscope.formatter import OpenAIChatFormatter
from agentscope.message import Msg
from agentscope.model import ChatModelBase, ChatResponse, ToolChoice


class ScriptedCredential(CredentialBase):
    @classmethod
    def get_chat_model_class(cls):
        return ScriptedChatModel


class ScriptedChatModel(ChatModelBase):
    """按预设顺序返回响应，不访问网络。"""

    class Parameters(BaseModel):
        pass

    def __init__(self, responses: list[ChatResponse]) -> None:
        super().__init__(
            credential=ScriptedCredential(),
            model="scripted",
            parameters=self.Parameters(),
            stream=False,
        )
        self.formatter = OpenAIChatFormatter()
        self._responses = deque(responses)

    async def _call_api(
        self,
        model_name: str,
        messages: list[Msg],
        tools: list[dict] | None = None,
        tool_choice: ToolChoice | None = None,
        **kwargs,
    ) -> ChatResponse:
        if not self._responses:
            raise AssertionError("脚本已用完：被测代码多调了一次模型")
        return self._responses.popleft()

ChatResponse _model_response.py:32 的最小必填字段只有 content 与 is_last； usage 可选，但在评测成本时建议填上，方便统计。

必须给假模型一个 formatter

Agent 在处理输入时会读 model.formatter.supported_input_media_types _agent.py:2063。 漏掉这一行，普通文本测试也可能在附件处理处直接报错。

别直接 import 上游的 tests.utils

MockModel 在源码仓库的 tests/ 里，不随安装包发布。 复制这个模式到自己项目的 tests/，比依赖内部路径稳。

需要流式时，不要返回单个 ChatResponse，而是返回一个异步生成器： 每个 chunk is_last=False，最后一个 is_last=True 且带完整内容与 usage。 ChatModelBase.__call__ _base.py:184 会把它们累积成完整响应，并处理中断与重试。

确定性断言：从事件流看行为

agent.reply() 只给你最终消息，过程信息在 agent.reply_stream() 的事件里。测试最关心三类事件：

事件 能断言什么 源码
ToolCallStartEvent 工具名、调用 id _event.py:313
ToolResultEndEvent 工具结果状态：成功 / 失败 / 中断 / 拒绝 _event.py:408
ReplyEndEvent 结束原因：完成 / 中断 / 超过迭代 / 错误 _event.py:111

下面这组测试让脚本模型先调一次天气工具，再给出最终回答： 

import unittest

from agentscope.agent import Agent
from agentscope.event import ToolCallStartEvent, ToolResultEndEvent
from agentscope.message import (
    Msg,
    TextBlock,
    ToolCallBlock,
    UserMsg,
)
from agentscope.model import ChatResponse, ChatUsage
from agentscope.permission import PermissionBehavior, PermissionDecision
from agentscope.tool import FunctionTool, Toolkit


def get_weather(city: str) -> str:
    """查询城市天气。"""
    return f"{city}：晴，24°C"


def make_toolkit() -> Toolkit:
    allow = PermissionDecision(
        behavior=PermissionBehavior.ALLOW,
        decision_reason="测试环境",
        message="allowed",
    )
    return Toolkit(
        tools=[FunctionTool(get_weather, permission=allow)],
    )


class WeatherAgentTest(unittest.IsolatedAsyncioTestCase):
    async def asyncSetUp(self) -> None:
        self.model = ScriptedChatModel(
            [
                ChatResponse(
                    content=[
                        ToolCallBlock(
                            id="call-1",
                            name="get_weather",
                            input='{"city": "Hangzhou"}',
                        ),
                    ],
                    is_last=True,
                ),
                ChatResponse(
                    content=[TextBlock(text="杭州晴，24°C。")],
                    is_last=True,
                    usage=ChatUsage(
                        input_tokens=32,
                        output_tokens=9,
                        time=0.01,
                    ),
                ),
            ],
        )
        self.agent = Agent(
            name="weather",
            system_prompt="你是一个天气助手。",
            model=self.model,
            toolkit=make_toolkit(),
        )

    async def test_tool_then_answer(self) -> None:
        events = []
        final: Msg | None = None
        async for event in self.agent.reply_stream(
            UserMsg(name="user", content="杭州天气怎么样？"),
            yield_final_msg=True,
        ):
            events.append(event)
            if isinstance(event, Msg):
                final = event

        calls = [
            e.tool_call_name
            for e in events
            if isinstance(e, ToolCallStartEvent)
        ]
        states = [
            e.state
            for e in events
            if isinstance(e, ToolResultEndEvent)
        ]

        self.assertEqual(calls, ["get_weather"])
        self.assertEqual(states, ["success"])
        self.assertEqual(final.get_text_content(), "杭州晴，24°C。")

ToolResultEndEvent.state _event.py:419 的取值来自 ToolResultState _block.py:185： success / error / interrupted / denied / running。 断言它比断言一段自由文本稳定得多。

yield_final_msg=True 会让流在最后额外产出一条最终 Msg；不传则只拿事件。最终文本用 get_text_content() _base.py:155 取，别自己拼。

先断言行为，再断言文本

工具名、状态、结束原因、轮次是稳定的；自然语言措辞不是。 行为断言失败时，定位也比 diff 一大段文本快。

金样本：只冻结稳定的部分

「黄金文件」不是把整个事件流 model_dump() 存下来—— id、时间戳、token 数每次都会变。只冻结你真正关心的行为签名： 

import json
from pathlib import Path

from agentscope.event import (
    ReplyEndEvent,
    ToolCallStartEvent,
    ToolResultEndEvent,
)


def behavior_signature(events) -> dict:
    return {
        "tools": [
            e.tool_call_name
            for e in events
            if isinstance(e, ToolCallStartEvent)
        ],
        "states": [
            e.state
            for e in events
            if isinstance(e, ToolResultEndEvent)
        ],
        "finished": [
            e.finished_reason.value
            for e in events
            if isinstance(e, ReplyEndEvent)
        ],
    }


def assert_matches_golden(events, path: str) -> None:
    expected = json.loads(Path(path).read_text(encoding="utf-8"))
    actual = behavior_signature(events)
    assert actual == expected, (
        f"行为与黄金样本不一致\n期望: {expected}\n实际: {actual}"
    )

对应的 tests/golden/weather.json： 

{
  "tools": ["get_weather"],
  "states": ["success"],
  "finished": ["completed"]
}

如果某些字段天生不稳定（比如耗时、模型返回的 id），上游测试用 AnyString utils.py:16 与 AnyValue utils.py:28 做「匹配任意值」的占位。你也可以在自己的断言里用同样的技巧。

  • 一个场景一个文件，命名对应输入，不要把所有场景塞进一个大 JSON
  • 黄金文件要进版本库，更新时必须能看到 diff 并有人 review
  • 不要把整段自然语言回答冻结成唯一正确解；用关键片段、结构或裁判分
  • 黄金文件是回归网，不是正确性证明：它只保证「没有意外变化」

工具指标：选对、传对、跑成功

工具场景至少要分三层看，否则「答对了」会掩盖很多问题：

指标 定义 失败意味着
选择准确率 期望工具名出现在实际调用里的比例 提示词、工具描述或路由有问题
参数正确率 入参 JSON 与期望字段 / 值一致的比例 schema 描述不清，模型在猜
执行成功率 ToolResultEndEvent.state == "success" 的比例 工具实现、权限或外部依赖有问题
任务完成率 ReplyEndEvent.finished_reason == "completed" 且回答通过检查 多轮规划或收尾有问题 
from agentscope.event import ToolCallStartEvent, ToolResultEndEvent


def tool_metrics(expected_calls: list[str], events) -> dict:
    calls = [
        e.tool_call_name
        for e in events
        if isinstance(e, ToolCallStartEvent)
    ]
    states = [
        e.state
        for e in events
        if isinstance(e, ToolResultEndEvent)
    ]

    expected = set(expected_calls)
    selected = expected & set(calls)

    return {
        "selection": len(selected) / len(expected) if expected else 1.0,
        "success": (
            states.count("success") / len(states) if states else 0.0
        ),
        "extra_calls": len(set(calls) - expected),
    }

extra_calls 很值得单独看：模型多调了一个无关工具， 最终答案可能仍然正确，但延迟和成本已经变差。

检索指标：recall@k 与 MRR

RAG 的回归要先单独测检索，再测生成。检索侧不需要模型参与， 只要你有「问题 → 应命中的文档 id」标注。 KnowledgeBase.search() _knowledge.py:197 返回按分数降序、已去重的 VectorSearchResult _vector_store.py:53， 每条带 document_id、score 与 chunk。 

def recall_at_k(expected_ids: list[str], results, k: int) -> float:
    top = {r.document_id for r in results[:k]}
    expected = set(expected_ids)
    return len(top & expected) / len(expected) if expected else 1.0


def reciprocal_rank(expected_ids: list[str], results) -> float:
    expected = set(expected_ids)
    for rank, result in enumerate(results, start=1):
        if result.document_id in expected:
            return 1.0 / rank
    return 0.0
指标 回答的问题 适合场景
recall@k 前 k 条里找回了多少应命中文档 「资料有没有被找到」
MRR 第一条正确结果排得多靠前 「用户能不能一眼看到」
引用命中 最终回答引用的文档是否在标注集合里 「生成有没有用对资料」
忠实度 回答是否只依据检索内容 通常需要裁判或人工
不同向量库的分数不可直接比较

VectorSearchResult.score 在同一后端内可排序， 不同距离度量之间没有统一尺度。跨库比较请用 recall@k / MRR 这类基于排名的指标。

生成侧再测：回答里是否包含应引用的事实、是否出现知识库之外的编造。 前者可以字符串 / 正则断言，后者才需要裁判。

模型当裁判：能用，但要防抖

开放式回答没有唯一解，常用 LLM-as-judge。它适合做趋势， 不适合做每次 PR 的硬门禁。至少要控制这几件事：

风险 做法
位置偏差（偏好第一个答案） 成对比较时随机交换 A/B 顺序，或两边各判一次取平均
长度偏差（偏好更长答案） 评分标准里明确「简洁不扣分」，必要时控制长度
裁判与被测模型同源 尽量用不同家族的模型；记录裁判版本
结果抖动 temperature 设低、固定随机种子、同一批样本多次取多数
成本失控 缓存「样本 + 回答 + 裁判版本」的判定结果，只重判变化项

裁判输出应该是一个带理由的结构化结果（分数 + 命中的评分项）， 而不是一句「好 / 不好」。理由让失败样本可复盘，结构化让统计可聚合。

CI 门禁：分层跑、按需花钱

上游仓库自己就是用 pytest + coverage 跑单元测试，并在三个操作系统上做矩阵 unittest.yml:1； pytest 在 dev 依赖里 pyproject.toml:203。 自己的 Agent 项目可以更简单： 

name: agent-regression

on: [pull_request]

jobs:
  unit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -e ".[dev]"
      - run: pytest tests/unit tests/replay -q

分层策略：

任务 触发 跑什么 密钥
PR 门禁 每次 push tests/unit + tests/replay 不需要
夜间冒烟 定时 20–50 条真实模型样本 仓库 secret
发布前 打 tag / 手动 完整回归集 + 关键 RAG 集 受控环境
周级评测 每周 LLM 裁判 + 人工抽查 受控环境
PR 不要拿仓库密钥跑真实模型

来自 fork 的 PR 默认拿不到 secret。即便能拿到，也不该让未审代码消耗你的额度。 真实调用放在受信任的分支或定时任务里。

成本控制：把评测预算花在刀刃上

评测成本 ≈ 样本数 × 每样本轮次 × 单轮 token。三个因子都能压：

手段 效果 代价
假模型覆盖主流程 把绝大多数回归压到 0 成本 测不到模型能力本身
按失败聚类抽样 少量样本覆盖多数退化 需要先有一轮全量结果做聚类
限制 max_iters_config.py:365 防止单样本无限调工具 可能截断需要长链路的样本
预算中间件 / 成本中间件 单样本超支立刻停 需要接第 21 章的 token 统计
缓存裁判结果 只重判变化项 缓存键要包含裁判版本与提示词哈希

每次评测结束都应该产出两份东西：通过率与 花费。只看通过率，很容易用十倍成本换一个百分点； 只看花费，又会把该跑的样本砍掉。

陷阱与窍门

把整段回答做成唯一黄金答案

换个同义句就红，团队很快就会开始无脑更新快照。 开放式回答用关键事实、结构或裁判分，不要逐字比。

假模型忘了 formatter

Agent 会读 supported_input_media_types，缺了就直接 AttributeError。假模型也要像真模型一样装配 formatter。

脚本用完返回兜底文本

多调一次模型被静默吞掉，测试会误报通过。脚本耗尽时应该直接抛错， 让「意外的额外调用」变成失败。

只测快乐路径

工具被拒绝、参数校验失败、模型超时、达到最大迭代，都是行为的一部分。 用脚本模型和固定事件同样能覆盖，不需要真实故障。

把裁判当唯一门禁

裁判本身有方差，模型升级还会漂移。它适合趋势与抽样， 不适合「差 0.1 分就阻塞合并」。

检索只测 top1

生成模型可能拿到第 3 条也能答对。只看 top1 会低估检索， 也看不到排序退化。至少同时看 recall@k 与 MRR。

把线上失败样本带回回归集

第 21 章的 span 里有完整输入输出。挑出失败案例，脱敏后写成固定脚本响应， 回归集会越用越值钱。
