08 · 权限与 HITL

05 章你给 FunctionTool 加了 is_read_only=True 绕开确认，但那只是最简单的场景。 真实系统里，工具会删文件、发消息、动生产库。这一章讲清权限的四种决策、五种模式、规则写法， 以及「停下来问人」之后怎么把结果带回去。

读完你能做到

  • 说出 DEFAULT 模式下一次工具调用的六步判定顺序
  • 写 allow / deny / ask 规则，并知道 rule_content 在不同工具上的语义
  • 解释 bypass_immune 为什么能挡住 allow 规则，以及 BYPASS 模式为什么挡不住
  • 完整走一遍 RequireUserConfirmEvent → UserConfirmResultEvent 的暂停与恢复

先说为什么：权限不是「加个 if」

一个布尔值 allowed 无法表达真实需求。你需要的是四种结果：

行为 含义
ALLOW 直接执行
DENY 拒绝，把「被拒绝」作为工具结果回给模型
ASK 停下来问用户，回复进入暂停状态
PASSTHROUGH 工具不表态，交给权限引擎继续匹配规则

而且判定不是一层：全局模式决定大方向，规则处理具体调用， 工具自己还能做安全检查，最后用户可以逐次确认。 这四层合起来才是权限系统。

五种模式：从 DEFAULT 到 DONT_ASK

模式定义在 PermissionMode _types.py:18：

模式 行为 适用场景
DEFAULT_types.py:81 只读自动放行，其余没有 allow 规则就问用户 默认，最安全
ACCEPT_EDITS_types.py:82 DEFAULT + 工作目录内的写入/编辑自动放行 用户在场、快速迭代
EXPLORE_types.py:83 只读放行，任何修改都拒绝 代码探索、做方案
BYPASS_types.py:84 跳过安全检查，只剩 deny / ask 规则 沙箱、完全可信环境
DONT_ASK_types.py:85 所有 ASK 转成 DENY 无人值守、定时任务
BYPASS 不是「更宽松的默认」

它会跳过工具发出的安全 ASK，包括 rm -rf /、写 ~/.bashrc、 命令注入模式。无人值守又想要安全，用 DONT_ASK，不是 BYPASS。

决策顺序：一次工具调用怎么被判定

引擎入口是 PermissionEngine.check_permission() _engine.py:77， 按模式分发。以最常用的 DEFAULT 为例 _engine.py:117： 

1. deny 规则命中        → DENY
2. ask 规则命中         → ASK（附带建议规则）
3. 只读快速通道         → ALLOW
4. 工具自己的 check_permissions：
     ALLOW / DENY       → 原样返回
     安全 ASK           → 原样返回，allow 规则不能覆盖
     普通 ASK / PASSTHROUGH → 继续
5. allow 规则命中       → ALLOW
6. 默认                 → ASK（附带建议规则）

顺序本身就是优先级：deny 最高，ask 次之，allow 只排在工具检查之后。 这解释了为什么「加了一条 allow 规则，危险操作仍然会问」——它压根走不到 allow 那一步。

判定结果是一个 PermissionDecision _decision.py:11， 除了 behavior 和 message，还有三个字段值得知道：

字段 作用
suggested_rules_decision.py:30 给用户「以后都允许」的候选规则
bypass_immune_decision.py:33 安全 ASK：allow 规则不能把它静默成 ALLOW
updated_input 允许引擎修正输入（比如清洗路径）

规则：allow / deny / ask 的写法

一条 PermissionRule _rule.py:8 有四个字段：

字段 说明
tool_name_rule.py:24 工具名，如 Bash、Write
rule_content_rule.py:28 匹配模式，语义随工具变化
behavior_rule.py:31 ALLOW / DENY / ASK
source_rule.py:34 来源，如 userSettings、projectSettings、session

rule_content 在不同工具上的语义

工具 匹配对象 示例
Bash 命令字符串，前缀通配 npm run:*、git commit:*
Read / Write / Edit file_path，glob src/**、config.json
其他工具 JSON 序列化后的参数 工具自定义

规则按行为分三个字典存：allow_rules、deny_rules、ask_rules， 都以工具名为 key _context.py:39。 运行时接受建议规则，会走 add_rule() 追加到对应列表 _engine.py:49。 

from agentscope.permission import (
    PermissionBehavior,
    PermissionContext,
    PermissionMode,
    PermissionRule,
)

permission_context = PermissionContext(
    mode=PermissionMode.DEFAULT,
    allow_rules={
        "Bash": [
            PermissionRule(
                tool_name="Bash",
                rule_content="npm run:*",
                behavior=PermissionBehavior.ALLOW,
                source="projectSettings",
            ),
        ],
    },
    deny_rules={
        "Bash": [
            PermissionRule(
                tool_name="Bash",
                rule_content="rm:*",
                behavior=PermissionBehavior.DENY,
                source="projectSettings",
            ),
        ],
    },
)

把它挂到 Agent 上，是通过 AgentState.permission_context _context.py:31：

from agentscope.state import AgentState

agent = Agent(

    toolkit=toolkit,

运行时切换模式也很简单：

工具内置检查：bypass_immune 与危险路径

规则是「用户配置的策略」，工具检查是「工具自己的安全判断」。工具在 check_permissions() 里可以返回 ALLOW、DENY 或 ASK。

最值得注意的是带 bypass_immune=True 的 ASK _engine.py:186。 它表示「这次调用危险到不能用规则静默放行」：

模式 安全 ASK 的处理
DEFAULT / ACCEPT_EDITS尊重；allow 规则不能覆盖
EXPLORE不适用（只读路径不调用工具检查）
BYPASS故意忽略；只剩 deny / ask 规则
DONT_ASK转成 DENY

内置 Bash 会做静态分析：命令注入、危险命令、危险路径、危险删除。 文件工具会保护 .env、.ssh/、.bashrc 这类路径。 这些判断都在工具自己的 check_permissions() 里，不是引擎硬编码的。

还有一条和模式无关的快捷通道：check_read_only() 返回 True 时， 所有模式都直接放行 _engine.py:659。 Bash 的 ls 算只读、rm 不算，就是靠这个方法动态判断的。

HITL：停下来，等一个结果事件

当判定是 ASK（或 PASSTHROUGH）时，Agent 不会执行工具，而是：

  1. 把工具调用状态改成 ASKING_agent.py:2570
  2. 产出一个 RequireUserConfirmEvent_agent.py:2576
  3. 直接 return，这一轮 reply 进入暂停_agent.py:2580

reply() 此时返回的消息 finished_reason 是 None， 表示「停靠中」，不是失败也不是完成。数据库里别把它当错误。

1. 接收暂停事件

from agentscope.event import RequireUserConfirmEvent


async def watch(agent, msg) -> None:
    async for event in agent.reply_stream(msg):
        if isinstance(event, RequireUserConfirmEvent):
            for tc in event.tool_calls:
                print(tc.name, tc.input)
                print("建议规则:", tc.suggested_rules)

2. 构造确认结果

from agentscope.event import ConfirmResult, UserConfirmResultEvent

results = [
    ConfirmResult(
        confirmed=True,              # 或 False 表示拒绝
        tool_call=tc,                # 可以修改后再传回
        rules=tc.suggested_rules,    # 接受后未来同类调用自动放行
    )
    for tc in event.tool_calls
]

confirm_event = UserConfirmResultEvent(
    reply_id=event.reply_id,
    confirm_results=results,
)

3. 恢复

async def resume(agent, confirm_event) -> None:
    async for follow in agent.reply_stream(confirm_event):
        ...

恢复时，_handle_incoming_event() _agent.py:1955 会把确认结果写回状态：

  • 确认 → 工具调用状态改为 ALLOWED_agent.py:1971
  • 接受规则 → engine.add_rule() 持久化_agent.py:1984
  • 拒绝 → 生成 DENIED 的工具结果，模型看到「被用户拒绝」_agent.py:1988
多个工具只确认了一部分

如果一批里有 3 个待确认调用，只传回 1 个，Agent 不会为剩下 2 个重新发请求事件。 前端必须自己保存未确认的列表，否则它们会一直停在 ASKING。

AskUser：让 Agent 主动问人

AskUser _ask_user.py:166 是内置的外部执行工具（is_external_tool=True _ask_user.py:211）。 它自己不含任何执行逻辑，只声明「要问什么」。

Agent 调用它时会产出 RequireExternalExecutionEvent 并暂停。 界面从 tool_calls[].input 里拿到问题结构，渲染成卡片或列表；用户答完后， 把一个 ToolResultBlock 放进 ExternalExecutionResultEvent 传回。 

from agentscope.event import ExternalExecutionResultEvent
from agentscope.message import TextBlock, ToolResultBlock, ToolResultState
from agentscope.tool import AskUserAnswer, AskUserMetadata

result = ToolResultBlock(
    id=tc.id,
    name=tc.name,
    output=[TextBlock(text="鉴权方式：OAuth 2.0")],
    metadata=AskUserMetadata(
        answers=[
            AskUserAnswer(
                question="接入哪种鉴权方式？",
                selected=["OAuth 2.0"],
                other=None,
            ),
        ],
    ).model_dump(),
    state=ToolResultState.SUCCESS,
)

resume = ExternalExecutionResultEvent(
    reply_id=event.reply_id,
    execution_results=[result],
)

output 写给模型读，metadata 按 AskUserMetadata _ask_user.py:131 的结构放同一份答案，供程序按选择分支。一次最多 4 个问题，每个 2–4 个选项 _ask_user.py:148。

拒绝之后：模型看到什么

用户点「拒绝」后，框架不会静默跳过，而是生成一条状态为 DENIED 的工具结果， 文本大意是「该工具的执行被用户拒绝」。模型会像读普通工具结果一样读到它，然后决定： 换个参数、换工具，或者直接向用户解释。

如果你希望「被拒绝就停止整轮」，把 ReActConfig.stop_on_reject 设为 True _config.py:385； 默认是 False，模型可以继续尝试别的办法。

拒绝信息要写清楚

拒绝结果里的文本会进模型上下文。与其只写「denied」，不如写「用户拒绝了删除 /data 的操作，因为该目录是生产数据」。模型下一轮会据此调整。

陷阱与窍门

用 BYPASS 解决「无人值守」

BYPASS 会跳过安全 ASK，rm -rf / 也能执行。无人值守应该是 DONT_ASK：只读放行、工作目录内编辑放行、其余 ASK 转 DENY。

以为 allow 规则能覆盖一切

bypass_immune=True 的 ASK 在 DEFAULT / ACCEPT_EDITS 下不受 allow 规则影响。 如果某条危险操作仍然被询问，先看工具是不是故意标了安全 ASK。

把 finished_reason=None 当成失败

它是「等待外部交互」的正常状态。前端应该展示确认卡片，而不是报错重试。

恢复时 reply_id 对不上

UserConfirmResultEvent.reply_id 必须与暂停事件一致，否则 Agent 无法把结果 关联回等待中的工具调用。跨请求保存时，把 reply_id 一起存。

用建议规则减少重复确认

RequireUserConfirmEvent 里每个工具调用都带 suggested_rules。 用户在界面上勾选「以后都允许」，就把这些规则放进 ConfirmResult.rules， 引擎会持久化，下一次同类调用自动放行。
