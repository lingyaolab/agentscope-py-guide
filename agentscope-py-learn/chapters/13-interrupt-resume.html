13 · 中断、恢复与状态

长任务最怕两件事：跑到一半被打断，以及重启后什么都不记得。这一章讲两套机制—— 干净地停下来（中断 / 取消）和接着跑（状态持久化 / 恢复）。 它们共同保证：无论停在哪，上下文都不会留下半截工具调用。

读完你能做到

  • 说清 AgentState 里哪些字段必须一起保存
  • 区分「运行中取消」与「挂起中中断」，知道各自触发什么清理
  • 用 reply(None) 和三类事件从断点继续
  • 用 RedisStorage 的 get_session / update_session_state 持久化会话

先说为什么：长任务最怕「从头再来」

一次长任务会经过很多步：模型推理、工具执行、等人确认、再推理。任何一步都可能被用户取消、 被进程重启、被服务扩容打断。如果状态只存在内存里，恢复就只能重跑整条链路——费钱、费时， 还可能产生重复副作用。

状态（State）
已经发生了什么：上下文、摘要、轮次、权限规则、任务清单。可序列化。
生命周期（Lifecycle）
怎么安全停下：取消正在跑的协程，或给挂起的回复发中断事件。
一致性（Consistency）
停下之后，每个 tool_call 都要有对应的 tool_result；否则下一轮模型输入是不合法的。

AgentState：一次回复的全部上下文

序列化与恢复：一份 JSON 带走

AgentState 是 Pydantic 模型，直接 model_dump_json() / model_validate_json() 即可： 

from pathlib import Path

from agentscope.agent import Agent
from agentscope.state import AgentState


def save_state(agent: Agent, path: str) -> None:
    Path(path).write_text(
        agent.state.model_dump_json(),
        encoding="utf-8",
    )


def load_agent(path: str, **agent_kwargs) -> Agent:
    state = AgentState.model_validate_json(
        Path(path).read_text(encoding="utf-8"),
    )
    return Agent(state=state, **agent_kwargs)

恢复时把 state 传给新 Agent 即可。模型、工具、工作区这些「配置」不在状态里， 需要你按原来的方式重新构造；状态只负责「已经发生了什么」。

别只存 context

只存消息列表看起来能恢复对话，但摘要、权限规则、任务清单、中间件预算全丢了。 长任务恢复后会表现得像「失忆 + 失权」：计划没了、之前允许的工具又要重新确认。

中断：运行中 vs 挂起中

两种中断方式，触发路径完全不同：

状态 怎么中断 发生什么
正在运行 task.cancel() Agent 内部收到 asyncio.CancelledError，走取消清理
挂起等待 HITL UserInterruptEvent(reply_id=...) 关闭未决工具调用，结束本次回复

运行中：取消任务

import asyncio


async def interrupt_running(agent, msg) -> None:
    task = asyncio.create_task(agent.reply(msg))
    await asyncio.sleep(1)
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        pass

取消后，_reply_impl 会捕获 CancelledError _agent.py:1272， 生成一个 finished_reason=interrupted 的 ReplyEndEvent， 再产出一条兜底助手消息 _agent.py:1299。 兜底文案由 interruption_message 控制 _config.py:395。

默认情况下取消异常会被吞掉，Agent 以「已中断」状态正常收尾。如果希望调用方还能感知 CancelledError，把 interruption_raise_cancelled_error 设为 True _config.py:402。

挂起中：发中断事件

from agentscope.event import UserInterruptEvent


async def interrupt_parked(agent) -> None:
    async for event in agent.reply_stream(
        UserInterruptEvent(reply_id=agent.state.reply_id),
    ):
        ...

如果 Agent 没有挂起（没有等待确认或外部执行），这个事件是空操作， 直接返回 _agent.py:1085。 只有确实存在待处理工具调用时，才会生成 INTERRUPTED 的结束事件。

取消时发生了什么：关闭未完成工具调用

这是中断最关键的一步。模型上下文里不能出现「有 tool_call 但没有 tool_result」的消息， 否则下一次调用模型时，厂商 API 会直接报参数错误。

_close_unfinished_tool_calls() _agent.py:971 会扫描最后一条助手消息，对每个还没有结果的 tool_call：

  1. 把状态置为 finished
  2. 产出 ToolResultStart / TextDelta / End 事件，状态是 interrupted
  3. 往上下文追加一条 ToolResultBlock，内容是「tool call has been interrupted by the user」 _agent.py:1027

这样恢复后，上下文里每个调用都有配对结果，模型可以正常继续。 这也是为什么中断不能只是「停止消费事件」——必须让 Agent 走到清理逻辑。

恢复：reply(None) 与三类事件

reply() / reply_stream() 的 inputs 除了消息，还接受三类恢复事件：

输入 用途
UserConfirmResultEvent 用户对工具授权的答复
ExternalExecutionResultEvent 外部执行的结果
UserInterruptEvent 放弃挂起的回复
None 没有新输入，从当前状态继续 
async def continue_reply(agent) -> None:
    msg = await agent.reply(None)
    print(msg.finished_reason)

None 适合「状态已经恢复、但还没有新消息」的场景。它会沿用当前 reply_context，继续原来的循环；如果 Agent 并没有挂起，它会按新的空输入继续推理。

HITL 恢复要对上 reply_id

确认和外部执行事件都带 reply_id。恢复时它必须与暂停时的回复一致， Agent 才能把结果关联回等待中的工具调用。跨进程保存时，把 reply_id 和状态一起存。

中断后想开始新一轮，直接传一条新的 UserMsg 即可：Agent 会保留 context，但生成新的 reply_id、cur_iter 归零。

一致性：哪些东西必须一起存

持久化的最小单位不是「消息」，而是「一次完整的回复边界」。建议在以下时机保存：

时机 保存什么 为什么
每次 reply 结束 整个 AgentState 上下文、摘要、预算、任务都一致
HITL 暂停 整个 AgentState + reply_id 恢复时要路由回同一个回复
长任务中间 整个 AgentState 不要只存 context，会丢其他状态
不要在一轮进行到一半时只存 context

此时最后一条助手消息可能只有 tool_call 没有 tool_result。单独存 context 再恢复， 会得到一份不合法的模型输入。要么等这一轮收口，要么连同 reply_context 和未完成工具状态一起处理。

还有三样东西不在 AgentState 里，需要单独管理：

  • 工作区文件：在 workdir / PVC / 沙箱文件系统里（12 章）
  • 本地技能与 MCP 声明：在工作区的 skills/ 与 .mcp 里
  • 外部长期记忆：Mem0 / ReMe 自己的存储（11 章）

存储后端：Redis / SQLAlchemy

SDK 层可以自己存 JSON；Agent Service 层用统一的 StorageBase _base.py:32。 内置两个实现：

实现 依赖 适合
RedisStorage_redis_storage.py:56 agentscope[storage-redis] 低延迟、会话热数据
AsyncSQLAlchemyStorage agentscope[storage-sql] 需要事务、查询、长期归档

RedisStorage 的构造参数 _redis_storage.py:152 就是标准连接参数： 

from agentscope.app.storage import RedisStorage
from agentscope.state import AgentState


async def load_state(user_id, agent_id, session_id) -> AgentState:
    async with RedisStorage(host="localhost", port=6379) as storage:
        record = await storage.get_session(
            user_id=user_id,
            agent_id=agent_id,
            session_id=session_id,
        )
        return record.state if record else AgentState()

SessionRecord _session.py:319 除了 user_id、agent_id、config，还带一个 state _session.py:452， 就是完整的 AgentState。

方法 用途
upsert_session(...)_base.py:369 创建或更新会话；首次创建用它
update_session_state(...)_base.py:435 只更新状态，聊天结束后的热路径
get_session(...)_base.py:489 读取会话与状态
update_session_state 要求会话已存在

它对不存在的会话抛 KeyError。第一次必须先 upsert_session 建立记录，后续轮次再切到 update_session_state。

会话隔离：user_id / agent_id / session_id

Agent Service 用三元组定位一份状态： (user_id, agent_id, session_id)。三者的含义：

  • user_id：谁的数据，决定权限与配额
  • agent_id：哪个 Agent 配置，决定模型、工具、系统提示
  • session_id：哪次对话，决定上下文与摘要

同一个 Agent 可以有多个会话，互不干扰；同一个会话也可以被同一用户重新打开继续。 AgentState.session_id 必须与存储键里的 session_id 一致， 否则恢复出来的状态会挂到错误的会话上。

SDK 层没有强制这套键，但建议照同样的结构自己存。最简单的做法是： f"{user_id}/{agent_id}/{session_id}.json"。

陷阱与窍门

只保存 context

摘要、权限规则、任务清单、中间件预算都会丢。恢复后 Agent 会重新问已经允许过的工具， 计划模式也会从零开始。保存整个 AgentState。

取消后不等清理就退出

task.cancel() 只是发出取消请求。要 await task， 让 finally 里的 _close_unfinished_tool_calls 跑完， 否则上下文里会留下半截 tool_call。

对没挂起的 Agent 发 UserInterruptEvent

它是空操作，不会停止正在运行的推理。运行中的中断只能靠 task.cancel()。

恢复时 reply_id 对不上

HITL 的确认 / 外部执行事件必须带暂停时的 reply_id。跨进程保存时， 把 reply_id 和 AgentState 一起存。

结构化 schema 会跟着状态走

reply_context.structured_schema 会被序列化成 dict。恢复后仍要求同一种输出结构， 但注意：从序列化状态恢复时只有 JSON schema，自定义校验器不会执行 _state.py:193。

工作区与记忆要单独持久化

AgentState 不含工作区文件，也不含 Mem0 / ReMe 的存储。 恢复时要同时把 workdir / PVC / 记忆后端接回原来的位置。
